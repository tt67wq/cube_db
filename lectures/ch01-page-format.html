1为什么存储引擎从「页」开始

是什么：cube_db 把整个数据库文件切成一格一格固定大小的 页（page，磁盘读写的最小方格，本引擎一页固定 4096 字节）。 每格有个编号（第 0 页、第 1 页……），引擎里所有的「指针」其实都是 页号（page number，一个 u32 整数，指向文件里第几格）。 想读第 100 页？文件偏移量 = 100 × 4096，就这么简单。

常量就两行：PAGE_SIZE = 4096（src/format.zig:5）、 PAGE_HEADER_SIZE = 24（src/format.zig:6，页头后面 1.2 节讲）。

为什么需要它：操作系统读写磁盘本来就不是按字节的——磁盘按「块」工作， 一次读太多浪费、太少又慢。既然硬件的最小单位是块，存储引擎就顺着它：把文件也切成同样粒度的方格。 更关键的是，「页号」把磁盘变成了一个巨大的数组：上层算法（B-tree，第 3 章见） 只需要说「给我第 100 页」，完全不用关心这页在文件里的偏移、在内存哪个地址、是不是在缓存里。

仓库货架：不管你存的是一根牙签还是一台冰箱，占的都是一整个货架位。 因为货架位大小统一，「3 号货架第 7 格」这句话对仓库里所有人（管理员、叉车、盘点员）都是无歧义的地址。 页就是 cube_db 的货架位，页号就是货架位编号。
为什么是 4096？因为主流文件系统与 SSD 的块大小就是 4KB。一次磁盘 IO 恰好搬一页， 不多不少。更大的页（比如 16KB）读一点数据也要搬一整页，小页则让「页头」这类管理开销占比变高。 4KB 是几十年来被验证的甜点值。

另外三个有固定编号的「特殊席位」也要记住（src/format.zig:20-22）：

页号名字作用
0NULL_PAGE「空指针」的页号版。凡是「没有下一页」「没有根」的地方都写 0。
1META_PAGE_0meta 页 A（数据库总目录，1.4 节讲）
2META_PAGE_1meta 页 B（总目录的备用副本，两份轮流写）

所以真正存数据的页从页号 3 开始。

2一页的解剖图

是什么：每一页——不管它是干什么的——都长一个模样：

页头（PageHeader，每页开头 24 字节的「说明卡」）有 5 个字段 （src/format.zig:40-46）：

字段类型偏移人话解释
page_nou320我自己是第几页。读到手里能自查「寄没寄错」。
page_typeu84我是哪种页（下一节的 6 种之一）。解码器靠它决定怎么解读正文。
genu645「世代号」。平时是写入时的提交序号；在 meta 页上它就是 sequence（src/format.zig:239），1.4 节会讲它怎么判新旧。
nkeysu1613这页装了多少条记录 / 条目。B-tree 页靠它遍历，墓碑页也拿它当条目计数（1.7 节）。
free_nextu3215freelist 链上的「下一页」页号；非 freelist 页恒为 0。注意：每种页只有一个「下一个」指针，所以它能免费借用给墓碑链（1.7 节）。

编码/解码就是把这些字段按小端序（little-endian，低字节放前面的一种字节摆放约定； 两台机器对同一个整数的字节摆放顺序必须一致，否则读出来就是错的）逐个写进/读出这 24 字节 （encodePageHeader src/format.zig:74、decodePageHeader src/format.zig:90）。

一页的格式是全引擎的「宪法」：24 字节头 + 4068 字节正文 + 4 字节 CRC，无一例外。 后面所有花样的区别只在正文里怎么摆。认死这个信封，读任何一页都不会迷路。

3六种页类型逐个图解

是什么：src/format.zig:9-17 定义了全部 6 种页类型。 为什么需要它：页头的正文区只有 4068 字节，解码器必须先知道「这页是哪类」， 才知道按哪种规则解读正文——同一串字节，按 LEAF 解读是记录，按 FREELIST 解读就是页号数组。

值类型是干什么的正文里装什么
0FREE空页，等待复用freelist 的页号数组（1.7 节）
1META数据库总目录（两份轮换）MetaPage 字段（1.4 节）
2BRANCHB-tree 的分岔节点一堆 key + 指向孩子页的页号（第 3 章）
3LEAFB-tree 的叶子，真正存数据key + value 记录（第 3 章）
4OVERFLOW大 value 的「仓库」一条 value 的续段，串成链（第 3 章）
5RANGE_TOMBSTONE「某段 key 区间已整体作废」的墓碑链页区间端点数组（1.7 节）
图书馆的书架都长得一样（= 页格式统一），但书脊上贴的分类色标不同（= page_type）： 蓝色是目录卡（META）、绿色是正文（LEAF）、黄色是「此架空闲」登记表（FREE）。 管理员拿到一册，先看色标，再决定用哪套规则翻它。
为什么 FREE 也是一种「类型」而不是「没有数据」？因为磁盘上没有真正的空字节—— 一页被释放后，它原来的字节还在那。把「我是废页、可复用」写成类型 0 存进页头， 引擎扫到它才知道这格货架可以重新分配，而不用额外的位图表去记哪些页是空的。

4meta 页：数据库的总目录

是什么：打开数据库后，引擎读的第一样东西不是数据，而是 meta 页（meta page，记录「整棵树从哪开始、空页都在哪」的总目录，存在固定的第 1、2 页）。 找不到它，后面 400 万页都是无字天书。

MetaPage 结构体在 src/format.zig:49-63，逐个字段拆开：

字段偏移人话解释
magic0魔数，固定 0x4355_4232（ASCII 就是 "CUB2"，src/format.zig:24）。读到一个文件，先看有没有这句「暗号」，没有就说明这不是本引擎的文件。
version4格式版本号（u16）。当前磁盘上有 v2 和 v3 两种合法版本（下面讲为什么）。
mapsize8映射区大小（第 7 章的 1TB 预留会用到）。
sequence16提交序号：每成功提交一次事务 +1。它是「哪份 meta 更新」的唯一裁判。
root_page24B-tree 根页的页号。整个数据库的入口。
entry_count28数据库里有多少条 key-value 记录。
byte_size36记录的总字节数（统计用）。
free_head44freelist 链头的页号（1.7 节）。
free_count48空闲页总数。
last_page56文件目前用到的最后一页号（文件长到哪了）。
tomb_head58range-tombstone 链头页号，0 = 没有墓碑。只有 v3 才写盘。

v2 → v3 的兼容处理：在旧格式尾部「加座」

meta 正文定长 62 字节（META_PAGE_PAYLOAD_SIZE，src/format.zig:28）， 但 v2 时代只有前 58 字节（META_PAGE_PAYLOAD_SIZE_V2，src/format.zig:29）。 后来加区间删除功能时需要一个新字段 tomb_head，怎么不砸了老文件？

  • 写：v3 版 meta 在 [58..62) 追加 tomb_head；v2 版这 4 字节保持 0（src/format.zig:168-173）。
  • 读：解码时先看 version——等于 3 才去读 [58..62)，是 v2 就直接给 tomb_head = 0，绝不去碰可能没定义的尾巴（src/format.zig:202-204）。
老式户口本的最后一页原本是空白页。新版登记办法在空白页上加了「宠物」一栏。 读户口本时先看封面版本：老版本就不翻那一页（视作「没养宠物」）， 新版本才读。户口本一行字没改动，新老办事员却都能读——这就是「尾部追加式」版本兼容。
sequence 是 meta 页的灵魂字段：两份 meta 都合法时，序号大的那个说了算 （src/format.zig:292）。第 5 章讲提交时会看到，整个「原子提交」就是围绕这个数字设计的。

5meta 的合法性判定：magic "CUB2"、双份互验、坏一份怎么办

meta 页只有一页大——万一写它的那一瞬间断电，它写了一半怎么办？引擎的答案： 准备两份（第 1、2 页），轮流更新，读的时候两份都验、择优录取。

单个槽位的判定分三层（readMetaPageSingle，src/format.zig:253-259）： ① 整页 CRC 要过；② 页头类型必须是 META；③ 解出来的 magic 必须是 "CUB2" 且版本合法。 任何一层不过，这个槽位就是 null（「此槽不可用」）。

这里有个非常讲究的区分（src/format.zig:261-274 的注释写得很清楚）：

  • 「被撕碎的槽」（CRC 都不过 / 全零）：可能是断电写一半的正常产物， 另一份 meta 完好即可安全启动 → 返回 null，走兜底。
  • 「完整的陌生人」（CRC 合法、格式工整，但 magic/version 认不出）： 这说明这个文件曾被另一个（可能更新的）程序写过。如果此时假装「没目录、当新库初始化」， 就会悄悄覆盖别人的数据——这是 T-49/T-50 号缺陷修掉的静默覆盖 bug。 所以正确动作是报 error.InvalidMeta 拒绝打开。

版本判定也有两个函数：老接口 isValidMeta 只认 v2（src/format.zig:220-221）， 实际打开文件用的是 isValidMetaAny，v2 和 v3 都收（src/format.zig:227-228）—— 对应 1.4 节的「尾部加座」兼容。

为什么「认不出的完整 meta」比「撕碎的 meta」更危险？因为撕碎几乎只能是物理损伤或断电， 而一份 CRC 完好、只是版本更高的 meta，意味着文件被别的写入者动过。 继续用另一份（更旧的）目录等于把时间拨回去——数据可能已经在新目录里发生了变化。 宁可拒绝服务，不可静默回滚。

6校验和：CRC32 与整页自覆盖

是什么：CRC（Cyclic Redundancy Check，循环冗余校验，一种「数据指纹」算法）： 把任意长的字节串压成一个 32 位指纹。数据哪怕只翻转一个比特，指纹也几乎必然对不上—— 所以「重算指纹 ≠ 存的指纹」就能断定数据坏了。

cube_db 的指纹规则（src/format.zig:118-136）：

  • 计算范围是 整页的前 4092 字节（page[0 .. PAGE_SIZE - 4]，src/format.zig:128）；
  • 结果（4 字节，小端序）写在页的最后 4 字节（setPageChecksum，src/format.zig:135）；
  • 验证 = 重算一遍，和页尾存的比对（verifyPageChecksum，src/format.zig:138-143）。

为什么放在页尾、校验「除自己以外的整页」？这就是整页自覆盖校验的巧妙处：

封箱时在箱底贴一张封条，封条上写着「箱内其他所有物品的清单指纹」。 验货时不看封条本身，把箱里其他东西重新点一遍、对上指纹就说明这一整箱没被调包。 封条贴箱底（页尾）而不是箱顶，是因为指纹算不出来的时候封条必须「不参与计算」—— 它覆盖的范围恰好是「除它以外的整页」，检查强度最大化，规则又只有一句。
为什么不每 100 字节一个小校验、坏了只重读那一小段？因为磁盘损坏几乎总是以「整页」为单位发生的 （坏块、写一半断电、mmap 页损坏），页级指纹已经足够发现它们，而整页一次 CRC 在 ARM64 上有 CPU 硬件指令加速（src/format.zig:119-121：aarch64 走硬件指令，其他平台软件查表，结果逐位一致）， 成本低到可以每页都算。
一个容易忽略的工程细节：encodeTombPage 写页前先 @memset 把整页清零 （src/format.zig:420）。因为缓冲区里可能有未初始化的随机字节—— 它们混进 CRC 计算的话，同一份逻辑数据每次写盘指纹都不一样，验证必然出鬼。算指纹之前，页必须是干净的。

7freelist 页与 range-tombstone 页的编码

这两类页是 format.zig 里最「值得画图」的部分，它们的共同套路： 16B 定长 entry 头 + 变长数据（墓碑页），或定长小数组（freelist 页）。

7.1 freelist 页：一页能记 1016 个空页号

空页太多了怎么办？freelist（空闲页链表，记录「哪些页可以复用」的链）： 每个 FREE 页的正文 = 4 字节「条目数」 + 一串 u32 页号，链与链之间用页头的 free_next 串起来。

一页能装多少个？MAX_FREE_ENTRIES_PER_PAGE = (4096 - 24 - 4 - 4) / 4 = 1016 （src/format.zig:34-36）——分子里两个 4 分别是「条目数计数」和「页尾 CRC」。

  • 写：writeFreelistEntries（src/format.zig:299）——先写计数，再逐个写 u32，剩余空间清零，最后重算 CRC。
  • 读：readFreelistEntries（src/format.zig:324）——直接借页缓冲区里的切片返回，零拷贝。它用 align(1) 诚实地声明「不保证 4 字节对齐」（正文从偏移 24 开始，24 不是 4 的倍数），靠 CPU 天然支持的非对齐读取省掉一次拷贝。

7.2 range-tombstone 页：「从 a 到 z 都删了」怎么存

是什么：range tombstone（区间墓碑，一条「[min, max) 范围内的 key 全部作废」的记录）。 删一千万个连续 key 时，逐个写「已删」标记要写一千万条；区间墓碑只写一条「这段全作废」。 一页装不下的墓碑，用页头的 free_next（此处借用为「下一链页」）串成链。

编码（encodeTombPage，src/format.zig:399）：

  • 每条墓碑先写一个 16 字节定长头（TOMB_ENTRY_SIZE，src/format.zig:340）： min 长度、max 长度、min 数据偏移、max 数据偏移，共 4 个 u32。
  • 所有定长头排前面，变长的端点字节串统一排在后面——这就是「16B 定长 entry 头 + 变长 bound」。
  • 长度字的编码很省：bit31 = append_zero 标志（表示「有效字节串 = 存的字节 + 一个 0x00」， 这是 succ(k) = k ++ 0x00 的紧凑编码，src/format.zig:354-359）； bit30 = 预留（未来「超长端点溢出存储」用，当前必须为 0）； 低 30 位才是长度。
  • 页头复用：nkeys = 墓碑条数，gen = 写入时的提交序号 （每条墓碑不单独存序号，统一继承页头的 gen，省 8 字节/条，src/format.zig:362-367）， free_next = 链上下一页。

错误处理分两级，不许混为一谈（src/format.zig:390-415）：

  • TombBoundTooLarge：单条墓碑 16 + min长度 + max长度 超 4068 字节预算——一条都装不下，属于「未来要靠溢出页解决」的问题；
  • TombPageOverflow：多条墓碑打包超页预算——正常现象，调用方拆成链页即可。

而且这两个检查必须先于一切位打包运行：它们保证条目数 ≤ 254、长度 ≤ 4052 < 2³⁰， 后面的 @intCast 才安全（src/format.zig:392-396 的注释专门叮嘱「Do not reorder」）。

解码（decodeTombPage，src/format.zig:475）面对的是磁盘上可能被伪造的字节， 所以每个字段都要设防：CRC 坏 → CorruptCrc；类型不对或预留位被置 → InvalidTombPage； 条目数超出正文容量、或「偏移 + 长度」越过正文边界 → Truncated（src/format.zig:482-511）。 注意偏移 + 长度是先升位成 u64 再相加——直接 u32 相加在 32 位平台上会溢出 panic（src/format.zig:505-510）。

区间墓碑像搬家公司的「整屋不搬」标签：不把每件不要的家具逐个贴条， 而是贴一张「这个房间的东西全不要」——房间号（min/max）写在标签上。 一页贴纸贴满了？再加一页（free_next 串链），一张清单永远查得到头。
两个 16B/定长的共同思想：元数据定长、数据变长、用偏移量连接。 定长头让「跳到第 i 条」是纯算术；变长区让短 key 不浪费字节。 B-tree 叶子页的 payload 编码（第 3 章）用的也是同一招。

8本章自测

不看上文，试着用自己的话回答。答不出就回到对应小节再读一遍。

  1. 断电瞬间的两份 meta：这次提交正在写 Meta 1，写了一半断电。重启时 readMetaPage（src/format.zig:285）会怎么判定 Meta 1？最终用哪份数据？ 如果 Meta 1 不是写坏的，而是 CRC 完好、magic 却是别的程序写的，行为又有什么不同，为什么？ （提示：1.5 节，「撕碎的槽」vs「完整的陌生人」。）
  2. CRC 的覆盖范围：整页 CRC 为什么只算前 4092 字节、却写在最后一格？ 如果把 CRC 放在页头、只校验正文，会漏掉哪类损坏？ （提示：1.6 节，封条要「不参与计算」才能自覆盖。）
  3. 一条墓碑多大：v3 的 meta 正文比 v2 多 4 字节（58→62）。多出来的 4 字节存的是什么？ 为什么 v2 的解码器不去读这 4 字节也不会出错？ （提示：1.4 节，先看 version 再决定读不读尾巴。）
如果三题都答顺了，你已经握住了这个引擎的「宪法」：统一页信封、页号即指针、 双 meta 乒乓、页级 CRC。下一章我们看引擎怎么把「磁盘」抽象成可插拔的 PageStore 接口——宪法之下的第一层政府。
