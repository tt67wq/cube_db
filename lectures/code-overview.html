1先搞懂：这个项目到底是什么

嵌入式（embedded）键值存储引擎：它不是一个像 MySQL、Redis 那样单独跑着的「数据库服务器」， 而是一个编译进你程序里的库。你的应用调用 db.put(key, value) / db.get(key)， 数据就存到本地一个文件里。SQLite 也是这类东西（嵌入式），但 SQLite 存的是表；cube_db 更底层，只存「键 → 值」。

把它想象成一个超大的、带目录的档案柜：你递给管理员一张纸条「把这个文件放到 3 号抽屉 X 格」， 管理员直接放好；下次你说「给我 X 格的文件」，他直奔目标，不用翻箱倒柜。 cube_db 的全部代码，就是在设计「抽屉怎么分格、目录怎么记、柜子着火（断电崩溃）后怎么保证档案不烂」。

README 里一句话定位：LMDB 风格架构 —— 纯 COW B-tree，freelist 页面复用，没有 WAL，靠原子切换 meta 页保证崩溃安全。 这句话里每个词你都会在第 2、5、7 节学明白。先记一个大局观：

  • 目标：又快又安全地存/取字节对，任何时刻断电，已提交的数据都不丢不坏。
  • 手段：数据按固定大小的「页」管理，用一棵 B-tree 做索引，写的时候从不覆盖旧数据。

2四个必须先懂的领域词

后面所有图解都围绕这四个概念。每个都按「它是什么 → 为什么需要它」讲。

① 页（Page）—— 磁盘读写的最小单位

操作系统读写磁盘时，不是一个字节一个字节来的，而是以块为单位。cube_db 把文件切成固定 4096 字节一页的方格，每页开头有 24 字节的「页头」说明这是什么页，结尾 4 字节放校验和（CRC，一种能发现数据被写坏的指纹）。

像一本书的「页码 + 页眉 + 正文」：装订好之后每页就是那么大，写不满也占一页。好处是引擎永远只需跟「第几页」打交道，寻址简单。

② B-tree —— 磁盘上的「多叉搜索树」

你肯定知道内存里的二叉搜索树。B-tree 是它的磁盘版：每个节点是一整页， 可以有很多个叉（本项目：叶子页最多 32 条记录，分支页最多 64 个孩子）。 按 key 排序存放，从根往下走几层就定位到目标 —— 百万级数据通常只要 2~3 层，也就是 2~3 次磁盘页读取。

查字典：先看「偏旁目录」（分支页），翻到对应区间（还是分支页），最后落到具体那一页（叶子页，真正存 key+value 的地方）。层数少，是因为每层的「岔口」多。

③ COW（Copy-On-Write，写时复制）—— 从不原地涂改

要修改一页时，不覆盖旧页，而是写一份新页放到别处，再把「指向它的指针」换过来。旧页随后回收进 freelist 等下次复用。

像在草稿纸上改论文：不是在原文上涂改（涂到一半笔断了，论文就毁了），而是誊一份新的，改新那份，改完才宣布「新版生效」。宣布生效之前，旧版始终完好。

④ 事务（Transaction）与 MVCC —— 多人同时用，各看各的版本

事务：一串操作要么全生效、要么全不算（比如转账扣钱和加钱）。 MVCC（多版本并发控制）：读操作看到的是「我开始读那一刻的数据快照」， 就算后来写的人提交了新数据，也不影响我正在读的旧快照 —— 因为 COW 保证了旧页一直没被覆盖。

图书馆的旧版百科全书不销毁，复印新版上架。正在查旧版的人继续查他的，不会因为「出了新版」手里的书突然变内容。谁在读旧版，旧版的那几页就不许回收（这就是代码里的 reader 水位线 / pending_free 机制要解决的问题）。
这四个词是互相咬合的：页是存储粒度，B-tree 是组织方式， COW 是修改方式（顺带送来了崩溃安全和 MVCC），事务/MVCC 是使用契约。 理解了这条链，整个项目的设计动机就通了 80%。

3全景：一座五层的楼（模块分层）

各文件一览（按建议阅读顺序）：

文件行数一句话职责
src/format.zig652「文件格式宪法」：页多大、页头长什么样、meta 页字段、CRC 怎么算。纯函数，不碰 IO。
src/page_store.zig260定义 PageStore 接口（用函数表 vtable 手工做的「多态」），外加一个纯内存实现 MemPageStore 给测试用。
src/file_page_store.zig1040生产实现：开机 mmap 预留 1TB 地址空间（LMDB 风格），读页零拷贝；写路径维护 freelist 页链、文件按需 ftruncate 长大、flock 排他锁防多开。
src/btree.zig2512项目最大文件：COW B-tree 本体。按 key 查找、插入、删除、范围扫描；把每条记录编解码进页 payload；大 value 挂 overflow 页链。
src/writer.zig1047「提交仪式」的操刀人：一个事务的批量修改怎么应用进树、旧页何时才能安全回收（MVCC 水位线）、meta 页怎么交替写完成原子提交。reader 句柄（beginRead/endRead）也在这。
src/db.zig1185门面：把上面所有东西包成 Db / WriteTxn / ReadTxn 三个用户对象，管 key 大小闸门、单写者互斥锁、sync 策略。
src/crc32_hw.zig129页校验和小加速：ARM64 用 CPU 指令算 CRC32，其他平台退回软件查表。结果逐位一致。
src/cube_check.zig159离线体检工具（独立可执行）：逐页验 CRC，报告坏页，用退出码说话（0 好 / 1 用法错 / 2 有损坏）。
src/root.zig / main.zig40root 是库的统一出口（re-export）；main 只打一行字证明能编译。
为什么要抽出 PageStore 这个接口？因为「B-tree 算法」和「数据真放哪」是两件事。 测试时把整棵树放进内存（MemPageStore，快、可注入崩溃、随便检查），生产时换成 mmap 文件， 树的一行代码都不用改。这是存储引擎最常见的可测试性设计。

5一次写入的旅程（核心流程）

用户侧写法：beginWriteTxn → 若干 put/delete → commit。 commit 内部发生的事，就是整个项目的灵魂：

版本化的维基条目：改词条不是直接编辑线上版（①~④ 全在草稿/影子页里进行）， 改完点「发布」的那一瞬间才切换（⑤ 写 meta）。点发布前服务器爆炸，线上版一个标点都没变过。 而「旧版本页面何时能从服务器删除」，要看还有没有人挂着旧版本在读（③⑥ 的 MVCC 回收）。
为什么改动要先「攒」（staging）再批量应用？因为事务可能有一万条 put。逐条改树 = 逐条重写路径上的页， 既慢又会产生大量中间垃圾页；攒到最后一次性排进树，同一条路径一页只复制一次，写放大最小。

6一次读取的旅程

读路径的设计目标是：连 read() 系统调用都不要有。

  1. 开机预留 1TB 虚拟地址空间（mmap）。不是真占 1TB 磁盘/内存 —— 只是「先把门牌号全包下来」，文件长到多大都能直接透过这块地址看到，永远不用重新映射。
  2. 读 meta 页 → 拿到根页号 → 顺着 B-tree 逐页往下走，每层就是一次数组下标访问（页号 × 4096 = mmap 里的偏移），零拷贝。
  3. 读事务开始时记下当前版本（快照）：此后写者再怎么提交，我走的还是我那棵旧树 —— 因为 COW，旧页还在原地没被动过。
  4. 范围查询（select）：定位到起始 key 的叶子页后顺着叶子页横向走就是有序的；区间删除的 RANGE_TOMBSTONE 页负责让扫描时跳过「已整段作废」的 key。
  5. 校验策略是分档的（CrcCheck = off / sample / full）：性能模式下每 64 页抽查 1 页，安全模式下全量验 CRC —— 读放大和安全性自己选。
1TB mmap 像整栋楼一开始就把所有房钥匙都配好了，后面每盖一层（文件 grow）直接用对应钥匙进， 不用重新配锁（remmap）。快照读则是你手里那本出发时复印的书：别人在后面修订新版，不影响你读手里这本。

7崩溃了怎么办：不用 WAL 的安全术

很多数据库（MySQL、Postgres）用 WAL（Write-Ahead Log，预写日志）：先把「我打算改什么」追加到日志，崩溃后重放日志恢复。 cube_db 反着来 —— 根本没有日志可重放，靠三样东西：

机制解决什么
双 meta 页交替写
Meta 0 ↔ Meta 1		 「目录」本身只有一页，写一半断电怎么办？准备两份，轮流更新：这次写 Meta 1，下次写 Meta 0。重启时两份都读，哪份 CRC 合法且序号新就用哪份。永远有一份是上一提交的完整版本。
COW：未提交的页不可达 崩溃时就算新数据页写了一半，meta 还指向旧树 —— 那些散落的脏页从目录上根本走不到，等价于不存在，不污染任何已提交数据。
页级 CRC + 离线体检 恢复只是「读两页 meta」（O(1)，不用扫全文件）。至于磁盘介质慢慢坏掉的页（bit rot），由 cube_check 工具离线逐页验 CRC 抓出来，退出码汇报。
持久性还分两档：Options{fsync} 默认 commit 时同步刷盘（最稳）；设成异步模式则系统帮你攒着刷， 想要稳时手动 db.sync()。这是「安全 vs 快」的旋钮，也是 README 里 async/sync durability 那条。

9推荐阅读顺序

按「先契约、后实现；先格式、后算法」的顺序，每步都带着第 2~7 节的一个概念去验证：

  • 第 0 步：docs/usage.md 前 3 节 —— 先当用户，知道 API 承诺了什么。
  • 第 1 步：format.zig —— 60 分钟读完页/头/meta/CRC 常量，第 4 节的图就在你脑子里了。
  • 第 2 步：page_store.zig —— 只有 260 行的 vtable 接口 + 内存实现，看懂「楼上的三层」。
  • 第 3 步：btree.zig —— 挑一条线走：get 查找路径（最短）→ 叶子 payload 编解码 → 插入的 COW 路径。对应第 5 节的步骤②。
  • 第 4 步：writer.zig 的 commit 编排 + db.zig 的 WriteTxn —— 把第 5 节六步逐一在代码里对号入座；重点看 pending_free 与 reader 水位线（第 2 节概念④）。
  • 第 5 步：file_page_store.zig —— 最后看 mmap/freelist 链/flock 这些「跟 OS 贴身肉搏」的部分（第 6 节），因为它最冗长也最不需要提前懂。
  • 选修：cube_check.zig（159 行，读完有成就感）+ crc32_hw.zig；再翻 tests/ 里任意一个 fuzz 测试，看「崩溃安全」是怎么被机器证明的。
检验你是否真读懂了这个项目的三个问题：① 为什么 commit 只需要「换 meta 页」这一动作就原子？ ② 为什么一个旧页「进了 freelist」还不代表「可以被覆写」？ ③ 为什么读方完全不需要锁？ 三个答案分别是：乒乓双 meta、reader 水位线、COW 快照 + mmap 只读指针。能用自己的话展开这三句，纲要就读完了。
