1树形与容量账：为什么百万数据只要走几页

是什么：cube_db 的所有键值对都组织在一棵 B-tree 里。 第 0 章说过：B-tree 是「多叉搜索树」的磁盘版，每个节点正好占一页（4096 字节）。 节点分两种：分支页（branch）只存「路标」，不存数据； 叶子页（leaf）才真正存 key 和 value。

这棵树的体型由两个常量定死（src/btree.zig:12-15）：

常量值含义
LEAF_MAX_ENTRIES32一片叶子页最多装 32 条记录
BRANCH_MAX_CHILDREN64一个分支页最多有 64 个孩子

现在做一道小学算术，看看这两个数字为什么「够用」：

  • 根分支页：64 个岔口 → 第 2 层有 64 个分支页
  • 每个分支页又是 64 岔 → 第 3 层有 64 × 64 = 4096 个分支页
  • 再来一层岔口：4096 × 64 = 262144 片叶子 × 32 条/片 ≈ 838 万条记录

也就是说，从根到叶子只需读 4 页（根 → 分支 → 分支 → 叶子）就能在 800 多万条数据里定位任意一个 key。 一百万条数据更宽松 —— 64 × 64 × 32 ≈ 13 万/层，三四层绰绰有余。 这就是 B-tree 相比二叉树的全部秘密：每层岔口极多，所以层数极少。

查字典从来不是从第一页翻起：先翻「部首目录」（根分支页），再翻「拼音索引」（下层分支页）， 最后落到印着正文的那一页（叶子页）。目录每层分得越细（岔口越多），需要翻的次数就越少 —— 64 岔的树翻 4 次，二叉树（每页只有 2 岔）翻同样次数只能覆盖 16 条数据。
为什么偏偏是 32 和 64？不是拍脑袋：一片 4096 字节的叶子页去掉页头（24B，format.zig:6）和页尾 CRC（4B）后， 还要装下 32 条「key + value + 每条十来字节的元信息」，再大就要溢出页了； 分支页的一个岔口只占 4 字节（一个 u32 页号），64 个岔口加路标 key 刚好也在一页内。 常量是被「一页装得下」这个物理约束倒推出来的，第 4 章讲分裂时会再见到它们的另一半 （LEAF_MIN_ENTRIES = 16，半满规则）。

2cmpKey：key 是「排序的字节串」

是什么：整个树里所有「往左还是往右」的判断，最终都落在同一个函数上 （src/btree.zig:33）：

pub fn cmpKey(a: []const u8, b: []const u8) std.math.Order —— 一行代码，直接调标准库的 std.mem.order(u8, a, b)： 按无符号字节逐个比，返回 lt / eq / gt。

为什么需要它：KV 引擎的 key 不是「字符串」而是字节数组（byte string）。 两者排序规则不同：

  • 字符串比较可能涉及编码、大小写折叠、本地化规则（「Apple」和「apple」谁在前？取决于你问谁）；
  • 字节串比较只有一条铁律：逐字节比 u8 值，结果永远确定、永远一致。

为什么必须「永远一致」？因为磁盘上的记录是按 key 排好序物理摆放的。 写入时按这个顺序放，读取时按这个顺序找 —— 两边必须用同一个 cmpKey， 否则找 key 时「该往左」的数据被写到了右边，树就废了。 字节序比较没有丝毫歧义，是唯一能让「写」和「读」跨越时间、跨越进程保持一致的规则。

图书馆给书编索书号：如果按「书名的意思」排，两个管理员会吵起来（《三国演义》算文学还是历史？）； 按一串固定编号的数字逐位比，谁都不会排错。key 排序要的不是「合理」，是「无歧义」。

顺带一提：这个设计把「想要什么样的排序」交给了上层 —— 想让时间序列按时间排？把时间戳编码进 key 的前几个字节即可。 引擎本身只认识字节。

3get 的一次旅程：meta → root → branch → leaf

是什么：点查询 get(key) 的核心是 getChecked （src/btree.zig:613）。它做的事用一句话说：从根页号出发，一层层往下换页号， 直到落在一篇叶子上，在叶子里线性扫描找 key。

先补一个第 1 章的衔接：get 的入参不是「数据库」，而是 root（根页号）。 根页号从哪来？上层（db.zig）先读 meta 页（数据库总目录）拿到当前版本的根页号，再把它递进来 —— 所以本章只管「从根往下」这一段。

getChecked 的骨架（去掉防御性检查后）只有三种动作：

  • 读一页：readNodePayloadPolicy(store, cur, crc) —— 按第 2 章的 PageStore 接口读当前页号，拿到页的 payload 部分（去掉 24B 页头和 4B CRC）；
  • 是叶子？ payload[0] == LEAF_KIND（值为 2）→ 交给 findInLeaf（btree.zig:629）在叶子里找；
  • 是分支？ → findInBranchPayload（btree.zig:789）算出「该进哪个孩子」，把 cur 换成那个孩子的页号，回到第一步。

分支页怎么选岔口（findInBranchPayload，btree.zig:789）： 分支页存着若干分隔 key（separator）和一排孩子页号。 规则是：找到第一个大于目标 key 的分隔符，进它左边那个孩子；没有比它大的，就进最后一个孩子 —— 这就是普通的「二分区间」语义，只是这里用 cmpKey 线性扫一遍分隔符。

叶子页怎么找（findInLeaf，btree.zig:629）： 从第一条记录开始逐条扫，key 小于目标就跳过、等于就命中、大于就说明不存在（数据有序，后面不可能有了）。 命中后还有两个分支，正好对应接下来两节：

  • 记录带着 tombstone（墓碑，1 字节的「已删除」标记）→ 返回 null：key 存在过，但已被删；
  • value 带 overflow 标志 → 读 4 字节溢出页号，顺着链把大 value 拼回来（见第 5 节）。
三个值得咀嚼的细节：① 树的「指针」就是 u32 页号，没有任何额外内存结构； ② 每层下降 = 一次 store.readPage()，第 2 章的接口抽象在这里兑现：同一份 btree 代码，内存实现和 mmap 文件实现都能跑； ③ depth < 1000 的护栏（btree.zig:617）：页数据万一损坏出现「环」，报错而不是死循环。

4叶子页 payload 编码：4KB 里怎么塞记录

是什么：一页 4096 字节，去掉页头（24B）和页尾 CRC（4B），剩约 4068 字节的 payload。 encodeLeafPayload（src/btree.zig:279）负责把一组记录按固定格式塞进去； decodeLeafPayload（btree.zig:322）负责原样解出来。

格式没有魔法，就是「头 + 一串变长记录」紧挨着排：

部位字节数内容
叶子头3类型标记 LEAF_KIND（1B）+ 记录条数 nkeys（2B，小端 u16）
每条记录1tombstone：1 = 这条 key 已被删除（墓碑标记）
4klen：key 长度（u32 小端）
klenkey 本体（变长）
4vlen：value 长度（u32 小端）
1 + ?flags（1B）：普通值 = 后面直接跟 value 本体；overflow 位（btree.zig:179 的 LEAF_FLAG_OVERFLOW）= 后面只跟 4 字节溢出页号
像快递面单：[1B 是否易碎(墓碑)] [4B 收件人名字多长] [名字] [4B 货物多长] [1B 是否超大件] [货物 或 超大件提货单号]， 一张张面单首尾相接贴成一页。字段全是「长度 + 本体」，所以变长 key/value 不需要分隔符，扫到哪算哪。

为什么这么设计，三个点：

  • 解码零分配：decodeLeafPayload 解出的 key/value 是直接指向页 payload 内部的切片（btree.zig:345-360 附近），不复制数据。数据本来就在 mmap 的页里，复制纯属浪费 —— 这是整个读路径「零拷贝」哲学的第一块拼图；
  • 墓碑不删数据只打标记：删除一个 key 时，写入路径把那条记录的 tombstone 位翻成 1（第 4 章详讲），读路径见到标记当作「不存在」。物理删除要整理页面，打标记只改 1 字节 —— 崩溃安全和 MVCC 都依赖「旧页永不被改动」；
  • 截断防御：decode 每读一个字段前都检查 pos + len > payload.len 返回 error.Truncated（如 btree.zig:331）。磁盘上的字节不可信，解析器永远假定「页可能是坏的」。
记住这个布局，第 4 章写路径会反复用到：插入 = 在排好序的位置重新编码整个 payload 写新页； 分裂预算的推导（MAX_KEY_SIZE，btree.zig:173）也完全建立在这套「3B 头 + 每条 10B 固定 + 变长」的账上。

5大 value 的去处：overflow 页链

是什么：叶子页只有约 4KB，而 value 可能几 MB。装不下怎么办？ —— value 留在叶子里的资格有上限：MAX_INLINE_VALUE = 3800 字节（src/btree.zig:134）。 超过预算的 value 不进叶子，而是被 writeOverflowPages（btree.zig:181）切成若干块， 每块塞一页 OVERFLOW 页，页与页之间用页头里的 free_next 字段串成单向链表； 叶子里只留一个 4 字节的「链头页号」。

为什么阈值是 3800 而且有两个条件：这就要看 inlineValueBudget(key_len) （btree.zig:148）—— 一条记录能不能留在叶子里，不是只看 value 自己，而是看 key + value 的组合：

  • 条件一：value ≤ MAX_INLINE_VALUE（3800）—— 给同页其他记录留余量，别让一个大 value 独占一页；
  • 条件二：3（叶子头）+ 10（每条固定开销）+ key 长度 + value 长度 ≤ 页 payload 上限 —— 组合起来不能撑爆一页。

两个条件取更严的那个。所以一个 3000 字节的 value 配一个 1200 字节的 key 也会被送去 overflow —— 组合超预算了。这就是源码注释里反复强调的 composite-aware（组合感知）判定（btree.zig:137-150）。

行李托运：随身包（叶子页）塞得下小件，但每人限重 3800「克」，且你和你的行李加起来不能超载 —— 超了不是因为行李大，而是因为「你 + 行李」这个组合超了。超载的行李贴个签（4B 页号）送去货舱（overflow 链）。
读路径的三个入口（get / getInto / Iterator）读溢出链都走同一套逻辑：顺着 free_next 逐页搬字节 （readOverflowValue / readOverflowValueInto）。get 版本先整块分配再填； getInto / Iterator 版本直接往调用方的缓冲区里逐页拷 —— 又是零拷贝思想：不多搬一趟。

6select 与 Iterator：范围扫描、getInto 零拷贝

select：只定位起点，不搬数据

是什么：select(min, max)（src/btree.zig:2420，带 CRC 分档的版本是 selectChecked，btree.zig:2426）做范围查询。它返回的不是一个装满结果的数组，而是一个 Iterator（迭代器） —— 一个记录着「我现在走到哪了」的光标对象。

为什么：一次范围查询可能命中上百万条，一次性装进内存既慢又爆。 「给我一个光标，我调一次 next() 你给我一条」—— 想要几条走几条，不要了直接丢。 定位起点的过程和 get 一样：从根下降，按 min 选岔口，落到第一片目标叶子。

Iterator 怎么「横向走」

迭代器本体在 btree.zig:2203。它维护一个下沉栈： 定长数组 frames: [MAX_DEPTH]Frame（MAX_DEPTH = 64，btree.zig:2243），每帧记 { page_no, child_idx } —— 「我在这一层的这个分支页，正看着第几个孩子」。 当前叶子扫完后，stepToNextLeaf（btree.zig:2338）：

  • 把栈顶帧的 child_idx + 1：右边还有孩子 → 进去一路「最左边」扎到底（descendLeftmost），落到下一片叶子；
  • 右边没了 → 弹栈，回到上一层的分支页继续找 —— 和二叉树的中序遍历是同一个思想。

因为叶子页本身就是按 key 顺序串着的逻辑序列（树把 key 有序地摊在各片叶子上），「中序遍历」就是全库有序扫描。 next()（btree.zig:2298）每吐一条前做四道过滤：跳过 tombstone、跳过 < min 的、碰到 ≥ max 直接结束、 可选的注入式过滤钩子（skip_fn，给上层做区间删除阴影用，第 4/6 章见）。

getInto：把「零拷贝」拧到最后一滴

get（btree.zig:607）命中后要 allocator.dupe 复制一份 value 给调用方。 getInto（btree.zig:691，策略版 getIntoChecked btree.zig:696）换了个契约： 调用方自带缓冲区，引擎直接往里拷，返回写入字节数。 缓冲区太小 → 返回 error.BufferTooSmall，且一个字节都不写（拦截在任何写入之前，btree.zig:749 附近）， 调用方换个更大的缓冲区重试即可。省掉的是中间那次临时分配 + 复制 —— 对高频小 value 的点查， 这就是热路径上最贵的那一刀。

打水：get 是「你伸手，我倒进一次性纸杯递给你」；getInto 是「你把自家水壶递过来，我直接灌」—— 壶太小我不动你的壶，先告诉你需要多大的壶。纸杯（临时分配）用完就扔，是纯浪费。
迭代器吐出的 key/value 也是借用：指向 mmap 页里的字节，不复制（Iterator 注释 btree.zig:2200 前后的借用契约）。 上层 db.zig 会在迭代器存活期间「钉住」相关页不被回收（MVCC pin，第 6 章的主角）； 引擎层只保证一条：迭代器还活着，页就还在。分层各管各的承诺。

7读时的 CRC 分档：off / sample / full

是什么：第 1 章讲过每页尾部有 4 字节 CRC32 校验和。但读的时候要不要每次都验？ cube_db 把这个选择做成了一个三档枚举 CrcCheck（src/btree.zig:64）， 由数据库启动选项决定，贯穿所有读路径：

档位行为代价 / 收益
.off完全不验，直接返回页数据最快。依据：COW 保证已发布的页从不被原地改写，页内容坏多来自介质损坏（低概率，交给离线体检工具兜底）
.sample抽查：页号 % 64 == 0 的页才验（SAMPLE_INTERVAL = 64，btree.zig:69；判定函数 sampleHit btree.zig:73）平均每 64 页验 1 页。介质刚开始坏时，迟早有抽查页命中，给出早期警报
.full每一页都验，坏了返回 error.CorruptCrc最安全。适合「宁可慢也要立刻发现数据损坏」的场景

三档汇合在唯一的咽喉 readNodePayloadPolicy（btree.zig:82）： get / getInto / Iterator / 溢出链的每一次页读取都必须经过它， 所以换档 = 改一个启动选项，读路径一行代码不用动。

为什么 .sample 是确定性抽查：sampleHit 只做 page_no % 64 == 0， 没有任何随机数。同一个页号永远得到同样的判定 —— 测试可复现、离线工具可以精确预言「哪些页会被抽到」。 随机抽查看起来更「均匀」，但不可复现的检查在存储系统里是灾难：你永远没法回答「上次那次报警到底是哪个页触发的」。

食品安全抽检的两种做法：每批次全检（full，成本最高）、按批次号尾号抽检（sample，规则公开可复核）、 完全信任冷链不检（off，赌供应链不出事）。尾号抽检的妙处是供应商事先知道规则 —— 可复核的抽查才叫监控，不可复核的抽查叫抽奖。
为什么读路径敢默认少验甚至不验？因为这套系统把校验放在了它最便宜的位置： 写路径每次落盘都算 CRC（writeNodePage，btree.zig:111 附近），页一旦发布就永不改写； 剩下的风险只有「磁盘介质自己慢慢坏」（bit rot），那是以月年计的慢过程 —— 交给 .sample 抽查给早期预警、 离线体检工具 cube_check 全量扫（第 8 章）兜底。在正确的地方花正确的钱， 这是性能与可靠性的经典权衡，也是第 8 章可靠性工程的开胃菜。

8本章自测

② 一个 3500 字节的 value，配一个 900 字节的 key，它能留在叶子里吗？ （提示：别只看 3500 < MAX_INLINE_VALUE=3800 —— 想想 inlineValueBudget 为什么叫「组合感知」。） 它如果进 overflow，叶子里留下的是什么？
③ get、getInto、Iterator 都从根下降到叶子，它们读页的「姿势」有什么共同点？ .off 档下读路径敢跳过 CRC 校验，靠的是哪条不变量？这条不变量是谁保证的（提示：第 0 章 COW）？
