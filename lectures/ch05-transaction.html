1API 形状：beginWriteTxn → put/delete → commit/abort

是什么：事务（transaction：一串操作要么全生效、要么全不算的打包单位） 的用法是标准三段式，跟 SQLite 的 BEGIN/COMMIT 一个形状：

var txn = try db.beginWriteTxn();     // ① 开事务（拿到「单写者」的锁）
try txn.put("alice", "100");
try txn.delete("bob");                // ② 攒改动（都在内存里，还没碰树）
try txn.commit();                     // ③ 一锤定音：全生效
// 或者 txn.abort() —— 全不算

这三个动作分布在两个文件里。beginWriteTxn 在 src/db.zig:562， 第一件事就是抓 write_mutex（单写者互斥锁：同一时刻只允许一个写事务在跑）；抓不到直接返回 error.LockFailed。WriteTxn 结构体本体在 src/db.zig:598， put/delete/commit/abort 四个方法分别位于 :605、:616、:629、:664。 读这边对称地有 beginReadTxn（src/db.zig:576）返回 ReadTxn—— 它不抓写锁，只登记一个 MVCC 快照（下一章的主角），所以读写互不阻塞。

方法位置干了什么锁
beginWriteTxndb.zig:562抓写锁 + 建暂存区占用 write_mutex 直到 commit/abort
txn.put / txn.deletedb.zig:605/616改动追加进内存暂存列表不加锁（写锁已在手）
txn.commitdb.zig:629批量应用 + 写 meta + fsync持有中，结束释放
txn.abortdb.zig:664丢弃暂存，什么都不应用释放
txn.deinitdb.zig:673兜底：忘叫 abort/commit 也会释放锁（防泄漏）
为什么整个引擎只允许一个写者？不是为了偷懒——是 B-tree 的 COW 写路径天然以「整棵树」为工作单位 （上一章讲的 applyBatch 一次重写一条路径）。两个写者同时改树，冲突合并的复杂度是灾难级的。 LMDB、SQLite（默认模式）都做了同样的取舍：写串行，读并发。读不受限的前提是 MVCC （多版本：写者改的是新副本，读者看的旧页原地不动），这正是第 2 节 staging 和第 4 节提交仪式能成立的地基。
写事务像银行的VIP 柜台：柜台只有一个（write_mutex），进去先取号独占； 你在柜台前填的单子（put/delete）只是攒在手上，柜员还没动账本； 最后说「办理」（commit），柜员才一次性把所有改动写进正式账本、盖章、归档。 中途你改主意了（abort），单子揉掉就走，账本一个字没变。

2staging：改动先进暂存区，key/value 立刻 dup 进 arena

是什么：txn.put 内部非常朴素——不碰树、不碰磁盘，只做两件事 （src/db.zig:605-614）：

pub fn put(self: *WriteTxn, key: []const u8, value: []const u8) !void {
    try checkKeySize(key);             // 超大 key 在这里就拒收，不用等到 commit
    if (self.finished) return error.TxnFinished;
    const alloc = self.staging_arena.allocator();
    const k = try alloc.dupe(u8, key);   // ← 立刻复制一份 key
    const v = try alloc.dupe(u8, value); // ← 立刻复制一份 value
    try self.staged.append(alloc, .{ .key = k, .value = v, .tombstone = false });
}

两个关键词都要解释。staging（暂存：改动先攒在内存列表里，不立刻生效）列表就是 staged 这个 ArrayList，攒的是 (key, value, tombstone) 三元组。 arena（内存竞技场：一种「只管分配、最后一把全释放」的分配器）是 staging_arena——每个事务开张时建一个（src/db.zig:570）， commit 或 abort 时 deinit() 一口气全释放，中间不逐个 free，也不用配对回收。

为什么要 dupe 复制？看 :608 那行注释：the caller's slice (e.g. a stack buffer) may not live until commit。调用方传来的 key/value 可能是栈上的临时缓冲区，事务可能要跑很久才 commit， 等到提交那一刻，那块栈内存早被别人用了。所以入口处立刻拷进 arena，把所有权收归事务。 为什么用 arena 而不是普通分配？一个事务可能攒上万条 put，普通分配器要逐条 malloc/free 上万次； arena 就是「先划一块地，随便圈，散场一起平」——提交路径里到处是同样的手法（下一节的 commit_arena、 applyBatchSwap 里的 COW arena，src/writer.zig:661）。
点奶茶用小票：店员不会你说一杯就立刻做一杯，而是先把「三分糖、去冰、加珍珠」抄在小票上。 抄的时候用的是店里自己的纸（arena 复制），不是你手机屏幕（调用方的内存）——你手机等会儿可能关屏（栈帧销毁）， 小票不能跟着消失。等到叫号（commit），才按小票一口气做。

3put 走批（micro-batch）：把多次 commit 拼成一班车

是什么：每次 commit 都有一笔固定开销——COW 重写路径 + 写 meta 页 + fsync。 如果程序连续 db.put 一万次，难道要付一万次这笔钱？micro-batch（微批：把多次小提交合并成一次大提交） 就是干这个的。开关在 src/writer.zig:164：

pub const MicroBatchConfig = struct {
    /// Max staged entries before auto-flush. 0 = disabled (direct commit).
    batch_threshold: usize = 0,     // 默认关：每次 put 直接走完整提交
};

打开后（batch_threshold > 0），db.put 走另一条路 （src/db.zig:147-163）：改动先 dup 进 pending 暂存列表， 攒够 batch_threshold 条就自动 flush()。flush 的活法很讲究 （src/db.zig:202-221）：在 staging_mutex 保护下原子地偷走整个 pending 列表 （换一个空列表回去），松锁，然后把偷来的整批交给 putBatch（:224）走一次完整提交。 另外还有绕过 micro-batch 的直通车 putDirect / deleteDirect （src/db.zig:179/187）——它们内部就是「开一个隐式 WriteTxn、put 一条、立刻 commit」。

入口行为适合
db.put（threshold=0，默认）经 putDirect：一条 = 一个事务 = 一次 fsync零散写入，要求每条立刻持久
db.put（threshold>0）先攒 pending，攒够自动 flush；也可手动 db.flush()连续导入、灌数据
db.putBatch一次性提交一批，完全绕开 staging调用方自己手里就有一批数据
db.beginWriteTxn显式事务：攒什么、何时提交全由你控制需要「全生效或全不算」语义
拼车：去机场的固定成本（车费 = COW + fsync）是绕不开的，但一辆车坐 4 个人就摊薄成 1/4。 batch_threshold 是「凑满 4 人发车」；db.flush() 是「不等了，现在就发」； putDirect 是「包车」——贵，但随叫随走。三种方式到达同一个机场（数据落盘），只差成本分摊。
注意一个容易误解的点：micro-batch 攒批期间，数据还没提交——进程这时候崩了， pending 列表（纯内存）就没了，这批 put 等于没发生过。所以 micro-batch 适合「可以重放的批量导入」 （fuzz 测试、灌数据脚本），不适合「每一笔都不能丢」的记账场景——后者请用默认的直接提交模式。 这是性能和持久性之间明码标价的旋钮，不是魔法。

4commit 全程走查：publishSnapshot → 树应用 → freelist 持久化 → 交替写 meta + fsync

是什么：txn.commit（src/db.zig:629）先做三件家务： 标记 finished、注册两个 defer（松锁 + 释放 staging arena——不管成败都会执行）、 空事务直接返回。然后把 staged 列表打包成 Request 数组，交给 applyBatchSwap（src/writer.zig:619）—— 这才是六步仪式的正戏。逐步对号：

几个图上看不见、但值得知道的细节：

  • 步骤②是智能的：单条改动直接走 btree.insert 快路；多条则先探测是否已按序 （O(n) 扫一遍），有序就免排序直接 insertBatch，乱序才「复制进 arena → 排序 → 相邻去重 （后写覆盖先写）」再批量插入（src/writer.zig:670-780 附近的三个分支）。
  • freelist 持久化不在这六步里显式出现：meta 里的 free_head/free_count 由 FilePageStore 的 vtWriteMeta 在写 meta 的瞬间自动塞进去（第 2 章提过：store 是唯一知道 这些值的层）。所以图④一格就涵盖了它。
  • power_fail 档的额外一步：写 meta 前先 syncDataPages 把数据页先刷盘 （见第 6 节），这是图④内部的一个可选前缀。
整场仪式里，「提交点」只有一处：publishSnapshot（src/writer.zig:879， 函数本体 :257）。它把新 root 和 sequence 用原子写（release 语义）发布出去——从这一纳秒起， 所有新读者看到的都是新树。在此之前进程崩了，磁盘上的 meta 还指着旧树，新写的那些页成了无人认领的孤儿 （无害，第 7 节讲）；在此之后崩了，meta 已指向新树，事务「已经在」盘上了。

5「原子」到底原子在哪：单页写 + 双 meta 乒乓 + sequence 判新旧

是什么：上一节的结论依赖一个物理事实——meta 页的切换是「原子的」。 它由三件事合力保证：

① meta 只有几百字节，写它基本是一瞬间

meta 页的有效内容远小于 4096 字节，磁盘写入这么一小段的窗口期极短。但「极短」不等于「零」—— 所以还需要②。

② 双 meta 乒乓：任何时刻都有一份完整的上一版

引擎准备了 meta0（页 1）和 meta1（页 2）两个席位（第 2 章第 4 节）。这次提交写 meta1，下次写 meta0， 　轮流覆盖。于是任何一版 meta 都有一个「上一版」安然躺在另一个席位上—— 写到一半断电毁掉的只是「即将成为最新版」的那份，上一版完好。

③ sequence 号：重启时怎么知道哪份更新

每份 meta 里都盖着一个单调递增的 sequence（序号：每次成功提交 +1 的计数器，谁的号大谁新）。 本次提交的序号 = 上次 + 1（new_sequence = cur_sequence + 1，src/writer.zig:821）。 重启恢复时两份都读出来，取 sequence 大的当真相（src/format.zig:285 的 readMetaPage 最后一行：m0.sequence >= m1.sequence ? m0 : m1； FilePageStore 开机恢复用同样规则，src/file_page_store.zig:229）。

两本轮流抄的账本：账本 A 记到第 41 笔，会计这次往账本 B 抄第 42 笔。 抄到一半钢笔没水了（断电）？没关系，A 还完整——对外宣布「第 42 笔作废」，从 A 继续。 抄完了？B 完整，且页脚的笔数（42）比 A 的 41 大——宣布 B 是账本。 会计永远不需要「回滚日志」这种东西，因为上一本永远是完整的。
为什么不用「在 meta 里写一个 in-progress 标志位」这种方案？因为标志位本身也占字节、也要写， 「写标志位」这个动作自己又可能被打断——问题原地踏步。乒乓双副本是唯一不需要任何额外假设的方案： 它把「写入原子性」这个不可能的承诺，换成了「两份副本至少一份完整」这个必然成立的承诺。 CPU 和 OS 层面还有一层：publishSnapshot 用原子变量（release/acquire 语义）发布，保证内存里的读者 也绝看不到「写了一半的 root」。

6持久性旋钮：Durability 两档 + Options{fsync} + Db.sync()

是什么：同样的提交仪式，刷盘的力度可以调。旋钮在 src/writer.zig:145 和 src/writer.zig:152：

pub const Durability = enum { process_crash, power_fail };  // writer.zig:145

pub const Options = struct {
    fsync: bool = true,                          // 提交时是否同步刷盘
    micro_batch: MicroBatchConfig = .{},          // 上一节的拼车开关
    durability: Durability = .process_crash,      // 崩溃模型档位
    crc_check: CrcCheck = .off,                   // 读路径 CRC 分档（第 3 章讲过）
};

两档 Durability（持久性档位：防到哪一级崩溃的保险等级）的区别，就是提交时多一次还是少一次 fsync：

档位提交流程防什么代价
process_crash（默认） 写 meta → 一次 fsync（writer.zig:300） 进程崩（kill -9、panic）——OS 页缓存还在，数据丢不了 最快；但机器断电时，已提交事务的数据页可能还没真正落盘
power_fail 先 syncDataPages（数据页落盘）→ 写 meta → 再 fsync（writer.zig:296-302） 整机断电——meta 落盘的那一刻，它指向的数据页必然已经在盘上了 每次提交两次 fsync，单条 put 延迟约翻倍

而 Options.fsync 是另一个独立旋钮：设成 false 进入「异步模式」—— commit 只写不刷，想什么时候稳，什么时候手动调 db.sync() （src/db.zig:550，内部就一行：store.sync()，即整个文件的 fsync）。 这个异步档只在 process_crash 档有意义（power_fail 的正确性依赖强制双刷，见 :143 注释）。

快递保价：process_crash = 普通快递（放驿站 = OS 页缓存），丢件风险只在「驿站着火」（断电）； power_fail = 送到手签收（数据页先 fsync），贵一倍但火烧不到；fsync=false + Db.sync() = 你自己决定 什么时候去驿站取件攒着的一堆包裹——攒得越久越快，着火全没。
选型口诀：怕进程死 → 默认档；怕拔电源 → power_fail；要极限吞吐且能接受最后几秒丢失 → fsync=false + 手动 sync()。三档都成立的前提是仪式本身没错——「meta 指到的数据页必须不新于 meta」 这条顺序约束，power_fail 用「先刷数据页」满足，默认档靠「页缓存不丢」满足。

7abort 与错误路径：提交前失败时那些 dirty 页去哪了

是什么：先分两种情况。

情况 A：commit 还没开始（abort 或 put 阶段报错）

txn.abort（src/db.zig:664）做的几乎是「什么都不做」： 标记 finished、释放 staging arena（暂存列表连同里面的 key/value 一起蒸发）、松锁。 树没被碰过、磁盘没被碰过——因为第 2 节的设计，改动在 commit 之前对树是零接触的， abort 天然干净。甚至你忘了调 abort，deinit（:673）也会兜底松锁防死锁。

情况 B：commit 跑到一半报错（比如磁盘满 MapFull）

这才是有意思的：步骤②往树上写的时候，新页已经写进去了（mmap 区域里已经有多余的页）。 提交失败，这些页岂不是脏了盘？答案藏在前几章的伏笔里：

  • meta 没切换 → 新页不可达。meta 还指着旧 root，从旧 root 出发遍历整棵树， 走不到任何本次新写的页。它们成了孤儿页（orphan：占着页号但从目录走不到的页）。
  • 孤儿无害：不会被读到（不可达），不会被复用（freelist 没登记它们——登记发生在 vtWriteMeta 的持久化链里，而那步没走到）。它们只是浪费空间，这就是注释里反复出现的 「leak direction is safe」（泄漏方向安全：出错宁可浪费空间，绝不误用数据）原则。
  • 谁报错谁兜底：applyBatchSwap 里任何一步失败，都会给这批请求的 future 塞进错误 （src/writer.zig:675 等处），txn.commit 原样抛给调用方； 序号不 +1、meta 不写、快照不发布——仪式中途退场等于仪式没开始。
舞台剧彩排：commit 开始 = 大幕拉开。布景组（COW 写页）已经把新布景搬上台了， 结果主演忘词（错误）导演喊停——大幕没关过，观众（读者）从头到尾只看过上一幕； 台上多出来的那套新布景（孤儿页）下次换幕时拆掉回收，不影响演出。 真正不能出错的只有换幕那一秒（meta 切换）——而那一秒短到几乎不可能失败。
把本章串成一句话：事务的原子性 = 「staging 隔离 + 单一提交点 + 双 meta 乒乓」三件套。 staging 保证 commit 前零接触；单一提交点保证崩溃只有回滚/生效两态；乒乓保证提交点本身崩不坏。 三者各管一段，缺一不可。

8本章自测

  1. 为什么 txn.put 必须把 key/value 立刻 dup 进 arena？如果直接存调用方的切片，会出什么事故？
    提示：第 2 节。想想调用方的内存（栈缓冲）和事务的生命周期哪个长。
  2. commit 执行到「批量应用进树」之后、「写 meta」之前，进程被 kill -9。重启后：这批改动生效了吗？ 那些已经写进 mmap 的新页会污染数据吗？
    提示：第 4、7 节。meta 指向谁？从旧 root 能走到新页吗？
  3. power_fail 档为什么必须「先刷数据页、再写 meta」？顺序反了会发生什么？
    提示：第 6 节。假设 meta 先落盘、数据页还在页缓存里，此时拔电源——重启后 meta 指向的页在盘上吗？
参考答案骨架：① 调用方切片可能活不过当前函数（栈帧销毁/缓冲复用），commit 在未来某个时刻才用它， 必须入口处复制收权；② 不生效——meta 仍指旧树，恢复走旧 root；新页不可达、不在 freelist，只是空间浪费， 完全无害；③ 顺序反了，重启后 meta（已落盘）指向的数据页可能还在页缓存里没落盘——根页号指向盘上的空洞， 「目录说有、货架是空的」，这就是必须先 syncDataPages 的原因。
