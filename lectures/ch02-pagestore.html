1Zig 没有 interface：手工 vtable 多态长什么样

是什么：你可能用过 Java 的 interface、Go 的 interface{}、C++ 的虚函数—— 它们都是「多态」：同一段调用代码，运行时可以接到不同实现上。Zig 语言故意不提供这个语法， 于是 cube_db 在 src/page_store.zig:17 手工搭了一个，行话叫 vtable（virtual table，函数表：一张「这个类型会哪些动作」的表格）。整个结构只有两个成员：

pub const PageStore = struct {          // ← src/page_store.zig:17
    ptr: *anyopaque,                    // 指向「真实现」的指针（anyopaque = 未知类型，void* 的 Zig 版）
    vtable: *const VTable,              // 指向函数表的指针（表在编译期就固定了）
    ...
};

函数表 VTable 在 src/page_store.zig:21，每一格就是一个函数指针。 以「分配一页」为例，表里的格子长这样：

pub const VTable = struct {             // ← src/page_store.zig:21
    allocPage: *const fn (ptr: *anyopaque) anyerror!u32,
    //  ↑ 一格 = 一个函数指针：输入一个实现指针，返回页号或错误
    ...
};

调用方的体验和用 interface 没区别。真正的多态发生在 src/page_store.zig:54 这层薄包装里：

pub fn allocPage(self: PageStore) !u32 {
    return self.vtable.allocPage(self.ptr);   // 查表 → 调到真实现的那份函数
}

翻译成人话：PageStore 本身不干任何活，它只是一对「转接头 + 遥控器」。 按下遥控器上的 allocPage 按钮，遥控器去查 vtable 这张「接线表」，把信号转给接在上面的那台真机器。

墙上的插座是国标定的：两个孔一个地线，形状永不改变。电饭锅、吹风机、台灯都是「插头」， 谁符合标准谁就能插上去。插座（PageStore）从不在乎插上来的是发热的（文件实现）还是发光的（内存实现）， 它只保证「插上了就有电」——在这里，「电」就是那 9 个函数。
Zig 是 2020 年代的新语言，它砍掉 interface 是坚持「显式优于隐式」：虚函数表、动态分发这些事一旦发生， 就应该像上面这样写在你眼前，而不是藏在编译器的魔法里。代价是每个类型要手写一份 vt* 函数 （src/page_store.zig:164-231，九个 vt 开头的小函数 + 一个静态的 mem_vtable 表）；好处是没有隐藏的运行时机制，你看到的两个指针就是多态的全部。
@ptrCast(@alignCast(ptr)) 是这套路数里唯一的「咒语」：把无所不知的 *anyopaque 变回具体类型（如 *MemPageStore），出现在每个 vt 函数的第一行 （如 src/page_store.zig:165）。看不懂没关系，记住它只干一件事：把 void* 变回真身。

2接口只切四刀：为什么这九个动作就够了

是什么：VTable 一共九格（src/page_store.zig:21-51），但核心只有「四刀」 ——对页的四种操作，外加 meta 页和刷盘相关动作：

VTable 槽位干什么人话
allocPage 要一个空页，返回页号 「给我一间空房，房号多少？」—— 优先复用回收站，没有就发新号
freePage 把一个页还回去（进 freelist（空闲页登记表：被删数据腾出来的页号清单）） 「这间房退了，下次可以再租」——只登记房号，不抹房间里的东西
readPage 读一页，返回 []const u8（只读切片） 「房号 7 的房间让我看一眼」—— 借给你看，不许改
writePage 写一页，返回 []u8（可写切片） 「房号 7 的房间钥匙给我」—— 拿到钥匙随便改
readMeta / writeMeta 读写meta 页（数据库总目录，上一章的主角） 单独两刀，因为 meta 走「双页交替写」的特殊安全协议
syncDataPages / sync 把数据页 / 全部刷到稳定存储 内存版里是空操作；文件版里是 fsync——「断电后东西还在」的最后一步
mapsize 告诉我总容量（最多多少页） 让上层知道「什么时候会满」

注意两个返回类型的差别，这是 Zig 借用（borrowing：把东西「借」给你用，所有权还在主人手里）惯例的活教材： readPage 返回的切片是「借」的——主人保证它一直有效，你也只许看不许改 （契约写在 src/page_store.zig:65 的注释里）；要自己的副本，请自己 dupe。 而 writePage 返回的切片可以直接写入，因为它本来就是拿来改的。

为什么不把接口做成「读写任意字节区间」或「append 一段日志」？因为上层的全部需求，恰好就是 「页号 ↔ 整页内容」这一个形状：B-tree 的每个节点 = 一页，COW 写 = 写新页，回收 = freePage， 提交 = 写 meta。接口多一刀，将来每换一个实现就多一刀要兑现；接口少一刀，上层就得自己绕。切在这四刀上， 是「上层需求」和「底层能力」的最小公共面。文件版实现里有大量复杂代码（freelist 链、崩溃恢复）， 但都藏在九格函数后面，从没泄漏到接口上——这就是接口厚的意义：复杂度被关在实现里，不传染。

3MemPageStore：纯内存实现，给谁用

是什么：src/page_store.zig:95 起的 MemPageStore， 是 PageStore 的「实验室版」：所有页就是一块块 4096 字节的堆内存，说「读页」就是读内存，说「刷盘」就是什么都不做 （vtSync 是空函数，src/page_store.zig:217）。看它的核心字段就明白了：

pub const MemPageStore = struct {                 // ← src/page_store.zig:95
    pages: std.ArrayList(*[f2.PAGE_SIZE]u8),      // 页号 → 页内存 的数组（存的是指针）
    freelist: std.ArrayList(u32),                 // 回收站：退回来的页号，LIFO
    next_free: u32,                               // 发号器：下一个全新页号
    meta0: [f2.PAGE_SIZE]u8, meta1: [f2.PAGE_SIZE]u8,  // 两份总目录，内存里现成的
    ...
};

它怎么兑现那四刀（代码都在 src/page_store.zig:164-231）：

  • allocPage（:164）：回收站里有货就弹一个（freelist.pop()，后进先出——刚退的房最容易再租）； 没货就发新号 next_free，同时 ensurePage（:144）现分配一块 4KB 内存。 发号器顶到 max_pages 就报 error.MapFull——「库满了」。
  • freePage（:176）：把页号塞回回收站。完事。不擦数据。
  • readPage / writePage（:183, :195）：页号 1、2 直接返回 meta0/meta1；普通页查数组返回那块内存。
  • writeMeta（:210）：这次写 meta0、下次写 meta1，轮流来——双页交替协议在内存版里也认真演练， 这样上层代码在内存里测到的行为，和文件版落盘的行为一致。
MemPageStore 是飞行模拟器：座舱（上层接口）和真飞机一模一样，仪表都会动，唯独不真的飞。 测试要的是「跟真的一样的座舱 + 随便坠机不心疼」——内存版让每个测试都能完整跑一遍分配、写树、提交、回收的全流程， 毫秒级完成，还不会在硬盘上留下一堆 .db 尸体文件。
一个容易忽略的细节：pages 数组里存的是指针，每一页是独立的一块堆内存（:98-103 的注释）。 为什么这么讲究？因为数组自己长大时会搬家（整块内存 realloc 到新地址），如果页数据直接放在数组里， 别人借出去的 readPage 切片就指向了旧地址——悬空、崩溃。存指针的话，数组搬家只是挪动一串门牌号， 页本身纹丝不动。这是第 1 节「借用契约」能在 MemPageStore 里兑现的物理前提。

4页号从 3 开始：NULL / meta0 / meta1 三个特殊席位

是什么：src/page_store.zig:8 有一行再简单不过、却贯穿整个引擎的常量：

/// First data page number (0=NULL, 1=meta0, 2=meta1)
pub const FIRST_DATA_PAGE: u32 = 3;      // ← src/page_store.zig:8

意思是：页号 0、1、2 是保留的特殊席位，第一个普通数据页从 3 号开始。 MemPageStore 的发号器出厂值就是它（.next_free = FIRST_DATA_PAGE，src/page_store.zig:120）， 文件版的 init 也用它算出「文件至少要有 3 页」（src/file_page_store.zig:183）。

页号席位为什么必须单独留座
0 NULL（src/format.zig:21） 「没有页」要有个能写进 4 字节的表示。指针字段的类型是 u32 页号，不是可空类型， 于是 0 号被征用为「此处无页」。B-tree 空树的根指针、页头里各种「没有下一页」都写 0。
1 / 2 meta0 / meta1（src/format.zig:22-23） 总目录要有两个席位才能「乒乓交替写」：这次写 1，下次写 2。任何时刻断电，至少一席是完整的上一版目录 ——这是全引擎崩溃安全的锚点（第 0 章第 7 节讲过）。
影院前三个座位永远用胶带封住不卖票：一号座坐着「空位」的牌子（NULL，标明「这里没人」本身也是信息）， 二、三号座是放映员的目录台（meta0/meta1）。检票系统（发号器）的票号永远从 4 号座（=页 3）开始发， 谁也别想把目录台当观众席卖出去。

5分层收益复盘：同一棵树，跑内存也跑文件

是什么：把前三节串起来看收益。B-tree、事务提交、MVCC 这些上层代码， 全都只握着 PageStore 这个插座。于是同一个引擎出现两个世界：

MemPageStore 插上FilePageStore 插上
数据在哪堆内存里的 4KB 小块mmap 映射的 DB 文件（1TB 预留地址空间）
断电后全没了（vtSync 空操作）fsync 保证已提交数据还在
速度纯内存，微秒级跑完一个事务真实磁盘语义
上层代码改了几行0 行。btree.zig / writer.zig / db.zig 完全不知道换了插头

动手小实验：打开 tests/txn_writer_db/overflow_test.zig（测试「超过一页的大 value」）， 头几行是这样的：

var ms = ps.MemPageStore.init(std.testing.allocator, 10000);  // 建一间内存实验室，限 10000 页
defer ms.deinit();                                           // 实验结束全部销毁
var db = try dbi.Db.open(std.testing.allocator, ms.store(), .{});  // 把内存插座插给完整数据库！
defer db.close();

try db.put("big", big);        // 之后照常 put/get —— 代码和生产路径一模一样

注意 ms.store()（src/page_store.zig:137）：它就是把 ptr 和 vtable 打包成插座形状的一行胶水。接下来整个数据库——B-tree、事务、overflow 页链—— 都跑在这个「假磁盘」上。这个测试文件里没有一行代码关心「页到底在内存还是在文件」。

这就是本章标题的全部含义：磁盘不是引擎的一部分，磁盘是插在引擎上的外设。 测试与 fuzz 之所以能像流水线一样铺开（tests/ 下几十个文件全用 MemPageStore），地基就是这一层接口。
复盘一下这一刀切在哪、为什么值钱。「算法」（树怎么组织数据）和「介质」（字节躺在哪）是两条独立演化的轴： 算法层以后可能加压缩、加并发结构；介质层以后可能换网络盘、换加密文件。接口把它们钉死在九个函数上， 两边各自狂奔互不牵连。这个模式不止数据库用——图形引擎把「渲染器」做成接口，音频库把「输出设备」做成接口， 都是同一招：把最难替换的东西，变成一个插头。

6本章自测

能用自己的话回答，才算真懂。答案都藏在前文里，想不起来就回头翻。

  1. Zig 没有 interface，那 PageStore 凭什么能「运行时换实现」？
    提示：只有两个成员。想想 ptr 和 vtable 各自管什么， 以及 src/page_store.zig:54 那层包装函数里发生了什么。
  2. 为什么 readPage 返回只读切片（[]const u8）、而 writePage 返回可写切片（[]u8）？ 借用契约要求实现方（MemPageStore / FilePageStore）额外保证什么物理前提？
    提示：第 3 节讲过「数组里存指针」的原因。
  3. 如果不留 FIRST_DATA_PAGE=3 这三个特殊席位，而让数据页从 0 号开始用，会出什么乱子？
    提示：分别考虑「0 号被当作普通页分配出去」和「总目录只有一页可写」两种情况， 后者会杀死整个崩溃安全设计。
三个问题的参考答案骨架：① 一个指针找实现、一个指针找函数表，包装函数查表转发，多态就是两个指针； ② 类型本身就是契约——只读切片保护读方不改数据，实现方必须保证页数据地址永不搬家（独立堆分配 / 固定 mmap）； ③ 0 号若可分配，「空指针」语义就没了；meta 只有一页则乒乓交替写不存在，断电可能落在「目录写了一半」的瞬间。
