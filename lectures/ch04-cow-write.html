1复习 COW：一次插入产生一串新副本页

COW（Copy-On-Write，写时复制，改数据时先复制一份新副本再改，绝不覆盖原件） 在第 0 章我们打过比方：改论文不在原稿上涂改，而是誊一份新的。本章把这比方落到页的粒度上—— 一次插入，究竟誊了哪几页？

答案：从被修改的叶子页一路到根，路径上的每一页都复制一份，旧页一页不碰。

修改图书馆里的一本书：你只复印被改的那一页（叶子页）、 以及目录卡片柜里指向这本书的几张索引卡（分支页和根页）—— 因为卡片上写着页号，新页换了页号，卡片也得重做。 书架上其他人正在读的旧书、旧卡片原封不动（这就是 MVCC 读快照的前提）。

为什么这么折腾？两个回报：

  • 崩溃安全：提交前任何时刻断电，旧树完好无损——新页从目录上走不到，等于没写（第 5 章的 meta 乒乓负责「官宣」）。
  • 读不加锁：读者永远拿着自己快照的根页号在旧页上行走，和写者井水不犯河水。
COW 的代价是「多写几页」，收益是「旧版本永远完好」。本章剩下的内容都在算这本账： 什么时候必须复制（4.2）、页装不下了怎么分裂（4.3）、太大的 value 往哪塞（4.4）、 怎么让一万条修改只付一次复制的钱（4.5）、删除为什么不删（4.6）、最后总账是多少（4.7）。

2单条 insert 的路径复制

是什么：入口是 insert()（src/btree.zig:1497）。 它先把超大 key 挡在门外（key.len > MAX_KEY_SIZE 直接报 error.KeyTooLarge，src/btree.zig:1508）， 空树则直接造第一个叶子页（src/btree.zig:1509）。否则递归下行：

dirty 列表：被替换下来的旧页去哪了

dirty 页（脏页，COW 之后被「淘汰出局」的旧页——它们还装着合法的旧版本数据，只是不再被新树引用） 不是垃圾，是待回收资产。insert 全程把它们的页号 append 进一个列表 （叶子在 src/btree.zig:1079，分支在 src/btree.zig:1340）， 随 WriteResult{new_root, live_delta, count_delta} 一起交回上层。 提交编排者 writer.zig 接手后，给每个旧页打上「本次提交序号」放进 pending_free 队列（src/writer.zig:797-815）—— 等所有还在读旧快照的读者退场，才放回 freelist 复用（第 6 章专讲这个水位线）。

为什么叶子修改前先整页 @memcpy 到栈缓冲（src/btree.zig:924-926）？ 因为后面 allocPage 可能触发底层存储的扩容/重排，之前借来的页指针会失效。 先抄一份到自己的栈上，就谁也动不了它——这是贯穿整个写侧的防御习惯 （src/btree.zig:41-49 的注释原话：copy the whole page to a stack buffer before modifying）。

3页满了怎么办：分裂

是什么：一页容量有硬顶——叶子最多 32 条记录 （LEAF_MAX_ENTRIES，src/btree.zig:12）， 分支最多 64 个孩子（src/btree.zig:14）， 而且不管条数多少，正文不能超过 4068 字节（NODE_PAYLOAD_CAP，src/btree.zig:370）。 装不下就分裂（split，把一个装满的页拆成几个新页，并在父页里补上分隔 key）。

插入时的两级检查（insertIntoLeaf，src/btree.zig:913）：

  • 条数检查：新条数 > 32 → 走分裂路径（src/btree.zig:1082）；
  • 字节数检查：就算 ≤32 条，拼完超过 4068 字节也要分裂（src/btree.zig:1089-1103， 31 条小记录加一条大记录就能踩中这个坑）。

分裂本体在 insertIntoLeafSplit（src/btree.zig:1189）： 把旧叶解码进内存、应用本次插入，然后按 leafChunkLen 按字节预算切块——每块 ≤32 条且 ≤4068B（src/btree.zig:1247-1269）， 每块写成一个新叶子页，块与块之间的分隔 key 取「下一块第一条记录的 key」。

分裂是向上传染的：叶子切出的新页组（代码里叫 splice，一组「新页号 + 分隔 key」的包裹，交给上一层去整合）交给父分支整合； 父分支也装不下（条数 > 64 或字节超预算，检查在 src/btree.zig:1413）就把自己重建成 几个满装分支页再向上交；只有根溢出时，buildBranchLevels （src/btree.zig:1707）把整组重建成层层分支、加一个新根—— 树高只在这里长（src/btree.zig:1535-1538 注释原话：Height grows HERE and only here）。

课本上的 B-tree 分裂是「对半分」，还规定兄弟至少半满（LEAF_MIN_ENTRIES=16、 BRANCH_MIN_CHILDREN=32 这两个常量就定义在 src/btree.zig:13 和 15）。 但 cube_db 的分裂是「装箱式」：尽量装满一块再开下一块，而且 全代码没有合并（merge）逻辑——删除不缩页，所以永远不会出现「太空」的页， 半满规则自然用不上。这是「删除走逻辑墓碑」（4.6 节）换来的整个简化：没有下溢，就没有回溯再平衡。
高速公路满员的巴士不搞「对半拆客」，而是装满一辆发一辆：32 个座位坐满就关门发车（写成一页）， 下一辆重新装。因为没人下车摘座位（删除不物理腾位），永远不会有「只剩一半人还占着整车」的浪费。

4大 key / 大 value 的特殊账

是什么：一页 4068 字节正文，一条记录想住进去，得先过两道尺寸闸门。

闸门一：key 的硬上限 MAX_KEY_SIZE = 4051 字节

推导写在 src/btree.zig:154-173：一页最多也要装得下一条记录——

成分字节说明
正文容量40684096 − 页头 24 − 页尾 CRC 4（第 1 章）
叶子头3kind 1 + 条数 2
每条固定开销14tombstone 1 + klen 4 + vlen 4 + flags 1 + overflow 页号 4
key 剩余空间40514068 − 3 − 14。MAX_KEY_SIZE（src/btree.zig:173）

为什么 key 是「硬」的而 value 不是？因为 value 装不下可以搬去 overflow 页（下面讲）， 叶子里只留 4 字节页号；key 没有地方可搬——它必须留在叶子里供比较。这就是 key 上限比 value 严格的原因。

闸门二：value 的复合预算 inlineValueBudget

value 想内联（直接塞在叶子里）要满足 value.len ≤ inlineValueBudget(key.len) = min(3800, 4068 − 3 − 10 − key.len) （src/btree.zig:148-152）。两个条件任一不满足就溢出：

  • MAX_INLINE_VALUE = 3800（src/btree.zig:134）：给同页其他条目留地方，不让一个胖 value 独占整页；
  • 复合上限：key + value 合计必须装进一页——key 很大时，哪怕 value 只有几百字节也得溢出。

overflow 链：装不下的 value 挂「外仓」

writeOverflowPages（src/btree.zig:183）把 value 按 每页 4068 字节切块，写成 OVERFLOW 类型（第 1 章的类型 4）的页链， 链接用页头的 free_next 字段（注释自嘲 MVP 没用 nkeys 记长度，链就靠 free_next，src/btree.zig:182）。 叶子里只存 flags=1 + 链头页号（src/btree.zig:1142-1148）。 判断走不走外仓就一行：needsOverflow（src/btree.zig:264-266）。

保险柜（叶子页）格子小，大件行李（大 value）不放柜里，贴一张「寄存单」（4 字节链头页号）， 行李本身送去仓库（overflow 页），仓库一格装不下就寄存在相邻格子里并留「下一格」字条（free_next）。 取的时候按单子一格一格走。

条目被覆盖或删除时，它的旧 overflow 链整条回收进 dirty 列表 （freeOverflowPages，src/btree.zig:252-261）—— 外仓的格子跟着主格子一起进回收流程。

有个顺序细节值得记住：overflow 链的回收必须在确认走快路径之后才做 （src/btree.zig:1107-1112 注释）——若最终走了分裂路径，链已由另一处回收， 提前回收会把同一个页号塞进 dirty 两次 → 一页被分配两份 → 数据串页。回收要「谁最后负责谁动手」。

5insertBatch：一万条 put 为什么比一万次 insert 便宜得多

是什么：insertBatch（src/btree.zig:1569）把一批 已按 key 排序的条目在一趟树遍历里全部插入。 它的文档注释就是本节结论（src/btree.zig:1565-1567）： 同一叶子范围内的条目只复制页面一次，避免逐条 COW。

省的钱来自三层：

层一次 insert（×10000）一次 insertBatch（×1）
页复制每条都复制「叶子+沿途分支」同一个叶子页里的 N 条只付一次复制钱
内存分配每条约 145 次 alloc/free整个批次用一个 arena（内存竞技场，一块大内存上像切豆腐一样顺序划分、最后整体释放）一次性分配（src/writer.zig:658-662）
提交开销每条一次 meta 写 + fsync一批一次（第 5 章）

调用方 writer.zig 还做了排序 smart path：收到的请求如果已按 key 有序（O(n) 检测， src/writer.zig:712-734），直接引用调用方内存、相邻重复 key 就地去重（后写赢）； 无序则拷进一块连续缓冲、排序、去重（src/writer.zig:715-780）。 排序是前提——只有排好序，「同一叶子的条目挨在一起」才成立，一趟遍历才走得通。

快递员送 100 个包裹到同一栋楼：挨家挨户跑 100 趟（逐条 insert），还是按楼层排好序一次上楼、 一层一次把该层的都放下（insertBatch）？楼梯（树路径）只爬一次，每层的门（叶子页）只敲一次。
为什么不在用户侧自动永远开批量？MicroBatchConfig.batch_threshold 默认 0 = 关闭 （src/writer.zig:164-169，Options 在 src/writer.zig:152）。 批量意味着「攒一攒再提交」，牺牲单条提交的即时持久性换吞吐——这是用户的安全/速度旋钮（第 5 章展开）， 不该替用户拧。单条快路径也保留着：批里只有一条时直接走 btree.insert 免去排序开销 （src/writer.zig:673-681）。

6删除的真面目：tombstone 与区间墓碑

是什么：删除一个 key，磁盘上什么都没消失—— 只是写了一条「这个 key 已删」的记录。tombstone（墓碑，一个 value 为空、 打了 tombstone=1 标记的叶子条目，表示「这个 key 作废」）。

单删的旅程：WriteTxn.delete 只是把一条 tombstone=true 的条目 存进暂存区（src/db.zig:616-622）；提交时它变成一条普通请求， 走 btree.insert(..., tombstone=true, ...)（单条快路径 src/writer.zig:673-681）。 在叶子里，它的写法和普通条目一样，只是 tombstone 字节置 1、value 长度记 0 （src/btree.zig:1133-1139）——旧条目在新副本里被墓碑顶替， 旧的 overflow 链回收进 dirty。读路径（第 3 章）撞见墓碑就当 key 不存在； 计数也配合：活→墓碑 count_delta = -1（src/btree.zig:1064-1070）。

为什么不物理删除？两个理由： ① 正在读旧快照的读者还需要旧条目在那儿（COW/MVCC 的前提——旧页不许动）； ② 物理删除会引起「页变空 → 下溢 → 合并再平衡」整套复杂机器。墓碑方案下树只会分裂不会萎缩， 4.3 节「没有合并逻辑」正是从这里换来的。

细节三则：端点太大连一条墓碑都装不下时，退回「每 256 条一批的逐条墓碑」兜底 （deleteRangeMaterialized，src/db.zig:360）； 链头指针 tomb_head 和树根打包成一个 64 位原子量一起发布 （publishSnapshot，src/writer.zig:257-260）， 读者一次加载拿到配套的（根，链头）——不会出现「新树配旧墓碑」的撕裂； 第一次写墓碑后，meta 版本永久升到 3（sticky，src/writer.zig:879-880）。

墓碑链像一块盖在地图上的毛玻璃：地图（树）没重画，只是在「某街区已拆除」的范围上盖了玻璃。 游客（扫描查询）走到玻璃下就什么都看不到；换新玻璃（swap）只改「玻璃挂哪」这一个挂钩（tomb_head）， 旧玻璃留给还在看它的游客（旧快照读者）。

7写放大账本

写放大（write amplification，实际写进磁盘的字节数 ÷ 用户要写的逻辑数据量） 是存储引擎的头号成本指标。cube_db 一次单条提交碰几页？按树高算：

  • 1 个新叶子页（被改的那页）；
  • 沿途每个分支一页新副本（cowBranchNoSplit，一页只补 4 字节）；
  • 偶发：分裂的额外页；
  • 1 个 meta 页 + freelist 维护（第 5/7 章）。

百万级 key 约 3 层高，即一次单条提交写 3~5 页 ≈ 12~20KB——对小记录这账不好看； 但配合批量（4.5 节），同叶条目共享复制，长期平均就贴着数据本身的大小走。 更关键的是没有任何隐性的重复写：

引擎类型写路径写放大来源
LSM-tree（LevelDB/RocksDB 一族）先写日志，再写 memtable，后台一层层压实（compaction，把多层有序文件反复归并重写）同一条数据被压缩过程重写多层，典型 10~30×
原地更新 B-tree + WAL数据页原地改，先写预写日志（WAL）每条数据写两遍：日志一遍 + 页一遍
cube_db（COW + freelist）COW 写新页，旧页经 freelist 原地复用，无日志、无压实只有「改路径上的页」本身；批量摊薄后 ≈ 数据量级。旧页回收复用，文件不无限膨胀

第 0 章引用过 README 的说法：「写放大约 1×、永不整体重写（compact 是 O(1)）」。 现在你能解释它了：COW 天然是「只写增量」；freelist 让旧页原地翻新（不追加新空间）； 崩溃安全靠双 meta 乒乓而不是日志——三件事互相成全，才把账压到这么低。

天下没有免费的午餐，cube_db 把写放大的省，换成了空间放大： 已删的条目（墓碑顶替前的旧值）、旧版本页都还在文件里躺着，直到读者水位线放行（第 6 章）、 页被 freelist 复用才真正「翻篇」。顺序是：先用空间换写少，再用 MVCC 期限把空间收回。
本章链条串起来：COW 复制路径（4.2）→ 装满就装箱分裂（4.3）→ 装不下的 value 寄外仓（4.4）→ 批量共享复制（4.5）→ 删除只贴墓碑不拆房（4.6）→ 于是写路径永远「只写增量、原地翻新」（4.7）。 第 5 章看这些新页如何在 commit 的一瞬间「官宣生效」。
