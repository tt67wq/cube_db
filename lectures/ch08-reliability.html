1校验和的性能账：ARM64 硬件指令 vs 软件查表

是什么：CRC（Cyclic Redundancy Check，循环冗余校验：给一段数据算出一个 「指纹」整数，数据变一个比特指纹就大变）是每一页末尾那 4 字节的来历（第 1 章讲过页布局）。 算指纹有两种算式，选哪种在 src/crc32_hw.zig:26-29 一目了然：

pub fn crc32Hw(init: u32, data: []const u8) u32 {
    return switch (builtin.cpu.arch) {
        .aarch64, .aarch64_be => crc32HwArm64(init, data),  // ARM64：CPU 指令直接算
        else => crc32Sw(init, data),                        // 其他平台（含 x86）：软件查表
    };
}

ARM64 路径用的是 ARMv8 的 CRC 专属 CPU 指令（crc32x/w/h/b， src/crc32_hw.zig:91-130 的内联汇编包装），一次吃进 8 字节；软件路径 crc32Sw（:13）用查表法——预生成一张 256 格的表，逐字节迭代。两者的产出 逐位一致，因为用的是同一条生成多项式（IEEE 802.3，0xEDB88320，文件头注释 :6-8 写明）。

最有意思的是反直觉的那一刀：x86 明明有硬件 CRC 指令（SSE4.2 的 crc32），为什么反而退回软件？ 因为 x86 那条指令算的是另一个多项式（CRC-32C / Castagnoli），和 IEEE 802.3 不是同一种指纹—— 同一页数据，硬件算出来和软件算出来是两个不同的数。页尾只存一个指纹，全引擎必须用同一种算法： ARM64 上写入用硬件算、校验用硬件验，x86 上写入用软件算、校验用软件验，永远一致； 但绝不能「x86 写入、ARM 校验」混着用两种算法。src/format.zig:116-122 的 computePageChecksum 做同样的架构分派，CRC32_HW 这 129 行（外加 format.zig 里的开关） 就是整个一致性的守门人。
CRC 像快递面单上的条形码：包裹（数据页）中途被雨泡了、被压瘪了（磁盘 bit rot、写一半断电）， 收件方扫一下码对不上，就知道「这件货坏了」，绝不会把坏货当好货收下。而多项式就像条形码的编码规范—— 两大快递公司（ARM 和 x86 的硬件指令）用了两套不兼容的编码规范，规范不同，同一件货打出的码就不同。 cube_db 选择：在 ARM 地盘全程用 ARM 规范，在其他地盘全程用手写规范，但一个仓库里绝不混用两套。
为什么值得为一页 4KB 的校验费这么大劲？因为校验发生的频率极高：写入时每页都要算一次，读路径开启 full 档时每页都要验一次。软件查表约是硬件指令的几倍到十几倍慢——在「每一纳秒都要跟磁盘抢」 的存储引擎里，这个差价直接写进 README 的基准成绩单。

2三道防线：谁在什么时候验哪页

是什么：单靠 CRC 本身不构成可靠性，构成可靠性的是「谁在什么时候验它」的三层设计。 cube_db 的答案是一道纵深防御：

为什么读路径默认 off（不验）也敢卖？分工不同：写路径已经全量贴了封条， 而本引擎没有「原地修改」——读者读到的每一页都是当初 COW 写入时验算过的；在线读验 CRC 防的只是 「写入之后、读取之前」这段窗口里磁盘介质慢慢变坏（bit rot）。这种损坏以月年为单位积累，由第三道防线的 离线 scrub 负责兜底即可。在意的话，把 Options.crc_check 拧到 sample （每 64 页确定性抽 1 页，src/btree.zig:68）或 full， 就把在线防线也补上了——性能与安全明码标价，用户自己选。
进口食品的三重检查：出厂时每件贴防伪封条（写入算 CRC，出厂必做）； 电商发货时按批次抽检（sample，64 件抽一件）；货架上的货每季度全量盘点（cube_check scrub）。 三道检查的成本和彻底程度递增，但坏货无论在哪道被抓住，结局都一样：下架报损，绝不卖给你。

3cube_check：离线体检工具与退出码契约

是什么：src/cube_check.zig 是一个独立的可执行文件，全文 159 行， 是本章最推荐通读的代码。用法一行：cube_check scrub <db-path>。 它把第二道防线缺的那块「彻底但慢」补齐：逐页验 CRC，一个不漏。核心函数 scrub（src/cube_check.zig:61）的骨架：

pub fn scrub(alloc, store, writer) !ScrubReport {
    const meta = (try store.readMeta()) orelse return error.NoMeta;  // 没有合法 meta = 没法体检
    var page_no: u64 = cube.page_store.FIRST_DATA_PAGE;    // 从 3 号页开始（0/1/2 是特殊席位）
    while (page_no <= meta.last_page) : (page_no += 1) {
        const page = try store.readPage(no);
        if (cube.format.verifyPageChecksum(arr)) { passed += 1; continue; }
        // 坏页：记下页号 + 尽力从页头恢复类型，打印一行诊断
        try failed.append(alloc, .{ .page_no = no, .page_type = hdr.page_type });
    }
    ...  // 打印 total / passed / failed 汇总 + 坏页清单
}

产出是一个 ScrubReport（:31，total / passed / failed 三项 + 坏页列表）。 但这个工具真正的精华在退出码契约（:20-22）：

退出码含义谁在消费
0 EXIT_OK所有页 CRC 全过运维脚本：继续跑
1 EXIT_USAGE用法错误：参数不对、文件打不开（含 flock 冲突）、没有合法 meta运维脚本：是我的命令错了，改命令
2 EXIT_CORRUPT发现损坏：至少一页 CRC 不合格运维脚本：报警——数据有恙，人工介入
为什么这么较真退出码？因为体检工具注定被放进 cron 定时任务和 CI 流水线里， 而脚本不看 stdout，只看退出码。「0/1/2 三分法」把「我的调用方式错了」和「你的数据坏了」 这两种截然不同的失败分开——前者重试没有意义，后者重试更没有意义。main 函数（:125 起）的全部工作 就是解析参数和把结果映射成这三个码，判定逻辑全在可单测的 scrub 库函数里 （tests/cube_check_test.zig 直接测它）——这是「逻辑与外壳分离」的标准做法。 另外注意 ：15 的约束：scrub 要求独占——FilePageStore 打开时就要 flock，writer 开着就检不了， 这是有意为之（检个「正在被改的文件」结果毫无意义）。
cube_check 能发现第二道防线漏掉的损坏吗？能——而且这正是它的存在意义：线上读路径默认不验 CRC （第二道防线 off 档），一页慢慢烂掉可能几个月没人发现；scrub 是唯一「逐页、离线、不赶时间」的 全量检查。它抓的是 bit rot，抓不了逻辑 bug——那是下一节 fuzz 的辖区。

4模型检验式 fuzz：随机操作序列 vs 参照物对账

是什么：fuzz（模糊测试：机器自动生成大量随机/畸形输入喂给程序，看它崩不崩） 有个高阶玩法叫模型检验（model checking：除了程序本身，再维护一个极简的「参照物」， 每一步都比对两者是否一致）。cube_db 的 API fuzz 就是教科书式实现 （tests/fuzz/api_fuzz_test.zig，手册见 docs/fuzz-testing.md）：

  • 把随机字节流解码成操作序列：put / get / delete（OpType 定义 :12，每条 op 由 1 字节操作码 + 4 字节 key 长度 + key + 可选 value 组成）；
  • 每条操作同时打到两个地方：真正的 cube_db（MemPageStore 跑完整 COW 路径）和一个 std.StringHashMap 参照模型——几十行代码、绝不可能有 B-tree 那种 bug 的老实字典；
  • 每一步 get 都对账：db.get 的结果必须和 HashMap 的结果一模一样 ——db 说有模型说没有（或反之）、值不相等，立刻 error.ModelMismatch（:59-60）报 bug。
像给天才钢琴家配一位只识谱的陪练：钢琴家（cube_db）技巧华丽但可能有手误； 陪练（HashMap）只会最笨的办法——一个音一个音照着谱子念。每弹一小节就停下来核对： 钢琴家弹的必须和谱子逐音一致。陪练永远弹不了音乐会，但没有他，你没法证明钢琴家没弹错。
为什么不直接写几万个断言用例？因为人想不到的 bug 排列，机器想得到。put 两个相同的 key 再删一个、 key 恰好跨页边界、操作序列恰好触发某条 COW 路径重写——组合爆炸人力枚举不完。随机生成 + 参照物对账， 把「证明引擎语义正确」变成「两个独立实现给出相同答案」的机械比对。docs/fuzz-testing.md 还规定发现 bug 后 的三步仪式：crash 输入存进 tests/fuzz/corpus/（replayCorpus 每次跑 CI 都会重放）、 补确定性回归单测、修到全绿——随机性负责「发现」，corpus 负责「永不复发」。

5崩溃测试闭环：每个提交点都「拉电闸」

是什么：上一章埋的伏笔在这里收线。第 7 章看到 commit 路径里埋着七个 fireCrashHook 站点（src/file_page_store.zig:137 的 CrashTag 枚举：before_chain / mid_chain / after_chain_before_meta / after_meta + 三个 tomb_chain 变体；全局开关 test_crash_hook 在 :150，生产恒为 null）。 本章看它怎么被用成一台「断电发生器」。以 tests/crash_insertbatch_pb/freelist_persist_crash_test.zig 为例，闭环是：

// fork 出一个子进程，把电闸拉到指定提交点（:206 childCrashAt）
armCrashHook(&fps, "mid_chain");      // ← 武装注入点（:66）
putRange(db, 150, 250);               // C3 提交走到 mid_chain 瞬间 → std.process.abort()
                                      //   子进程原地暴毙 = 精确模拟「提交到一半断电」
// 父进程重新打开文件，验收四条铁律（:228 checkAfterCrash）：
try expectRangePresent(db, 0, 30);    // ① 断电前的提交全在（durable prefix）
const c3 = try allOrNone(db, 150, 250); // ③ 武装的这批：要么全在要么全没（原子性）
if (c4 and !c3) return error.CausalityViolation; // ② 后提交的不能先落地（因果）
try part.expectDisjoint(&rep);        // ④ freelist 恢复后不重不漏，绝无双重分配

七个 CrashTag × 逐个武装 = 把提交仪式的每一个可能断电的瞬间都变成一个测试用例。 配角还有更狠的 tests/crash_insertbatch_pb/crash_harness_test.zig： 真 fork 子进程、真提交、真 _exit（连析构都不跑，等价拔电源），父进程重开对账。

电梯的坠落测试：工程师不会等真事故——他们把电梯装满配重，在井道里逐层剪断缆绳做实验。 CrashTag 就是「剪缆绳的位置菜单」：剪在第 3 根会怎样？第 5 根呢？每一处剪断后（子进程 abort）， 检查员（父进程）重新走进电梯（重开 DB），核对四条验收铁律。真电梯里的乘客从不知道这些实验， 他们只享受结论：「任何一层断缆，电梯不会自由落体」。
三章知识在这里扣成闭环：fuzz 负责「语义对不对」（第 5 章的事务语义 vs HashMap 裁判）， crash hook 负责「崩溃后对不对」（第 4~6 章的 COW/双 meta/水位线设计在任意断电点自证）， cube_check 负责「盘上数据烂没烂」（第 1 章的页格式 + CRC）。三者共享同一个验收标准： 退出码或断言里没有「大概没事」，只有全绿或红。

6收尾：纲要第 9 节的三道题，现在能展开多少

第 0 章末尾留过三道检验题。读完全书，试着把每道题从「背答案」升级成「讲机制」：

纲要的题当时的一句话答案现在你该讲出的机制链
为什么 commit 只需「换 meta 页」就原子？ 乒乓双 meta 第 5 章六步仪式 → 单一提交点 publishSnapshot → 第 8 章 7 个 CrashTag 逐点验证 → format.zig 用 sequence 判新旧，恢复 O(1)
为什么旧页「进了 freelist」还不代表「可覆写」？ reader 水位线 第 6 章 MVCC 快照 → pending_free 带 release_seq → 水位线（最老 reader 的 seq）推进才真正回收 → 第 8 章崩溃测试证明恢复后 freelist 绝不双重分配
为什么读方完全不需要锁？ COW 快照 + mmap 第 3 章 readPage 借用契约 → 页地址永不搬家 → 第 2 章 MemPageStore 每页独立堆分配 / FilePageStore 固定 mmap → 第 8 章读路径 CRC 分档，坏页报错不传染
全书一句话串联：页格式（第 1 章）定空间语言 → PageStore（第 2 章）切出可替换的磁盘插头 → B-tree（第 3 章）在页上组织数据 → COW（第 4 章）让修改不破坏旧版 → 事务提交（第 5 章）把批量修改 压进单一提交点 → MVCC（第 6 章）决定旧版何时安息 → crash hook（第 7 章）把「断电」变成可枚举的测试输入 → 本章用 CRC、对账和体检，把「任何时刻断电都不坏」从口号变成可以机械验证的命题。 可靠性不是某个模块，是每个模块各让一步、合起来才成立的一条链。

  2. 读路径默认 off（不验 CRC）为什么不算裸奔？cube_check 补的是哪个时间窗里的风险？

  3. 崩溃测试里，武装 commit 的那批数据在断电后为什么必须「全在或全没」，而不是「写进去一半」？ 是哪三个机制合力保证了这一点？
    提示：第 5 节 + 第 5 章。staging、单一提交点、双 meta 乒乓 ——分别负责「断电前」「断电瞬间」「恢复时」的哪一段？
参考答案骨架：① SSE4.2 是 Castagnoli 多项式，与页尾存的 IEEE 指纹对不上，混用即误报/漏报—— 同一算法家族必须贯穿读写全链路；② 写路径已每页贴 CRC、无原地修改，在线风险只剩 bit rot（月年级慢变量）， 离线全量 scrub 兜底足够；③ 断电前 staging 保证改动隔离在内存、断电瞬间 meta 未切换则新页不可达 （回滚）、已切换则全部生效，恢复时 sequence 判新旧只会选出一棵完整的树——「一半」这个状态在磁盘上 根本没有对应的 meta 表达。
