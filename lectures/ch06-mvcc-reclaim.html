1问题引入：一个足以毁掉数据的时序

是什么问题：前几章建立了两件事 —— COW 写路径会不断产生「被替换下来的旧页」， 这些旧页要进 freelist（空闲页登记表）等下次复用；同时读事务拿着旧快照在树上随便走，完全不加锁。 这两件事单独看都对，合起来有一个致命的缝隙：freelist 复用一个「还有读者正在看」的页会怎样？

构造一个具体时序（这就是 6.1 要你先看见事故，再来看保险丝）：

酒店退房：你（写者）退了 302 房（旧页进 freelist），前台立刻把它挂到「可入住」名单； 另一位客人（读者）手里还攥着 302 的旧房卡，慢悠悠走到门口 —— 房里已经住进了新人，行李（数据）全换了。 保险丝的做法：退房先进「待清扫」状态，登记上「还有谁拿着这间房的旧房卡」， 最后一反应卡作废了，才挂回「可入住」。本章讲的就是这套登记簿。
术语速查（后文反复出现）：快照（snapshot）= 读事务开始那一刻的数据版本，像给整棵树拍了张照； sequence = 提交号，每 commit 一次加 1，是「版本」的数字坐标； MVCC（多版本并发控制）= 靠「保留旧版本」让读写互不阻塞的总策略 —— COW 是它的地基（第 0 章概念④）。

2Reader 句柄：beginRead / endRead 的形状

是什么：读者的注册制度只有两个函数（src/writer.zig:400 与 writer.zig:446）：

API签名做什么
beginRead () *Reader 登记一个读者，返回一个显式句柄 *Reader；句柄里存着本读者的快照 sequence（writer.zig:424-429：当前 sequence 原子读进来，挂进活跃读者链表）
endRead (reader: *Reader) void 拿着当初返回的那个句柄来注销：从活跃链表摘下（writer.zig:453-458）、句柄回池复用；如果积压的待回收页还没清，顺手触发一次 reclaimPendingFree（writer.zig:465-467）

一段值得读的演化史（T-30 → T-32）

这个 API 不是一开始就长这样的。旧版 endRead() 不带任何参数 —— 它不知道注销的是「哪一个」读者，只能猜。源码注释（writer.zig:10-14）留下了当年为「猜身份」堆出的全套机关： thread-local 栈（每个线程自己记 beginRead 的顺序）、固定 64 槽数组、页号最高位当「占用标记」的编码、 溢出时退化成计数器兜底……四套机制互相打补丁，只为回答一个问题：「我的 beginRead 当时占了哪个槽？」

T-32 的修法是釜底抽薪：beginRead 返回句柄，endRead 必须交回同一个句柄。 身份不再靠猜，「哪个槽」这个问题连同它的四套补丁一起被删除了。

游泳池的手牌制度：进场发手牌（beginRead 返回 *Reader），出场交回你手里那块（endRead(reader)）。 旧方案像不发票、出场时让保安猜「你是几点进的、用的哪个格子放鞋」—— 猜错就是别人的鞋。 让 API 把身份还给人，是删代码最好的方式。

为什么句柄还要做「池」：beginRead 是热路径（每次 get/每次迭代器都要调），不能每次 malloc。 State 里埋了一个 8 个槽的嵌入式句柄池（EMBEDDED_READERS = 8，writer.zig:39； 池在首次使用时惰性接线，writer.zig:409-414 —— 因为 init 按值返回，自引用指针只能等地址定型后再接）， 用完的句柄挂回空闲链表复用（writer.zig:460-461）；并发更深时再退回堆分配，同样走空闲链表回收。 所以「开一千次读事务」的分配次数上限是「历史峰值并发读者数」，而不是一千。

注释里的 B1 不变量（writer.zig:390-403）值得念一遍：reader_count 先加（在拿 pending_free_mu 锁之前），快照 sequence 在锁内读、读者在同一个临界区里挂进活跃链表 —— 这样写者的「无读者快速回收路径」（见 6.4）永远不可能在「一个读者已经出现但还没登记完」的缝隙里把页放走。 顺序错了就是竞态，顺序对了就是证明。多线程正确性经常不在代码量，而在这种先后关系里。

3sequence 与最老读者水位线

是什么：现在回答 6.1 的闸门问题——「旧页什么时候确定没人看了」。 核心数据结构小到不像话（src/writer.zig:28）：

pub const PendingPage = struct { page_no: u32, release_seq: u64 }

每个被替换下来的旧页登记两样：页号，和「是哪一次提交让它退役的」（release_seq = 那次提交的新 sequence，写入点在 writer.zig:810）。 回收规则就写在它头顶的注释里（writer.zig:23-27）：

回收规则：当 release_seq < 最老活跃读者的快照号（水位线）时，页才可回收。 为什么是严格小于？因为快照号 ≥ 水位线的读者「可能」还引用着它；把边界也算上（≤ 会误杀）， 宁可多留一版，绝不放走一页 —— 注释原话：the correctness floor, conservatively including the boundary。

水位线怎么算（reclaimPendingFree，writer.zig:533；水位线取值 552-555）：

  • 没有活跃读者 → 水位线 = sequence + 1，所有 release_seq ≤ sequence 的页全部回收（快速路径）；
  • 有活跃读者 → 水位线 = min(sequence + 1, 所有活跃读者快照号的最小值)。 取全体读者快照的最小值（readerWatermark，writer.zig:573-581）—— 最慢的那个读者决定所有人能回收多远，这就是「水位线」这个名字的意象。

sequence + 1 这个下限不是装饰，注释（writer.zig:546-551）讲了它救过的事故（T-33 P0 fix）： 正在飞行中的提交，它的 COW 受害页带着 release_seq = sequence+1 排进队列； 此刻一个新读者注册进来（快照号 = 当前 sequence），它要走的树仍然引用着这些页。 旧代码在 count==0 时无视 release_seq 全量放页，结果新读者的下行路径被下一笔分配覆盖 —— 页在脚下蒸发。 加上下限后，「没有读者」也只回收 release_seq ≤ sequence 的页，缝隙焊死。

地铁末班车按「最慢的乘客」发车确认：站台要清人，得等跑得最慢的那位也上了车（水位线 = 最老读者快照）； 而且边界的判定永远往安全侧偏 —— 拿不准这个人到底走没走，就当他在站台（保守包含边界）。 宁可晚关门一分钟，不把人关在车外。

4pending_free：旧页的完整生命周期

是什么：把前两节串起来，一页从「被替换」到「重获新生」的完整一生是这样的：

为什么回收是「顺手做」而不是一个后台线程：三个触发点全在既有路径上 —— 读者退场时（我走了，我压着的页放了吧）、每次 commit 的开头和结尾（没人读就立刻清，别攒着）。 好处：没有后台线程、没有定时器，回收延迟天然跟负载走。 读者走得勤，pending_free 几乎永远是空的；没有读者时，每次 commit 首尾各清一次，旧页生命周期不超过一次 commit。

注意一个反直觉点：freePage 不等于「清零覆写」，只是把页号记回 freelist 可用。 所以「旧页」在被复用前，磁盘上内容一直完好 —— 这正是快照读免费的原因： 读旧版本 = 照着旧树走，页还在原地。第 5 章的「崩溃安全」用的也是同一份完好性。

5ReadTxn 的 pin：谁替旧页「挡刀」

是什么：上层 API（db.zig）是水位线机制的「用户」。三种读入口，三种 pin（钉住）方式：

入口pin 的注入点存活期
Db.get / Db.getInto 下行前 beginRead，defer endRead（db.zig:130-134）—— 短命 pin，走完树就退 单次查询期间
beginReadTxn → ReadTxn beginReadTxn 里 beginRead + 捕获快照（db.zig:576-582）；ReadTxn.end/deinit 时注销（db.zig:737-745）。读期间走的是固定的 snapshot_root（db.zig:689） 整个读事务
select 惰性迭代器 select 时 beginRead，把句柄塞进迭代器的 pin_ctx/pin_deinit 回调（db.zig:481、732-733；回调 endReadPin db.zig:751）；迭代器 deinit() 时才退 迭代器存活全程

为什么 select 需要特殊处理：迭代器是惰性的 —— select() 只定位起点， 之后的每一页都是 next() 走到时才读，且吐出的 key/value 是借用（指向 mmap 里的字节，第 3 章讲过）。 这意味着从 select 到最后一次 next 之间，任何一秒都可能跨着别人的一次 commit： 不 pin 住快照，下一次 next 踩到的可能就是刚被复用的页。 而 btree 层不认识 MVCC（它只管树），所以 db.zig 通过两个函数指针把 pin「注入」进迭代器 —— 依赖倒置：树算法保持纯净，生命周期管理留给上层。

ReadTxn.select 还有个细节（db.zig:715-718 注释）：迭代器会再开自己的一个 reader 槽，和事务的 pin 叠加 （reader 计数是增量的）—— 这样就算先 txn.end() 再 it.deinit() 的顺序失误， 迭代器自己的 pin 仍护着它借用的页。防御性设计，但只花一个槽的代价。

图书馆借阅登记的三种形态：查一句话（Db.get）= 进门登记、查完就销记； 办借书证（ReadTxn）= 证件有效期内的旧版馆藏都为你保留； 长期借阅（select 迭代器）= 书不离手期间，馆里不许回收你手里那几页的存放架位 —— 还书（it.deinit）那一刻架位才解放。三种粒度对应三种使用时长，登记制度是同一套。
为什么快照要「先注册、后取根」？顺序反过来（先拿 root 再注册）会出现：拿到的 root 属于版本 vN， 而注册的快照号却是 vN+1 的 —— 水位线会高估「没有读者需要 vN 的页」，把 root 正引用的页放走。 db.zig:416 注释管这叫 register-then-capture，与 writer.zig B1 不变量是同一思想的两端： 先声明你在，再拿你要看的东西。

6慢读者的代价：空间放大

是什么：水位线被拖住时会发生什么？答案是 README 的这句话： dirty pages held until readers drain（脏页扣着不放，直到读者散场）。

推演一个具体场景：一个读者抱着半小时前的快照做全表扫描（select 后一直不 next 完）。 这半小时里写者照常提交 —— 每一次 commit 的 COW 受害页全部合法地堆进 pending_free （release_seq 都 ≥ 读者快照，一个都放不了）。后果：

  • 文件膨胀：freelist 没有页可复用，每次 commit 只能从文件尾开新页 —— 文件长度 ≈ 「活跃数据 + 所有被读者压住的旧版本」；
  • 不是泄漏，是滞留：读者一退场（endRead 触发 reclaim），积压页一次性全数归还，文件停止增长； 已长出来的部分也会被后续 commit 优先复用消化；
  • 内存无放大：pending_free 只是一个 {u32, u64} 的数组（writer.zig:225），百万页积压也就 12 字节/页的账本钱 —— 真正的成本在磁盘空间，不在内存。
自助餐的传菜带：传菜带（freelist）要循环使用盘子，但桌上还有人正在吃的盘子不能收。 一位客人（慢读者）抱着盘子拍照两小时，厨房只能上新盘子 —— 台面（文件）越堆越满； 客人一走，旧盘子瞬间全收（回收爆发），台面立刻恢复周转。 代价真实存在，但它是暂时的空间换正确的时间，且完全自愈。

为什么这个取舍是对的：对比一下其他选项 —— 等读者（本章做法）代价是暂时的空间； 强行回收（6.1 的竞态）代价是数据损坏；让读者加锁阻塞写者，代价是 MVCC 白做、读写互相卡死。 存储引擎领域这几乎是标准答案：LMDB 同样靠「读事务压住旧页」，文档里给的忠告也一样 —— 读事务别开着不用。工程上唯一的纪律是：长扫描要及时 end()/deinit()， 不要把 ReadTxn 挂在全局变量里过夜。

一句话总结本章：COW 让「旧页不死」变得便宜，水位线让「旧页该死时才死」变得精确。 两者咬合，读者才敢无锁读、写者才敢一路狂奔 —— 这就是 README 里 MVCC reader safety 的全部内容。
