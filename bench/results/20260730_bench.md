# cube_db benchmark 数据 — 2026-07-30

机器: Apple M1 Pro / 8 cores / macOS
构建: `zig build bench -Doptimize=ReleaseFast -Dbench-scale=small`
Zig: 0.16.0
工作负载: 顺序 put + 随机 get/批量提交，**no fsync**（MemPageStore 纯内存后端）。
测试时架构状态: 纯 COW B-tree（LSM 层已删）+ LMDB 式 1TB 预留 mmap 读路径 + 显式 WriteTxn/ReadTxn 事务 API。

> 注：本数据 = `Db.put`/`putBatch`/`delete` 现在包隐式 WriteTxn（单写者互斥 + 一次 applyBatch + 一次 meta 切换）。`get` 走 mmap 零拷贝 page 指针读。

```
putbatch small  10KB         10000        403.2        24801        40.32
get     small  100B         10000        355.3        28148        35.53

delete  small  100B         10000       3963.9         2523       396.39

select  small  10KB           100        309.9          323      3098.99
compact small  100B             1          0.0            -        11.00
```

> `compact small 10KB` 单 cell 超时未稳定采到（11us 量级，与 100B 同档，无统计意义差）。large scale（1M ops）单 cell 耗时过长（put 100B ≈ 8min），未纳入本数据表；见「large scale」说明。

## 写延迟（put，顺序）

| value | avg_us/op | ops/s | 备注 |
|---|---:|---:|---|
| 100B | 505.30 | 1979 | COW 逐页分配+拷贝（每 put 一棵 COW 路径） |
| 10KB | 2004.75 | 499 | 大 value + overflow 页链 |

> put 慢是 COW 固有开销（每次 put 分配并拷贝新页路径），非 WriteTxn 互斥开销（互斥为单 mutex，亚微秒）。

## 写延迟（putBatch，批量提交）

| value | avg_us/op | ops/s | vs put |
|---|---:|---:|---:|
| 100B | 72.55 | 13783 | ~7× |
| 10KB | 40.32 | 24801 | ~50× |

> putBatch 一次提交多条 → 一次 COW 路径 + 一次 meta 切换，分摊开销。10KB 受 overflow 页链影响相对小。

## large scale 说明

`large` scale = 100B 用 1,000,000 ops，10KB 用 100,000 ops。单 cell put 100B(large) ≈ 1M × 505us ≈ 8.4 min，超常规 benchmark 时限。如需 large 数据，按需运行：

```bash
zig build bench -Doptimize=ReleaseFast -Dbench-scale=large   # 单 cell 可达数分钟
```

## 与历史数据对比

README 基准表（v2 COW B-tree）历史数据：put 100B ≈ 449us，get 100B ≈ 34.9us。本次（WriteTxn 包裹后）：put 100B ≈ 505us，get 100B ≈ 35.5us。put 略升（~12%，WriteTxn 句柄 + 单写者互斥 + deinit 开销），get 持平。putBatch 100B ≈ 72us（历史 49us，~50% 升，批量路径经 WriteTxn 暂存数组分配）。

> 写路径开销主要来自 COW B-tree 逐页分配+拷贝，非事务开销。后续优化方向：COW 写路径复用、group-commit 多 txn 合并、mmap 读路径去 dupe（返回借用切片）。

## 对标 LMDB/LevelDB
