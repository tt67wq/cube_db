第一部分页格式与编解码基础

src/format.zig 是 cube_db 的「页格式层」：它定义了一页（4096 字节）在磁盘/内存里的物理布局， 以及把页头、meta、freelist 这些结构化数据编码成字节、再从字节解码回结构体的纯函数。它不碰任何 IO—— 不 open 文件、不 mmap、不读写内存，所有函数都是「给字节进、给结构出」或反之。上层的 page_store.zig 与 file_page_store.zig 通过 @import("format.zig") （别名 f2）调用它。

1.1 文件头与设计理念

//! format.zig — v2 页格式常量与编解码（页头、meta、freelist、CRC）
//! 纯函数模块，无 IO。PAGE_SIZE=4096，固定页头 24B，页尾 4B CRC。
const std = @import("std");

pub const PAGE_SIZE: usize = 4096;
pub const PAGE_HEADER_SIZE: usize = 24;

文件头三行即点明了设计核心：纯函数、无 IO。整个模块只做「数据 ↔ 字节」的转换，不做任何持久化或内存分配。 这意味着它可被 MemPageStore（堆页）与 FilePageStore（mmap 页）无差别复用—— 无论页物理落在哪，格式层只关心「这一页 4096 字节怎么排」。

一页的固定布局：前 24 字节是页头，尾 4 字节是 CRC 校验和，中间 4096-24-4=4068 字节是各页类型的 payload 区。 这个「页头 + payload + 页尾 CRC」的三段式是贯穿全部页类型的统一骨架：

页头 24B → payload 区 4068B（内容随页类型而异） → CRC 4B

每页 4096 字节 = 24B 页头 + 4068B payload + 4B CRC

为什么页尾放 CRC 而不是页头内？ 页尾 CRC 覆盖整页（含页头与 payload）——这样页头的 page_type、 page_no 等字段本身也受校验保护，任何一字节损坏都能被检出。若 CRC 放页头内，就无法覆盖页头自身。 这是「校验和覆盖全页」的设计，与 FilePageStore 的崩溃恢复直接相关：半写页的页尾 CRC 尚未写完，读时校验必然失败， 从而被识别为无效页。

常量值含义
PAGE_TYPE_FREE0空闲页（freelist 链节点）
PAGE_TYPE_META1meta 页（页 1 / 页 2）
PAGE_TYPE_BRANCH2B-tree 内部/分支节点页
PAGE_TYPE_LEAF3B-tree 叶子节点页
PAGE_TYPE_OVERFLOW4溢出页（大值续页）

META_PAGE_0/11 / 2双 meta 页（交替写，崩溃安全）

💡 说明 页号约定：页号 0 是 NULL_PAGE（哨兵，不做任何页分配）；页号 1、2 固定给双 meta 页； 页号 3 起（FIRST_DATA_PAGE，在 page_store.zig 定义）才是数据页。文件开头至少要有 3 页（12288 字节） 才能承载两个 meta —— 这正是 FilePageStore.init 先 ftruncate 到 3 页的原因。
✅ 提示 页类型枚举编码：页类型用 u8 而非 enum，是为了磁盘布局的确定性。 裸 u8 保证磁盘上这一字节恒为 1 字节、值域固定，不依赖 enum 的 tag type（@intFromEnum 的底层整型） 推断或任何布局重排——任何平台、任何编译配置下字节完全一致。这是格式层的硬约束。

1.3 页头结构 PageHeader

/// 页头（每个页前 24 字节）
pub const PageHeader = struct {
    page_no: u32,
    page_type: u8,
    gen: u64,
    nkeys: u16,
    free_next: u32, // freelist 链下一页；非 free 页为 0
};
字段类型字节含义
page_nou324本页页号（自我标识，用于一致性校验）
page_typeu81页类型（上表 0-4）
genu648代/序列号（meta 页存 meta.sequence）
nkeysu162键数（B-tree 节点用；meta/free 页为 0）
free_nextu324freelist 链下一页；非 free 页恒为 0
padding5填充对齐到 24B

4+1+8+2+4 = 19 字节，加上 5 字节 padding 恰好 PAGE_HEADER_SIZE = 24。 页头字段按字节偏移逐个编解码，不依赖结构体内存布局——即使结构体有 padding，编码时也只写声明的字段字节。

💡 说明 gen 字段的复用：gen 是通用「代」字段。在 meta 页它存 meta.sequence （序列号，见 2.2 节），用于双页交替时比较新旧；在其他页类型它可作为代际/版本标记。一个字段多种语义，靠 page_type 区分——这是紧凑页头的设计取向。

1.4 页头编解码

comptime {
    std.debug.assert(PAGE_HEADER_SIZE == 24);
}

pub fn encodePageHeader(buf: []u8, h: *const PageHeader) void {
    std.debug.assert(buf.len >= PAGE_HEADER_SIZE);
    var pos: usize = 0;
    std.mem.writeInt(u32, buf[pos..][0..4], h.page_no, .little);
    pos += 4;
    buf[pos] = h.page_type;
    pos += 1;
    std.mem.writeInt(u64, buf[pos..][0..8], h.gen, .little);
    pos += 8;
    std.mem.writeInt(u16, buf[pos..][0..2], h.nkeys, .little);
    pos += 2;
    std.mem.writeInt(u32, buf[pos..][0..4], h.free_next, .little);
    pos += 4;
    // padding 5 bytes (leave as is)
}

encodePageHeader 用一个游标 pos 顺序写入五个字段，全部用 std.mem.writeInt 显式指定小端序（.little）。要点：

  • 字节序显式化：不依赖主机字节序（大端/小端），统一写小端，保证跨平台磁盘文件可移植。
  • 定长编码：每个字段字节数固定，无变长、无对齐 padding 参与——读回时按同样偏移解析即可。
  • padding 不写：末尾 5 字节「leave as is」，编码方不负责清零（调用方通常已 @memset 整页）。
pub fn decodePageHeader(buf: []const u8) PageHeader {
    std.debug.assert(buf.len >= PAGE_HEADER_SIZE);
    var pos: usize = 0;
    const page_no = std.mem.readInt(u32, buf[pos..][0..4], .little);
    pos += 4;
    const page_type = buf[pos];
    pos += 1;
    const gen = std.mem.readInt(u64, buf[pos..][0..8], .little);
    pos += 8;
    const nkeys = std.mem.readInt(u16, buf[pos..][0..2], .little);
    pos += 2;
    const free_next = std.mem.readInt(u32, buf[pos..][0..4], .little);
    return .{
        .page_no = page_no, .page_type = page_type, .gen = gen,
        .nkeys = nkeys, .free_next = free_next,
    };
}

解码是编码的镜像：同一套偏移游标，用 readInt 读回各字段。encode/decode 严格对称是格式层的铁律—— 任何一边多写/少读一字节都会导致后续字段错位。这也是为什么有 §2.5 的 roundtrip 测试兜底。

1.5 整页 CRC 校验

CRC 是本模块性能最敏感的部分，因为每次读写页都要计算/校验。cube_db 用「硬件加速优先，软件兜底」的策略： ARM64 走内联汇编的 CRC32 指令，其他平台（含 x86_64）走软件表驱动。关键前提是两边多项式一致、结果逐位相同。

const builtin = @import("builtin");
const crc32_hw = @import("crc32_hw.zig");

/// 计算整页 CRC32（覆盖 bytes [0..PAGE_SIZE-4)）
/// ARM64 使用硬件 CRC32 指令，其他平台走软件表驱动
pub fn computePageChecksum(page: *const [PAGE_SIZE]u8) u32 {
    return switch (builtin.cpu.arch) {
        .aarch64, .aarch64_be => crc32_hw.computePageChecksumHw(page),
        else => computePageChecksumSw(page),
    };
}

/// 软件路径（表驱动 CRC32）
pub fn computePageChecksumSw(page: *const [PAGE_SIZE]u8) u32 {
    var crc = Crc32.init();
    crc.update(page[0 .. PAGE_SIZE - 4]);
    return crc.final();
}

computePageChecksum 在编译期（comptime switch on builtin.cpu.arch）决定走哪条路径： aarch64 系用硬件，其余用软件。注意它只覆盖 [0..PAGE_SIZE-4) —— 最后 4 字节（CRC 本身）不算入校验， 这是 CRC 防自我矛盾的标准做法。

/// 写入校验和到页尾
pub fn setPageChecksum(page: *[PAGE_SIZE]u8, cs: u32) void {
    std.mem.writeInt(u32, page[PAGE_SIZE - 4 ..][0..4], cs, .little);
}

/// 验证整页校验和
pub fn verifyPageChecksum(page: *const [PAGE_SIZE]u8) bool {
    const stored = std.mem.readInt(u32, page[PAGE_SIZE - 4 ..][0..4], .little);
    const computed = computePageChecksum(page);
    return stored == computed;
}

setPageChecksum 把 CRC 写进页尾 4 字节；verifyPageChecksum 读出存储值与重算值比对。 两者配合完成「写页尾带 CRC、读页校验 CRC」的闭环。任何一字节损坏（含页头）都会让 computed != stored。

✅ 提示 ARM64 硬件 CRC 细节（见 crc32_hw.zig）：ARMv8 的 crc32x/crc32w/crc32h/crc32b 指令使用与 std.hash.crc.Crc32 相同的 IEEE 802.3 多项式（0x04C11DB7，反射 0xEDB88320）， 故结果与软件路径逐位一致。硬件实现分层处理：先以 64 字节为步长循环（每步内联 8 × crc32x），再用一个独立 while 循环处理剩余的 8 字节块，最后补齐 4B/2B/1B 余量。x86_64 不用 SSE4.2 的 crc32——因为那是 Castagnoli 多项式 （CRC-32C），与 IEEE 多项式不同，会破坏跨平台一致性，所以 x86 一律走软件。这是「一致性优先于性能」的取舍。
⚠️ 注意 init/final 语义：标准 CRC32 的 init 是 0xFFFFFFFF、final 异或 0xFFFFFFFF。 硬件代码里 crc = init ^ 0xFFFFFFFF 开头、crc ^ 0xFFFFFFFF 结尾，正是为对齐标准 CRC32 的 init/final 约定（见 crc32_hw.crc32HwArm64）。任何一边忘记这两个异或，结果都会与软件路径不一致。

第一部分到此。第二部分深入 meta 与 freelist 这两种「结构性」页的编解码，以及它们如何支撑崩溃安全。

第二部分meta 与 freelist 编解码

第一部分处理的是「每个页都有的公共页头」；第二部分处理两种承载数据库元数据的页：meta 页（数据库全局状态） 与 freelist 页（空闲页链）。这两者是崩溃恢复与页复用机制的核心，其编解码策略也与普通页头有本质不同——

本部分核心命题：meta 页通过「双页交替写 + sequence 取大」实现崩溃安全；freelist 页通过页头 free_next 串联成链、在 payload 区存 u32 页号数组。前者依赖 CRC 的「整页原子性」， 后者必须小心处理非对齐访问与借用切片的对齐声明。

2.1 MetaPage 结构与 payload

/// meta page 内容（编码在 payload 区）
pub const MetaPage = struct {
    magic: u32,
    version: u16,
    mapsize: u64,
    sequence: u64,
    root_page: u32,
    entry_count: u64,
    byte_size: u64,
    free_head: u32,
    free_count: u64,
    last_page: u32,

字段类型含义
magicu32魔数，须等于 MAGIC_V2（"CUB2"）
versionu16格式版本，须为 2
mapsizeu64映射区大小（页存储容量）
sequenceu64递增序列号，双页交替写时判定新旧
root_pageu32B-tree 根页页号
entry_countu64键值对总数
byte_sizeu64数据库字节大小
free_headu32freelist 链头页号
free_countu64空闲页总数

meta 是所有「数据库全局状态」的唯一权威存储：根页、条目数、字节数、freelist 链头、分配水位。它编码在 meta 页的 payload 区（偏移 24 之后），而不是页头——因为字段多、需要 CRC 保护且要能独立编解码。

payload 总字节数 4+2+8+8+4+8+8+4+8+4 = 58，正是 META_PAGE_PAYLOAD_SIZE。 encodeMetaPayload / decodeMetaPayload 与页头编解码同构：游标 + 小端 writeInt/readInt， 逐字段定长读写，对称编解码。区别只在字段更多（10 个）、且 payload 区是「页内切片 page[PAGE_HEADER_SIZE .. PAGE_SIZE-4]」而非独立缓冲区——因此编码前需 @memset 清零以保证未用区确定： 

pub fn encodeMetaPayload(buf: []u8, meta: *const MetaPage) void {
    var pos: usize = 0;
    std.mem.writeInt(u32, buf[pos..][0..4], meta.magic, .little);      // +4
    pos += 4;
    std.mem.writeInt(u16, buf[pos..][0..2], meta.version, .little);    // +2
    pos += 2;
    std.mem.writeInt(u64, buf[pos..][0..8], meta.mapsize, .little);    // +8
    pos += 8;
    // ... sequence / root_page / entry_count / byte_size / free_head / free_count ...
    std.mem.writeInt(u32, buf[pos..][0..4], meta.last_page, .little); // 末字段
}

pub fn decodeMetaPayload(buf: []const u8) MetaPage { /* 与 encode 严格对称 */ }

decodeMetaPayload 完全镜像编码顺序读回，故不再逐行展开——其对称性由 §2.5 的 「meta page roundtrip」测试兜底。

💡 说明 isValidMeta：
pub fn isValidMeta(meta: MetaPage) bool {
    return meta.magic == MAGIC_V2 and meta.version == 2;
}

isValidMeta 是 meta 的「语义合法性」检查：魔数匹配且版本为 2。它与 CRC 校验是两道独立防线—— CRC 防物理损坏（字节被改写），isValidMeta 防格式不兼容（例如新版本程序读到旧版本 meta）。只有两道都过， meta 才算「合法」。这与 FilePageStore 里 readMetaPageSingle 先验 CRC、再验 type、再验 isValidMeta 的链路一致。

2.2 meta 页写入与交替写

/// 将 meta 写入 page 缓冲区（page 索引 0 或 1 → 页号 1 或 2）
pub fn writeMetaPage(page: *[PAGE_SIZE]u8, meta: *const MetaPage, index: u32) void {
    std.debug.assert(index == 0 or index == 1);
    const page_no = if (index == 0) META_PAGE_0 else META_PAGE_1;
    // 写页头
    const hdr = PageHeader{
        .page_no = page_no, .page_type = PAGE_TYPE_META,
        .gen = meta.sequence, .nkeys = 0, .free_next = 0,
    };
    encodePageHeader(page[0..PAGE_HEADER_SIZE], &hdr);
    // 写 meta payload
    @memset(page[PAGE_HEADER_SIZE .. PAGE_SIZE - 4], 0);
    encodeMetaPayload(page[PAGE_HEADER_SIZE .. PAGE_SIZE - 4], meta);
    // 写校验和
    setPageChecksum(page, computePageChecksum(page));
}

writeMetaPage 把一份 MetaPage 完整写进一个 meta 页缓冲，分三步：

  1. 写页头：复用 encodePageHeader，page_type = PAGE_TYPE_META，并把 meta.sequence 塞进 gen 字段——这样读 meta 页时从页头就能直接拿到序列号，无需解码 payload。
  2. 写 payload：先 @memset 整块 payload 清零（保证 padding/未用区确定），再 encodeMetaPayload 编码。
  3. 写 CRC：setPageChecksum 在页尾写入覆盖整页的校验和。
index=0 → 页号 1 (META_PAGE_0) ↕ index=1 → 页号 2 (META_PAGE_1)

交替写：本次写 index，下次写 1-index，循环往复

✅ 提示 整页原子性（崩溃安全的地基）：writeMetaPage 是「写一整页 + 末尾补 CRC」。 对 file_page_store 而言，这一页通过 flushMetaBuffer 一次性 @memcpy 到 mmap 区——单次内存拷贝、 崩溃窗口极小；即使中途被 kill 产生半写，读时 readMetaPageSingle 的 CRC 校验也会检出下半页无效、自动回退到 另一页（mmap 区已是「旧完整页 + 新完整页」的交替布局）。这就是 readMetaPageSingle 能用 CRC 区分合法/无效页的 保证。注意 @memcpy 保证的是一次内存拷贝的原子可见性，磁盘物理持久化仍依赖后续 fsync/页缓存刷新——这正是 vtSync 与上层事务时序的职责。若是 MemPageStore（纯内存）， 交替写不产生持久化意义，但逻辑结构与文件版完全对齐，便于测试可迁移。

2.3 meta 读取与崩溃恢复

/// 从单页缓冲区读 meta（校验 checksum / page_type / magic+version，任一不过返回 null）
pub fn readMetaPageSingle(page: *const [PAGE_SIZE]u8) ?MetaPage {
    if (!verifyPageChecksum(page)) return null;
    const hdr = decodePageHeader(page[0..PAGE_HEADER_SIZE]);
    if (hdr.page_type != PAGE_TYPE_META) return null;
    const meta = decodeMetaPayload(page[PAGE_HEADER_SIZE .. PAGE_SIZE - 4]);
    if (!isValidMeta(meta)) return null;
    return meta;
}

/// 从两个 meta page 读取，取 sequence 大者（crash 安全）
pub fn readMetaPage(page0: *const [PAGE_SIZE]u8, page1: *const [PAGE_SIZE]u8) ?MetaPage {
    const m0 = readMetaPageSingle(page0);
    const m1 = readMetaPageSingle(page1);
    if (m0 == null and m1 == null) return null;
    if (m0 == null) return m1;
    if (m1 == null) return m0;
    return if (m0.?.sequence >= m1.?.sequence) m0 else m1;
}

readMetaPageSingle 对单页做三道防线：① CRC 校验失败 → null；② 页头 page_type 非 META → null； ③ isValidMeta（magic+version）不过 → null。任一不过即判定该页无效。

💡 说明 注释与代码的一份小纠错：本讲义在 code review 时发现，源码 format.zig 中 readMetaPageSingle 的注释曾写「不校验 meta 页类型」，但函数体实际做了 page_type 检查（即上面的防线 ②）—— 注释与代码矛盾。源码注释已顺手修正为本函数实际的三道防线语义，本讲义也随之更新，正文均以函数体真实逻辑为准（三道防线）。

readMetaPage 对双页做崩溃恢复：两页都有效则取 sequence 大者（最新写入的那页）， 一页无效则回退到另一页。这是 LMDB 式的原子切换策略——不做事务日志，靠「写新页 + 取新页」保证 meta 原子性。

崩溃场景推演：

  • 写 meta0 途中崩溃：meta0 半写，CRC 不匹配 → readMetaPageSingle(meta0)=null， 回退到上次完整写入的 meta1（其 sequence 较小但完整）。数据一致性保持。
  • meta0 写完、meta1 是旧值：meta0.sequence > meta1.sequence，取 meta0（最新）。
  • 双页均完好：取 sequence 大者，正确指向最近提交。
  • 全新库（双页皆无效）：返回 null，上层按 fresh DB 初始化。
⚠️ 注意 与 FilePageStore 的闭环：format 层只负责「读双页取大」；而「下次写哪页」由 FilePageStore.meta_index 维护（写 meta0 后翻转为 1）。reopen 时 init 用 readMetaPageSingle 逐页判定、选 sequence 大者为活跃页，并把 meta_index 指向被覆盖的旧页—— 格式层提供判据，存储层维护状态机，二者协作构成完整崩溃恢复。

2.4 freelist 页编解码

freelist 是空闲页的回收复用链：空闲页的 payload 区存一个 u32 页号数组（可复用的页号）， 页头 free_next 指向链上下一页。这样空闲页自身即存储、无额外索引结构。

/// 空闲页的 payload 区存储 u32 页号数组，后续扩展
/// 写入 freelist 条目到页（覆盖 payload 区）
pub fn writeFreelistEntries(page: *[PAGE_SIZE]u8, entries: []const u32) void {
    const payload = page[PAGE_HEADER_SIZE .. PAGE_SIZE - 4];
    // 前 4 字节存条目数
    std.mem.writeInt(u32, payload[0..4], @intCast(entries.len), .little);
    var pos: usize = 4;
    for (entries) |e| {
        if (pos + 4 > payload.len) break;
        std.mem.writeInt(u32, payload[pos..][0..4], e, .little);
        pos += 4;
    }
    // 剩余 payload 区清零
    if (pos < payload.len) { @memset(payload[pos..], 0); }
    // 更新页校验和
    setPageChecksum(page, computePageChecksum(page));
}

writeFreelistEntries 把 u32 页号数组写进 freelist 页 payload：前 4 字节存条目数 count，随后按 4 字节一个页号顺序写入，剩余区域清零，末尾补 CRC。pos+4 > payload.len 的边界检查防止越界（最坏截断，不影响正确性）。

/// 从页读 freelist 条目（返回借用 payload 的切片）
/// 返回 []align(1) const u32：page 是 u8 数组（1 对齐），payload 偏移 24
/// 类型层面只保证 1 对齐，故借用切片诚实声明 []align(1) const u32，
/// 避免用 @alignCast 强行提升对齐（debug 下会 panic，release 下是 UB）。
pub fn readFreelistEntries(page: *const [PAGE_SIZE]u8) []align(1) const u32 {
    const payload = page[PAGE_HEADER_SIZE .. PAGE_SIZE - 4];
    const count = std.mem.readInt(u32, payload[0..4], .little);
    const max = @min(count, @as(u32, @intCast((payload.len - 4) / 4)));
    // 跳过前 4 字节 count 后，[]align(1) const u32 诚实声明对齐，
    // 允许非对齐 u32 读取（x86/ARM 原生支持），无需 @alignCast 运行时检查
    const ptr: [*]align(1) const u32 = @ptrCast(payload.ptr);
    return ptr[1..][0..max];
}
🔴 危险 对齐陷阱（历史 bug，commit d043687）：从类型系统层面看，page 是 [PAGE_SIZE]u8（1 对齐），payload.ptr 是 [*]u8——编译器无法证明其中的 u32 是 4 对齐的。 若改用 @alignCast 把返回类型提升到 4 对齐，在 debug/fast 构建下会触发 alignment panic，release 下则是 未定义行为（UB）——因为实际地址只保证 1 字节对齐。当前代码刻意用 @ptrCast（不做运行时对齐检查）配 诚实声明的 []align(1) const u32——告诉编译器这些 u32 只保证 1 字节对齐，由 CPU 原生支持非对齐读取 （x86/ARM 均支持），编译期不再生成对齐检查。这也是「用类型系统表达真实不变量，而非靠运行时断言硬扛」的范例。

format.zig 在系统全貌中的位置

format.zig 页格式层（本讲义） ↑ 依赖 page_store.zig PageStore 抽象 + MemPageStore ↑ 依赖 file_page_store.zig mmap 文件 Store ↑ 依赖 btree.zig / writer.zig / db.zig 上层

设计亮点：

  1. 纯函数、无 IO：只做「数据 ↔ 字节」，可被内存/文件两种 Store 无差别复用。
  2. 定长小端编码：逐字段 writeInt/readInt，跨平台字节一致，无对齐依赖。
  3. CRC 覆盖整页 + 硬件加速：ARM64 走指令、x86 走软件，多项式一致保证结果逐位相同。
  4. meta 双页交替写：sequence 取大 + 坏页回退，LMDB 式无日志崩溃安全。
  5. 诚实对齐声明：[]align(1) const u32 表达真实不变量，避开 @alignCast panic。
⚠️ 注意 风险与约束：
  • 格式不可变：一旦线上库写入，页头/ meta / CRC 布局即冻结。改版需引入新 magic/version 并做迁移，不能原地改布局。
  • CRC 仅检出、不纠错：CRC32 检测力强但非纠错码，检测到损坏只能丢弃/报错，无法恢复数据。
  • 非对齐读取依赖 CPU：[]align(1) u32 的读取依赖目标架构原生支持非对齐访问（x86/ARM 均支持）；理论上有架构不支持，则需显式字节拼接。
  • freelist 边界截断：写入时 pos+4 > payload.len 只是 break 截断，若条目数超载会静默丢弃尾部条目——当前设计中条目数远小于容量，属可接受上限。

format.zig 以「定长、小端、CRC 兜底」为基底，用纯函数把页头、meta、freelist 这三种结构编码成确定性的字节布局。 它不关心页存哪、怎么持久化，只保证「写进去的能原样读回来，坏掉的能被检出」。这一层稳定了，上层两个 PageStore 与 B-tree 才能在其上安全构建。
