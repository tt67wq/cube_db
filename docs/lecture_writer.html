第一部分MVCC 读者模型（T-30）

src/writer.zig 的核心职责之一是 MVCC 安全的脏页回收：写者每次提交都会把 COW 出来的旧页放进 pending_free 列表延迟回收，回收的前提是没有任何活跃读者还在引用这些页。 T-30 之前，读者跟踪只有单一全局 reader_count：任何一个读者活跃，所有积压脏页都不敢动， 只有最后一个读者退出（prev==1）才一次性全部回收。T-30 把它演进为 逐读者序列注册 + oldest-reader watermark：一页只要在序列 S 之前释放、且所有活跃读者的快照 都 ≥ S，就能回收——不必等最老的那个读者退出。

💡 为什么旧模型是个缺陷：单个长命读者会钉住其存活期间所有提交释放的脏页。 一个开着迭代器慢慢扫描的读者 + 持续写入的负载，会让 pending_free 与 dirt 计数无界增长； compact() 在有读者时更是只能静默清计数（dirt 误报 0，页仍被钉住）。精确回收语义也是后续 「freelist 持久化」（演进点 #2）的前置条件——free 链要安全落盘，必须先知道每一页何时真正可回收。

1.1 从全局计数到逐读者注册

先看新模型给回收判据带来的变化。旧 pending_free 只存裸页号 （ArrayList(u32)），“能不能回收”的答案只有两种：无读者（全回收）或有读者（全保留）。 新模型让每个条目携带释放序列：

/// pending_free entry: page number + the sequence of the commit that freed it
/// (that commit's new_sequence).
/// Reclamation rule: safe to reclaim when release_seq < the oldest-active-reader
/// watermark (every active reader snapshot is >= watermark > release_seq, so
/// nobody can still reference the page); equal or greater must be kept (old
/// snapshots remain valid — the correctness floor, conservatively including
/// the boundary).
pub const PendingPage = struct {
    page_no: u32,
    release_seq: u64,
};

release_seq 是释放该页的那次提交的 new_sequence（applyBatch 第 3 步入队时写入 cur_sequence + 1）。这个数字的语义是：该页属于 cur_sequence 时刻的树—— 快照 ≥ new_sequence 的读者不可能引用它（它已经不在 new_sequence 提交之后的树里）， 而快照更老的读者可能还在沿着它走。于是回收判据从二值变成了一条精确的序列不等式：

回收规则（正确性核心）：页 release_seq = S（由 q → S 的提交释放，属于 q = S−1 时刻的树） 可以回收，当且仅当所有活跃读者的快照都 ≥ S——即 release_seq < watermark，其中 watermark = 活跃读者快照序列的最小值。快照为 s 的读者遍历的是 root(s) 的树， 它引用的页只可能是“释放序列 > s”的页（被更晚的提交释放、但当时还是树的一部分）， 所以快照 ≥ S ⇒ 不引用该页。

注意边界：判据用严格小于。快照恰好等于 S 的读者看到的是 root(S)， 理论上已不含该页（它在 S−1 → S 提交时被替换），但实现选择保守保留—— “等于 watermark 的页不回收”。这半步保守换来的是注册竞态下的安全余量（见 1.3 的 B1 不变式）。

⚠️ 注意 两类读者、两套机制：reader_count（全局原子计数）仍然保留， 它服务于快路径——reader_count == 0 时无需任何序列计算，直接全量回收（既有行为不变）。 活跃读者链表（readers_head，显式 Reader 句柄，见 1.2）只在有读者时参与精确判据。两套机制各司其职： 计数答“还有没有人”，活跃集答“谁最老”。

1.2 显式 Reader 句柄：结构、池与注册

T-32 用显式 Reader 句柄取代了早期逐读者注册的槽位/TLS 栈机制 （reader_slots、overflow_readers、CLAIM_BIT、 claimReaderSlot、unregisterReaderSlot、saturatingOverflowDec ——全部删除）。难点从「注销如何配对」变成了「句柄如何回收」：因为 endRead 现在 携带句柄参数，注销不再需要任何隐式栈；代价是必须管理好句柄池，保证无泄漏、无双重释放。 载体是一个小结构体与一个按需链接的池：

/// 嵌入式句柄池大小：select() 读者热路径保持零分配（8 个并发内）
const EMBEDDED_READERS = 8;

pub const Reader = struct {
    state: *State,       // 所属 State（注销时做跨状态误用检查）
    seq: u64,            // 快照序列（watermark = 活跃集 min seq）
    active: bool,         // 双重 endRead 的 no-op guard
    prev_active: ?*Reader = null,  // 活跃集（intrusive 双向链表）链接
    next_active: ?*Reader = null,
    next_free: ?*Reader = null,       // 空闲池 free-list 链接
};
成员角色
readers_head活跃集头指针。State 内 ?*Reader，构成 intrusive 双向链表（受 pending_free_mu 保护）；watermark 就是遍历这个链表取 min seq，不再有 64 槽上限
reader_free空闲句柄池 free-list 头。注册时 pop、注销时 push，受同一把锁保护
embedded_readers[8]Reader 嵌入式池。首次 beginRead 时一次性链接进 free-list（init 按值返回，self 指针只能在此处接线），保证 select() 读者路径零分配
reader_poolArrayList(*Reader)，记录所有堆分配的句柄，供 deinit 统一销毁（无泄漏）；随峰值并发有界增长、经 free-list 回收

beginRead 的注册在 pending_free_mu 临界区内完成——关键的是快照读取与入活跃集 共享同一临界区：

pub fn beginRead(self: *State) *Reader {
    _ = self.reader_count.fetchAdd(1, .acquire);   // 先计数（B1：见 1.3）
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();
    if (!self.readers_linked) { /* 首次：把 8 个嵌入式句柄链入 free-list */ }
    const r = self.reader_free orelse blk: { /* 池满 → 堆分配一个，记入 reader_pool */ ... };
    self.reader_free = r.next_free;
    r.* = .{
        .state = self,
        .seq = self.sequence.load(.acquire),  // 锁内读快照 + 入活跃集 = 一个临界区
        .active = true,
        .prev_active = null,
        .next_active = self.readers_head,
        .next_free = null,
    };
    if (self.readers_head) |h| h.prev_active = r;
    self.readers_head = r;
    return r;
}

为什么这比槽位+TLS 简单且更好：

① 无槽上限、无 overflow 降级。活跃读者数由池按峰值并发撑开（8 嵌入式 + 堆 fallback）， 不再有「并发读者 > 64 → 退化为全钉」的分支，watermark 恒为精确 min-seq。旧的 64 槽/16 层/CLAIM_BIT 降级路径整段消失，读者簿记从「两套计数（全局 + 槽位）」收敛为「一套计数 + 一个链表」。

② 注册的原子性从哨兵让位给锁。旧机制用「哨兵 0 占位 → 读 seq → 发布快照」三步在无锁下 维持 B1（1.3）。新机制干脆把 seq.load 与入活跃集放进同一个锁临界区—— 其间没有任何回收能交错，watermark 在锁内永不可能看到「已入 pending_free 的页 < 本读者的 seq」。 语义等价，但无需位编码哨兵，正确性由锁序直接保证。

③ 热路径零分配由嵌入式池保证。8 个并发读者以内 beginRead 不分配堆内存 （嵌入式数组 + 链表操作），select() 迭代器借用的零分配测试（iterator_borrow）继续成立； 超出的堆句柄也被 reader_pool 记录并在 deinit 统一释放，不随 begin/end 反复分配。

💡 说明 池与 active/free 两条链为何并重：next_active 链让 readerWatermark 能在锁内精确遍历所有存活读者；next_free 链让句柄在注销后能立即复用。 一个 Reader 要么在活跃链上（active=true），要么在空闲链上，两条链都受 pending_free_mu 保护——同一把锁既串行化「读者注册/注销 vs 回收」，也串行化句柄的取/还， 不存在句柄被并发抢用的可能（详见 1.3 的误用语义）。

1.3 beginRead/endRead 与 B1 不变式

注册容易，注销也容易——因为 endRead 现在携带句柄：fn (self: *State, reader: *Reader) void。 注销不再需要任何线程本地栈来“找回我是哪个注册”，配对信息就是句柄本身。代价转到了句柄的语义防护上： 同一个句柄不得被重复释放，也不得对不属于本 State 的句柄误释放。

pub fn endRead(self: *State, reader: *Reader) void {
    if (reader.state != self) return; // 跨状态误用：guarded no-op（评审裁决，见下）
    if (!reader.active) return;    // 双重 endRead：no-op
    {
        self.pending_free_mu.lockUncancelable();
        defer self.pending_free_mu.unlock();
        // 从活跃链摘下
        if (reader.prev_active) |p| p.next_active = reader.next_active
        else self.readers_head = reader.next_active;
        if (reader.next_active) |n| n.prev_active = reader.prev_active;
        reader.active = false;
        // 还回空闲池
        reader.next_free = self.reader_free;
        self.reader_free = reader;
        _ = self.reader_count.fetchSub(1, .release);
    }
    if (self.dirt.load(.acquire) > 0) self.reclaimPendingFree();
}

误用语义（T-32 评审裁决）：对不属于本 State 的句柄调用 endRead（reader.state != self）， 实现为 guarded no-op——读到 reader.state 后、在任何锁/原子/链表修改之前返回。 四个理由（见 review.md）：

① 不会损坏任一 State。返回早于任何临界区，对方 State 的注册表、free-list、reader_count 以及本 State 的注册都未被触碰，也没有与 reclaimPendingFree/flushPendingFree 的任何交错。

② guard 不会被 stale state 绕过。reader.state 在 beginRead 的临界区里每次复用都会重写， 且池是 per-State 的（嵌入式数组 + 堆句柄不会跨 State 迁移）——句柄永远报告其真实属主，无法用旧 state 骗过检查。

③ 失败模式是「可见的泄漏」，不是静默损坏。若调用方误路由且一直没正确释放，读者会一直登记： reader_count 恒 > 0、watermark 钉住、pendingFreeCount()/dirtCount() 升高——和「忘了 endRead」一样， 通过既有公开计数即可检出，不会损坏数据或崩溃。

④ panic 更粗暴且不可测。panic 在 MVCC 临界路径上更严厉，且 Zig 0.16 无进程内 expectPanics， panic 契约在标准测试框架下不可测（需子进程 rig）；no-op 语义则被 reader_handle_test.zig 的用例 7 直接测试并固化。

💡 说明 双重 endRead 同样是 no-op：首次释放后 active=false，第二次进入前 if (!reader.active) return 直接返回——幂等。注意这两道 guard（state 与 active） 都在取锁前完成，保证常见路径零锁开销；并发对同一句柄的 endRead 属于契约外误用（评审 F1 记录了 可选的一行加固：把 active 检查移入临界区，非阻塞）。

最后是注册模型最关键的次序不变式——B1（评审阻塞项，新机制由锁直接保证）：

pub fn beginRead(self: *State) *Reader {
    _ = self.reader_count.fetchAdd(1, .acquire);   // 先计数
    self.pending_free_mu.lockUncancelable();          // 锁内完成注册
    defer self.pending_free_mu.unlock();
    // （池取句柄省略）
    r.* = .{ .state = self,
             .seq = self.sequence.load(.acquire),      // 锁内读快照
             .active = true,
             .prev_active = null, .next_active = self.readers_head, ... };
    self.readers_head = r;                               // 与读快照同一临界区入活跃集
    return r;
}

关键顺序：fetchAdd（先计数）→ 锁内读 sequence → 锁内入活跃集。

① 先计数再取锁。若顺序颠倒（先占活跃集再计数），取锁前可能出现「count==0 的假象」， 写者的 grace-period 全量回收（applyBatch 步骤 0/9）会把读者还需要的页放走。先 fetchAdd 保证 任何并发回收看到 0 时，本读者尚未开始，不可能引用将被放走的页。

② 读快照与入活跃集在同一个临界区。这正是 B1 在新机制下的落点。旧机制用「哨兵 0 占位 → 读 seq → 发布真实快照」三步在无锁下维持 B1；新机制把 seq.load 与入活跃集放进同一个锁临界区， 其间回收（同样持有 pending_free_mu）不可能交错。因此任何一次 reclaimPendingFree 在锁内计算 watermark 时，要么看到本读者已带着真实 seq 在活跃集里（watermark 被其压低），要么本读者尚未入集—— 但它读快照也在同一临界区，故此刻其 seq 还没被读过，也就没有「seq 已读但未登记」的窗口。

✅ 正确性 B1 不变式（锁序版）：因为 readerWatermark 只在持有 pending_free_mu 时被调用，而 beginRead 的 seq 读取与入活跃集共享同一临界区， watermark ≤ 每个活跃读者的快照 由锁序直接成立。读者引用的页满足 release_seq > 快照 ≥ watermark， 被水位放行的页（release_seq < watermark）在数学上不可能被任何活跃读者引用。读者快照注册 先于返回，调用方（Db.select / ReadTxn）随后才捕获 root——无论旧 root 还是新 root， 其 COW 旧页都滞留在 pending_free 直到 watermark 放行（这正是 db.zig 里 T-29「先注册后捕获」惯例在 writer 层的落点）。

1.4 watermark 精确回收

注册数据齐了，剩下的两个函数把数据变成回收动作。readerWatermark 取活跃快照最小值：

/// Oldest-active-reader watermark: the minimum snapshot sequence across
/// the active-reader set. Empty set -> 0 (a reader is mid-registration, its
/// seq not yet visible) = the conservative floor, pin everything.
/// Caller must hold pending_free_mu.
fn readerWatermark(self: *State) u64 {
    var min: u64 = 0;
    var found = false;
    var cur = self.readers_head;
    while (cur) |r| : (cur = r.next_active) {
        if (!found or r.seq < min) { min = r.seq; found = true; }
    }
    return min;
}

活跃集是 intrusive 双向链表（头 readers_head），遍历即可取 min seq，无槽上限、无位编码。 一个“返回 0”的来源要注意：found == false（活跃集为空但 reader_count > 0，说明读者正在注册的窗口， 其 seq 尚未入集）——水位保守为 0。0 是保守下界：严格小于 0 的 release_seq 不存在，所以什么都不放行。

reclaimPendingFree 是增量回收本体，被 endRead 和 compact 调用：

fn reclaimPendingFree(self: *State) void {
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();
    if (self.reader_count.load(.acquire) == 0) {
        // 无读者（锁内复查）→ 全量回收（旧快路径，保留）
        for (self.pending_free.items) |pp| self.store.freePage(pp.page_no);
        self.pending_free.clearRetainingCapacity();
        self.dirt.store(0, .release);
        return;
    }
    const watermark = self.readerWatermark();
    var keep: usize = 0;
    for (self.pending_free.items) |pp| {
        if (pp.release_seq < watermark) {
            self.store.freePage(pp.page_no);  // 放行
        } else {
            self.pending_free.items[keep] = pp;  // 原地保留
            keep += 1;
        }
    }
    self.pending_free.shrinkRetainingCapacity(keep);
    self.dirt.store(keep, .release);
}
endRead / compact→ 取 pending_free_mu→ 锁内查 reader_count→ 0：全量回收｜ >0：算 watermark→ 原地分区：release_seq < w 放行，其余保留→ dirt = 保留数

几个工程要点：

① 分区是原地的、O(n)、零分配。单次遍历里 keep 游标压缩保留项（source 下标恒 ≥ keep， 不会覆盖未处理项），shrinkRetainingCapacity 只改长度。回收发生在读者线程的 endRead 里——读者路径不碰 state.allocator，只动 MemPageStore.freelist（自有锁保护）， 所以 std.testing.allocator 的泄漏检测依然有效。

② reader_count 的检查在锁内。读者回收与写者 append（applyBatch 第 3 步） 经 pending_free_mu 互斥；锁内看到 count==0 才全量。若检查在锁外，会出现 “检查时无读者 → 锁前新读者注册 + 写者入队 → 全量回收误放新读者引用的页”的窗口。 锁内复查保证：其后注册的新读者快照必 ≥ 全部 pending 的 release_seq，不可能引用被回收的页。 （写者侧的 flushPendingFree 快路径在锁外预检 count 是安全的——单写者上下文里 sequence 不会在检查与锁之间前进。这两处看似一样、实则语境不同，是很好的阅读考点。）

③ dirt 从“计数器”变成“真话”。回收后 dirt = keep——仍被钉住的真实页数。 配合 compact() 不再静默清零（T-30 语义修正），以及 applyBatch 把 dirt 更新移入锁内 （避免写者用陈旧长度覆写读者刚写下的 keep），dirt == pendingFreeCount() 成为全程不变式， 监控与测试不再被误导性 0 值欺骗。

④ 末位读者快路径保留的是「回收」语义，不是「免锁」。新实现里 endRead 每次都要取 pending_free_mu 才能安全地把句柄从活跃链表摘下并还回 free-list（intrusive 链必须串行化）； 但锁内的摘链 + fetchSub 是 O(1)、零分配的。dirt > 0 守门的是锁之后的 reclaimPendingFree——无积压时跳过，避免再做一次「遍历 + 分区」的重活。 最后一个读者退出时 count==0 自然走全量分支。这把锁的引入是显式句柄的固有代价 （活跃集是链表而非无锁槽位），换来的是 B1 由锁序直接保证（1.3）。

✅ 正确性 水位只升不降的回收时机论证：新读者的快照 = 当前 sequence， 永远 ≥ 既有任何快照，所以 begin 只会保持或抬高水位下限；水位上升只发生在 endRead。 因此回收动作全部挂在 endRead / compact / applyBatch 快路径三个时机上即可，不会漏放—— 即使某次 endRead 因 dirt==0 跳过回收（此时本就无页可放），下次任何时机都会重新计算。 配套测试（mvcc_test.zig T-30 用例）锁定三件事：短命读者退出（长命读者仍活跃）即回收 release_seq < watermark 的页；release_seq > 长命读者快照 的页不回收；末位读者退出全量清零。
⚠️ 注意 边界保守性的代价：release_seq == watermark 的页会被多钉一个读者代际 （下一位读者退出、水位抬高后才放行）。这是刻意的半步保守：它给 B1 的注册窗口 （读快照 → 入活跃集之间）留出安全余量，也是“精确判据”与“简单可证”的折中。 若未来追求极致精确，可以改为 release_seq ≤ watermark 放行，但必须同时改变注册次序—— 复杂度上升，收益只有一个序列代际的延迟，不值。

第二部分State 骨架与读者 API

如果说第一部分的显式 Reader 句柄是「精密切割刀」，那么 State 就是整个 writer 的「底盘」： 它持有全部原子状态（root / sequence / dirt / 统计）、MVCC 读者模型的两套簿记（全局计数 + 活跃读者链表）、 以及待回收页队列 pending_free 与保护它的互斥锁 pending_free_mu。 本部分逐字段拆解 State（writer.zig:150-219），讲清 init/deinit 的生命周期约定、 beginRead/endRead 这对读者 API 的精确顺序（B1 不变式落在何处）、 以及 compact 在 T-30 之后如何做到「dirt 永远说真话」。

2.1 State 字段与 init/deinit

init 只做字段默认化，无任何 I/O；deinit 则是一条硬约定：

pub fn init(allocator: std.mem.Allocator, store: PageStore, opts: Options) State {
    return .{
        .allocator = allocator,
        .store = store,
        .root = std.atomic.Value(u32).init(btree.NULL_ROOT),
        .sequence = std.atomic.Value(u64).init(0),
        .dirt = std.atomic.Value(u64).init(0),
        // ... 其余原子量同理初始化为 0 / false；读者簿记字段走默认值
        // (readers_head/reader_free = null, embedded_readers = undefined,
        //  readers_linked = false, reader_pool = .empty)
        .pending_free = .empty,
        .pending_free_mu = .{},
    };
}

pub fn deinit(self: *State) void {
    self.closed.store(true, .release);
    // Free the remaining pending_free (safe: writer thread done, no readers)
    for (self.pending_free.items) |pp| self.store.freePage(pp.page_no);
    self.pending_free.deinit(self.allocator);
    // 释放所有堆分配的句柄（嵌入式 8 个随 State 一起回收，无需逐个 destroy）
    for (self.reader_pool.items) |r| self.allocator.destroy(r);
    self.reader_pool.deinit(self.allocator);
}
💡 说明 deinit 的安全前提：注释里那句 "safe: writer thread done, no readers" 是调用契约—— deinit 直接遍历 pending_free 全量 freePage，不取 pending_free_mu、不查 reader_count。 它只在「写者线程已结束、无任何读者存活」的关闭路径上调用（Db.close 持有写锁后到达）。 closed.store(true) 在最前面，让并发迟到者（如 applyBatch）走 error.Closed 分支而不是踩已释放内存。

pending_free 与 pending_free_mu：谁在锁内动这张表

pending_free 是 ArrayList(PendingPage)——一个会被写者线程与读者线程同时 mutate 的容器， 这正是 pending_free_mu 存在的理由（历史上 ArrayList 并发 mutate 曾直接 SEGV，修复见 commit 7f4805c）。 全部三处 mutate 点：

// ① 写者 append（applyBatch 步骤 3，writer.zig:679-697）：
{
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();
    for (batch_dirty.items) |pn| {
        // T-30: carry the release sequence (this commit's new_sequence)
        self.pending_free.append(self.allocator,
            .{ .page_no = pn, .release_seq = cur_sequence + 1 }) catch {};
    }
    // T-30: dirt is updated under the lock together with the append
    self.dirt.store(@intCast(self.pending_free.items.len), .release);
}

// ② 读者/compact 增量回收（reclaimPendingFree，见 2.3）
// ③ 写者 grace-period 全量回收（flushPendingFree，见 2.3）
⚠️ 注意 dirt 为什么搬进锁内：T-30 之前 dirt.store(...) 在 applyBatch 第 7 步锁外执行， 与读者线程 endRead 里的回收写回 dirt.store(keep) 存在竞态——写者可能用「append 前的旧值」覆盖读者刚算出的「回收后新值」。 T-30 把它移进 pending_free_mu 临界区，与 append 原子化：锁内永远满足不变式 dirt == pending_free.items.len。
🔴 风险 append 的 catch {}：页号入队时 OOM 被静默吞掉——该脏页从此永远不会被回收（泄漏一页，但不破坏正确性： freePage 少调一次只是浪费空间，多调一次才是灾难）。这是有意的保守取舍：写路径不因簿记失败而中断提交。

2.2 beginRead / endRead

这对 API 是 MVCC 的入口，也是第一部分所有机制的被调用方。它们的语句顺序本身就是正确性论证：

pub fn beginRead(self: *State) *Reader {
    _ = self.reader_count.fetchAdd(1, .acquire);
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();
    if (!self.readers_linked) { /* 首次：链入 8 个嵌入式句柄 */ }
    const r = self.reader_free orelse blk: { /* 池满 → 堆分配 + 记入 reader_pool */ ... };
    self.reader_free = r.next_free;
    r.* = .{ .state = self,
             .seq = self.sequence.load(.acquire),
             .active = true,
             .prev_active = null,
             .next_active = self.readers_head, .next_free = null };
    if (self.readers_head) |h| h.prev_active = r;
    self.readers_head = r;
    return r;
}

pub fn endRead(self: *State, reader: *Reader) void {
    if (reader.state != self) return; // 跨状态误用：guarded no-op
    if (!reader.active) return;    // 双重 endRead：no-op
    {
        self.pending_free_mu.lockUncancelable();
        defer self.pending_free_mu.unlock();
        /* 从活跃链摘下、active=false、还回 free-list */
        _ = self.reader_count.fetchSub(1, .release);
    }
    if (self.dirt.load(.acquire) > 0) self.reclaimPendingFree();
}

beginRead 的关键顺序是评审轮 B1 修复后定下的不变式（writer.zig:249-282）：

① fetchAdd(reader_count)→ ② 取 pending_free_mu→ ③ 池取句柄 + 锁内 sequence.load（读快照）→ ④ 锁内入活跃集（active=true）→ ⑤ 返回句柄，调用方捕获 root
  • ①→②：先计数再取锁。若顺序颠倒，取锁前可能出现「count==0 的假象」，写者的 grace-period 全量回收（applyBatch 步骤 0/9）会把读者还需要的页放走。
  • ③→④（B1 核心）：读快照与入活跃集在同一个锁临界区内完成。期间回收（同样持锁）不可能交错，watermark 要么看到本读者带着真实 seq 在集里（被其压低），要么本读者尚未入集——而其 seq 也还没被读，没有「seq 已读但未登记」的窗口。这正是 B1 修复掉的竞态，由锁序直接保证，无需哨兵占位。
  • ⑤：注册先于返回，调用方（db.zig 的 ReadTxn / select 的 Iterator pin）随后才捕获 root；无论看到新 root 还是旧 root，其 COW 旧页都滞留在 pending_free 直到 watermark 放行。
✅ 正确性 endRead 的顺序同样有讲究：先 fetchSub 再（出锁后按积压）回收。注销发生在回收 之前，所以本次计算 watermark 时自己已经不在活跃集里——「退出者的快照不再需要保护」先于「按新 watermark 放页」。 若注销在后，watermark 会被自己的旧快照压低，只是偏保守（多钉不少放），不破坏正确性，但白白放过回收机会。
💡 说明 读者路径的锁开销与零分配：新实现里 endRead 每次都要取 pending_free_mu （把句柄从活跃链表摘下并还回 free-list），但锁内操作是 O(1)、零分配的；if (dirt.load(.acquire) > 0) 守门的是锁之后的 reclaimPendingFree，无积压时跳过（见 1.4 ④）。 而 beginRead 也取同一把锁，但 8 个嵌入式句柄以内零堆分配（链表取/还）， select() 迭代器借用的零分配测试（iterator_borrow）依然成立。这把锁的引入是显式句柄的固有代价， 换来的是 B1 由锁序直接保证（1.3）。
⚠️ 注意 忘记 endRead 的后果：读者名额泄漏——reader_count 永不归零、句柄永久留在活跃集， watermark 被钉在泄漏者的快照上，其后所有提交的脏页（release_seq >= watermark）永不回收，pending_free 无界增长。 db.zig 层用 defer endRead / Iterator 的 pin_deinit 兜底，但直接使用 State 的调用方必须自觉配对。 （跨状态误用与双重 endRead 的 guarded no-op 语义见 1.3。）

2.3 compact 与 dirt 真实性

T-30 之前 compact 在有读者时只做 dirt.store(0)——计数被静默清零而页面仍被钉住，dirt 说谎。 现在的版本把「回收」统一交给 reclaimPendingFree，自己只负责 meta：

pub fn compact(self: *State) !void {
    // Reclaim (dispatched internally by reader_count/watermark; dirt set
    // to the remaining pinned count)
    self.reclaimPendingFree();
    // Write the new meta
    const cur_root = self.root.load(.acquire);
    const cur_sequence = self.sequence.load(.acquire);
    // ... entry_count / byte_size 同快照 ...
    const meta = f2.MetaPage{
        .magic = f2.MAGIC_V2, .version = 2,
        .mapsize = self.store.mapsize(),
        .sequence = cur_sequence + 1,
        .root_page = cur_root,
        // free_head/count、last_page 由 FilePageStore.writeMeta 覆写校准
        ...
    };
    try self.store.writeMeta(&meta);
    if (self.opts.fsync) {
        try self.store.sync();
    }
    self.sequence.store(cur_sequence + 1, .release);
    // T-30: dirt is no longer zeroed — reclaimPendingFree already set it
    // to the still-pinned page count
}

注意函数末尾没有 dirt.store(0)——这不是遗漏，而是语义修正的落点。回收的真正逻辑在 reclaimPendingFree，以及它的「全量兄弟」flushPendingFree：

// 全量回收：不检查 reader_count（调用方保证无读者——applyBatch 的
// reader_count==0 快路径，单写者上下文）
fn flushPendingFree(self: *State) void {
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();
    for (self.pending_free.items) |pp| {
        self.store.freePage(pp.page_no);
    }
    self.pending_free.clearRetainingCapacity();
    self.dirt.store(0, .release);
}

// T-30 增量回收：按 oldest-reader watermark 分拣
fn reclaimPendingFree(self: *State) void {
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();

    if (self.reader_count.load(.acquire) == 0) {
        // 无读者 → 全量回收（旧快路径，保留）
        for (self.pending_free.items) |pp| self.store.freePage(pp.page_no);
        self.pending_free.clearRetainingCapacity();
        self.dirt.store(0, .release);
        return;
    }
    const watermark = self.readerWatermark();
    var keep: usize = 0;
    for (self.pending_free.items) |pp| {
        if (pp.release_seq < watermark) {
            self.store.freePage(pp.page_no);   // 释放
        } else {
            self.pending_free.items[keep] = pp;  // 原地压缩保留
            keep += 1;
        }
    }
    self.pending_free.shrinkRetainingCapacity(keep);
    self.dirt.store(keep, .release);
}

三个值得咀嚼的设计点：

  • reader_count 检查在锁内。为什么不锁外判一次就完事？因为「count==0 → 全量放页」这个决定必须与 「新读者注册」互斥。读者注册（fetchAdd + 锁内读快照 + 入活跃集，见 1.2/1.3）取同一把锁， 但 fetchAdd 先于取锁发生；只要回收在锁内看到 count==0，其后注册的读者快照必然 ≥ 所有已入队页的 release_seq，不可能引用被放走的页。锁内复查把这个论证钉死。
  • 分拣是原地压缩（keep 游标）。一次遍历，无临时分配：release_seq < watermark 的立即 freePage， 其余前移到 items[0..keep]，最后 shrinkRetainingCapacity。注意判定是严格小于—— release_seq == watermark 的页保守保留（边界页宁可多钉一拍，也不赌快照可见性的边）。
  • flushPendingFree 与 reclaimPendingFree 的分工。前者是「调用方已证无读者」的全量版本，只在写者自己的 applyBatch 步骤 0/9（grace-period）调用；后者是通用入口（endRead / compact），自己锁内判 count。两者共享同一把锁， 对 pending_free 的所有 mutate 归一。
✅ 正确性 dirt 真实性不变式：T-30 之后，dirtCount() == pendingFreeCount() 恒成立 （deinit 之外）。三个写点——applyBatch 锁内 append 后 store(len)、reclaim 的 store(keep)、flush 的 store(0)——全在 pending_free_mu 临界区内与队列变更原子配对。compact_strong_assert_test.zig 正是拿这个等式做强断言： 有读者时 compact 后 dirt > 0 且等于 pendingFreeCount；末位读者退出后双双归零。
💡 说明 compact 的 meta 语义：compact 本质是一次「只动元数据」的提交——root/entry_count/byte_size 原样搬运，sequence +1（meta 双页交替需要序列号单调，也顺带把水位推高一格）；free_head/free_count/last_page 填 0 只是占位，FilePageStore.writeMeta 会用实际值覆写（last_page = next_free-1）。 它不会收缩文件，也不等待读者——「等」的部分已由 reclaimPendingFree 按 watermark 增量消化。
⚠️ 注意 compact 不是 free 的对立面：名字容易让人以为 compact = 空间整理，实际它只是 「回收当前可回收的 + 写一版新 meta」。真正把页还回 freelist 的是 reclaimPendingFree / flushPendingFree；而 freelist 本身是页存储的内存簿记（尚未持久化——见第三部分的 free_head 讨论）。把 compact 理解成「一次不写数据的提交」更准确。
🔴 风险 长命读者的天花板仍在：watermark 机制让「短命读者先走」能立即回收，但一个真正长命的读者 （如长开的 Iterator）依然会把 release_seq >= 其快照的所有页钉到底——这是 MVCC 的本质代价，不是缺陷。 区别在于 T-30 之后 dirt 如实报告这个钉住量，运维可以据此判断「是有人在长读，还是泄漏了 endRead」。

第三部分applyBatch 写路径与持久化

前两部分讲清了「读」的一侧：MVCC 读者如何注册快照、dirty 页如何按 watermark 增量回收。这一部分进入 写的一侧——applyBatch 是 writer.zig 的核心写路径：把一批 Request 应用到 COW B-tree、提交 meta、按持久化级别落盘、再原子更新可见状态。整条路径是一条 9 步流水线，每一步都在为「正确性边界」与「性能」做取舍。

💡 说明 写路径的宏观图景：一次 applyBatch = 一次逻辑事务。 它先做「准入检查 + 机会性回收」（步骤 0），再对 B-tree 做一次批量 COW 改写（步骤 1–2）， 把改写挤出的旧页挂到 pending_free 等待 MVCC 安全回收（步骤 3）， 写 meta 并按 Durability 级别决定几次 fsync（步骤 4–6）， 最后原子翻转可见状态并唤醒所有 future（步骤 7–8）。步骤 9 再做一次机会性回收。

3.1 结构：Durability / Options / Request / ProfileStats

写路径的配置与输入由四个小结构承载，全部集中在文件头部：

Options写路径总配置fsync、micro_batch、durability 三个旋钮
MicroBatchConfig微批暂存配置batch_threshold：暂存上限，0 = 关闭（直接提交）
Request单个写请求key/value 切片 + tombstone 标记 + 一个 zio.Future

几个值得展开的点：

① Request.future —— 失败也必须交付。每个请求自带一个 zio.Future(OpResult)。applyBatch 的每条失败路径（closed、B-tree 错误） 都不会直接把错误抛给调用方了事，而是逐一 r.future.set(err) 把结果 「送达」给等待者；成功路径则在步骤 8 统一 req.future.set({})。这保证批量提交的 调用方（db 层的 group commit / 事务 future 聚合）无论成败都能被唤醒，不会悬挂。

if (self.closed.load(.acquire)) {
    for (batch) |r| r.future.set(error.Closed);
    return;
}

② Durability 的两级语义。这是 T-27 引入的持久化契约：

  • process_crash（默认）：提交协议 = writeMeta + 一次 sync。 在「进程崩溃但页缓存完好」的模型下安全且快——这是 bench 主战场的默认档。
  • power_fail：提交协议 = syncDataPages（数据页先落盘）→ writeMeta → sync（meta 落盘）。两次 sync 换掉电正确性：meta 到达稳定存储的那一刻， 它指向的数据页已经（最迟同时）落盘。单次 put 延迟约翻倍，摊到批里可接受。
⚠️ 注意 fsync=false 与 power_fail 的组合语义：fsync=false 只在 process_crash 下有意义（异步持久化，用户手动调 Db.sync()）； power_fail 档每次提交无条件双重 sync——源码中的条件是 if (self.opts.fsync or self.opts.durability == .power_fail)，即 power_fail 压过 fsync=false。

③ MicroBatchConfig —— 摊销的入口。db 层用 batch_threshold 把单条 put/delete 暂存成批再调 applyBatch，摊薄 COW + meta 写 + fsync 的固定开销。 writer.zig 本身不实现暂存逻辑，只吃「已经是批」的输入——分层清晰。

④ ProfileStats —— 编译期开关的分相计时（#35）。一组 pub var 全局计数器（dupe / order_detect / sort / dedup / insertBatch / pending_free / flush_free / meta+write， 外加 db 层的 staging / reqs / futures.wait），由 enable 布尔控制。生产热路径上 prof=false，全部计时点退化为一次布尔测试；profiling 工具设 ProfileStats.enable = true 后，applyBatch 内各阶段自动累计纳秒数， print() 输出每相占比与 ns/entry。

pub const ProfileStats = struct {
    pub var enable: bool = false;
    // Per-phase timings (ns) and call counts
    pub var txn_dupe_ns: u64 = 0;
    pub var txn_order_ns: u64 = 0;
    pub var txn_sort_ns: u64 = 0;
    pub var txn_dedup_ns: u64 = 0;
    pub var txn_insertbatch_ns: u64 = 0;
    // ... 以及 flush_free / meta / total / count / entries
    // db layer (staging/futures)
    pub var db_staging_ns: u64 = 0;
    pub var db_reqs_ns: u64 = 0;
    pub var db_futures_wait_ns: u64 = 0;

    pub fn print() void { /* 各相 ns、占比、ns/entry 汇总输出 */ }
};
💡 说明 为什么用全局 var 而不是字段：ProfileStats 是跨批聚合的 进程级统计，放进 State 会让每份状态各记一份、失去「全局视角」；而全局 pub var 让 profiling 工具从任意位置开关、读取。代价是非线程安全——但它的设计场景（单写者线程 + 工具线程只读打印） 本就允许这一点。Zig 惯用法：std.debug.print 直出，不引依赖。

3.2 applyBatch 流水线

先看全景。applyBatch 对 batch.len > 1 的输入走「order 检测 → 三条支路」， 单条输入走直插快路径：

0 grace-period 回收 → 1 快照 root/seq → 2 arena + B-tree 改写 → 3 pending_free 入队 → 4-5 算 meta + 写 meta → 6 fsync → 7 原子状态更新 → 8 future 唤醒 → 9 机会性回收

步骤 0 · grace-period 回收。进入写路径第一件事：如果此刻 reader_count == 0，说明历史上积累的 dirty 页已无任何读者持有——直接 flushPendingFree() 全量回收。这是「宽限期」语义：写者每批开始前顺手清理上一批留下的垃圾， 不留给专门的回收线程。注意它与读者 endRead 的回收通过 pending_free_mu 互斥——pending_free 是一个普通 ArrayList，并发变更必须串行化。

步骤 1 · 快照。读取当前 root / sequence / entry_count / byte_size 四个原子值作为本批的基线。整批的改写与记账都基于这份快照，最后一步再原子地翻转出去—— 这就是「提交」的本质。

步骤 2 · arena + B-tree 改写（核心）。先建一个 ArenaAllocator 承载整批临时分配（key/value 拷贝、Leaf/Branch 解码）：

// 2. Arena for COW path temporary allocations (key/value dupe, Leaf/Branch decode).
// Eliminates per-allocation syscall overhead: ~145 alloc/free per btree.insert
// collapses to arena bump-pointer, freed in one shot at batch end.
var arena = std.heap.ArenaAllocator.init(self.allocator);
defer arena.deinit();
const arena_alloc = arena.allocator();
✅ 提示 arena 的收益量级：一次 btree.insert 内部约 145 次 alloc/free；换成 arena 后全部退化为 bump-pointer 递增，批结束时一次性释放。 对万级 entry 的批，这是「每条 145 次分配器往返」与「整批一次释放」的差别。

然后按输入形状分三条支路。单条快路径直接调 btree.insert， 省掉 sort/dupe/insertBatch 的全部准备开销。多条则先做一遍 O(n) 的 order 检测——扫描相邻 key 的比较结果，归为三档：

const Order = enum { strict, non_dec, unordered };
const order = blk: {
    if (batch.len <= 1) break :blk Order.strict;
    var has_dup = false;
    for (1..batch.len) |i| {
        switch (btree.cmpKey(batch[i - 1].key, batch[i].key)) {
            .lt => {},
            .eq => has_dup = true,
            .gt => break :blk Order.unordered,
        }
    }
    break :blk if (has_dup) Order.non_dec else Order.strict;
};
  • strict / non_dec（有序输入）：跳过 dupe 与 sort，arena_entries 直接引用调用方的切片（零拷贝），再走一遍 O(n) 相邻去重（last write wins），然后 btree.insertBatch。
  • unordered（乱序输入）：先把所有 key/value 打进一块连续 arena 缓冲 （单次分配 + memcpy），再排序——排序读写的是 cache 热的连续内存；排序后同样相邻去重， 最后 insertBatch。
💡 说明 order 检测为何值得：一趟 O(n) 邻对比较的成本远低于 「盲目 sort」。真实负载里顺序 put（自增 key）与有序批是常态，strict 支路省掉的是整个 dupe+sort 阶段；连「有序但带重复」（non_dec）也能只花一遍 O(n) 去重。只有真正乱序才付 O(n log n) 的排序税——而且是对连续内存排序。
⚠️ 注意 调用方切片可能不长寿：注释明言 「caller slices may not survive — e.g. stack buffer reuse」。因此只有检测出有序输入时 才直接引用调用方切片（本函数同步完成，切片在批处理期间存活）；乱序路径则必须先 memcpy 进 arena 自有缓冲再排序——排序过程中切片内容不能被外部复用踩掉。

步骤 3 · pending_free 入队。本批 COW 挤出的旧页（batch_dirty） 不立即回收——可能有活跃读者还引用着旧树。它们带着「释放序列」进入 pending_free：

{
    self.pending_free_mu.lockUncancelable();
    defer self.pending_free_mu.unlock();
    for (batch_dirty.items) |pn| {
        // T-30: carry the release sequence (this commit's
        // new_sequence = cur_sequence+1). The page belongs to the
        // tree as of cur_sequence; readers with snapshot >=
        // new_sequence cannot reference it.
        self.pending_free.append(self.allocator, .{ .page_no = pn,
            .release_seq = cur_sequence + 1 }) catch {};
    }
    // T-30: dirt is updated under the lock together with the append
    self.dirt.store(@intCast(self.pending_free.items.len), .release);
}

两个细节：release_seq = cur_sequence + 1（本提交的 new_sequence）—— 快照 ≥ new_sequence 的读者不可能引用此页（它在 new_sequence 提交后已不在树中），这正是第一部分 watermark 回收判据的数据来源；dirt 的更新移进了锁内——旧版在步骤 7 无锁 store，会覆盖读者线程增量回收刚写入的结果（修复回顾：锁内 append 与锁内 store 原子成对）。

步骤 4–5 · meta 计算与写入。新 entry_count / byte_size 由快照值加本批 delta（可为负，delete 场景），@max(..., 0) 钳到非负后写入 MetaPage：sequence = cur_sequence + 1、root_page = new_root。 meta 的交替写（meta0/meta1）由 store 层完成。

步骤 6–9 · 收尾。按持久化级别 sync（见 3.3）；然后四个原子 .release store 一次性翻转可见状态（root/sequence/entry_count/byte_size）； 所有 future 设成功；最后再看一眼 reader_count——为 0 则本批 dirty 立即回收。 注意步骤 0 与步骤 9 是同一判断的两次机会：批开始前与批结束后各一次。

✅ 提示 「先写数据页、后翻 root」的可见性语义：新页 （batch_dirty 中的 COW 新页）在步骤 3–5 期间已全部落盘，但读者仍看旧 root——直到步骤 7 的 release store。任何时刻拿到 root 快照的读者，看到的都是一棵完整一致的树：要么全旧、要么全新。 这是 COW + 原子指针翻转的经典提交协议。

3.3 持久化顺序与设计取舍

步骤 5 与 6 之间藏着 T-27 的核心——提交顺序契约：

// T-27 commit ordering: under power_fail, flush this batch's data
// pages to stable storage (fdatasync semantics) before writing meta,
// guaranteeing that at the moment the meta commit becomes durable,
// the data pages it points to have already landed (or land at the
// latest simultaneously) — power loss can never recover a root
// pointing at dangling pages.
if (self.opts.durability == .power_fail) {
    try self.store.syncDataPages();
}
try self.store.writeMeta(&meta);

// 6. fsync (meta to disk)
if (self.opts.fsync or self.opts.durability == .power_fail) {
    try self.store.sync();
}
COW 写新数据页 → syncDataPages（仅 power_fail） → writeMeta（交替 meta 页） → sync（meta 落盘）

为什么这个顺序是掉电正确的？关键在于恢复时读的是 meta。崩溃恢复 = 读 meta → 拿到 root_page → 沿 root 读树。如果 meta 先于数据页落盘，掉电后可能恢复出一个指向 「还没落盘的新页」的 root——悬空页，整库不可读。反过来，只要保证 meta 落盘时它指向的数据页 已在稳定存储，恢复出的树就一定完整：syncDataPages → writeMeta → sync 正是把「数据页先落盘」做成了字节级的先后。

🚨 风险 process_crash 档不承诺掉电安全：默认档的 提交协议是 writeMeta + 一次 sync——在「进程崩溃、OS 页缓存完好」的模型下正确 （崩溃后另一个进程 reopen，页缓存里的数据页仍然可见）；但真掉电时数据页可能在 meta 之后 才落盘，恢复可能拿到悬空 root。这是明确的取舍而非疏漏：默认档为 bench 主战场 换速度，需要掉电正确性的用户显式选 .power_fail。

这套顺序契约由 durability_order_test.zig 用一个 RecordingStore （vtable 桩）钉死：power_fail 档断言每个 write_meta 之前都有一次 sync_data、之后恰有一次 sync；process_crash 档断言没有前置 syncDataPages 且仅一次 sync。

最后把整条写路径的取舍表收拢：

决策点选择代价 / 边界
