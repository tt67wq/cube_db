cube_db · commit a3283b2 讲义：多进程打开防护

T-34 —— FilePageStore.init 加 flock 排他锁，同一数据库文件同时只允许一个打开者
Zig 0.16 flock advisory lock TDD 崩溃安全

本讲义由开发团队协作生成，讲解 commit a3283b2（T-34：多进程打开防护）的动机、flock 实现、 语义边界与 TDD 测试过程。代码块附逐行解释。

第一部分问题与动机：为什么需要一个进程锁

cube_db 是单进程写入数据库：FilePageStore 用 O_RDWR | O_CREAT 打开数据库文件， 再 mmap MAP_SHARED 出 1TB 预留区。此前 `init` 没有任何跨进程互斥——两个进程并发打开 同一路径，各自拿到独立的 open file description（OFD）与内存池副本，交叉写 meta 与 freelist， 最终静默损坏数据。

1.1 为什么需要"多进程打开防护"

要防的威胁：两个写者同时写一个文件。

  • 每个打开者独立 mmap。 MAP_SHARED 让两个进程各自映射到同一文件，但各自维护 进程内的 meta0/meta1 缓冲、next_free、freelist——彼此不可见。
  • 页号对撞。 两个进程各自 bump 分配，可能分到同一页号，互相覆盖对方刚写的数据。
  • meta 槽互踩。 双页交替写的崩溃安全机制假设只有一位写者；两个写者会让 sequence 判活与 next_free 恢复全部错乱。
🔴 危险 为什么是"静默"损坏：并发写不会立即报错——两次写入都"成功"， 到 reopen 时 CRC 校验往往仍能通过（两进程写的是完整页），只是内容互相覆盖，读出来的是错乱数据。 这种损坏必然而非概率性：只要两个写者都真正写盘，冲突就一定会发生。

1.2 并发打开如何静默损坏数据

进程 A open + mmap → 进程 B open + mmap（各自 OFD / 各自缓冲） → A 写 meta0、B 也写 meta0 → 页号对撞、freelist 链互相覆盖 → reopen 读到错乱数据（CRC 仍可能通过）
⚠️ 注意 T-33 放大了损坏面：T-33（freelist 持久化）把 freelist 链写到磁盘上。 T-34 之前，freelist 只在内存里，两进程并发写最多互相覆盖数据页；T-33 之后，freelist 链本身也落盘， 两个写者会破坏链式结构——损坏从"数据错乱"升级为"结构损坏"，reopen 恢复 freelist 时可能读到断裂的链。

1.3 为什么选 flock（advisory 排他锁）

方案对比与取舍：

方案是否选用理由
flock(fd, LOCK_EX | LOCK_NB)✅ 选用~20 行；锁绑定 OFD，最后一个 fd 关闭即释放（含崩溃）；fork 继承不自杀冲突
fcntl POSIX record lock否语义复杂（按进程、fork 后子进程锁行为特殊）；本库只需整文件排他
单独锁文件 + 原子创建否锁文件残留处理繁琐，崩溃清理不可靠
进程内单例 / 环境变量否只防同进程，防不了跨进程

第一部分小结：init 当前打开文件的方式让"第二个写者"能合法进入，造成必然而静默的损坏。 选 flock 是因为它是"误用即损坏"这一全项目唯一入口的最低成本堵漏手段，且崩溃时自动释放、无需清理。

第二部分init 加锁实现

T-34 的核心改动集中在 FilePageStore.init：open 成功后立即取 advisory 排他锁， 先于任何 fstat/ftruncate/mmap 副作用。锁失败时关闭 fd 并按 errno 区分返回 error.FileLocked 或 error.OpenFailed。

2.1 @cInclude errno.h

const c = @cImport({
    @cInclude("sys/mman.h");
    @cInclude("sys/stat.h");
    @cInclude("fcntl.h");
    @cInclude("unistd.h");
    @cInclude("errno.h"); // T-34: EWOULDBLOCK/EAGAIN for the flock error path
});

新增 @cInclude("errno.h") 以使用 EWOULDBLOCK/EAGAIN 两个 errno 常量。 在 macOS 上二者同值（均等于 35）；Linux 上 EWOULDBLOCK 与 EAGAIN 也同值。实现里双检 是为了可移植性——不同平台/实现可能分别使用其一，同时判断最稳妥。

2.2 open 后立即 flock

    const fd = c.open(path_z, @as(c_int, c.O_RDWR | c.O_CREAT), @as(c.mode_t, 0o644));
    if (fd < 0) return error.OpenFailed;

    // T-34: advisory exclusive lock — one writer process per file.
    // flock binds to the open file description: a second open (any process,
    // or the same process via a different fd) fails with EWOULDBLOCK.
    if (c.flock(fd, c.LOCK_EX | c.LOCK_NB) != 0) {
        const errno: *c_int = std.c._errno();
        if (errno.* == c.EWOULDBLOCK or errno.* == c.EAGAIN) {
            _ = c.close(fd);
            return error.FileLocked;
        }
        // other flock failures (EBADF/EINTR/ENOLCK...): treat as open failure
        _ = c.close(fd);
        return error.OpenFailed;
    }
open(O_RDWR|O_CREAT, 0644) → flock(fd, LOCK_EX | LOCK_NB) → 0 继续 fstat/ftruncate/mmap → 非 0 读 errno 分流 → EWOULDBLOCK/EAGAIN close + error.FileLocked → 其他 close + error.OpenFailed
💡 说明 为什么"立即"加锁：在 open 成功、尚未做任何 fstat/ftruncate/ mmap 副作用之前取锁。若先 mmap 再发现被锁，就必须处理"已映射区的释放"；现在锁失败直接 close(fd) 返回，不留半初始化状态。这也让锁语义与"打开即独占"完全一致。

2.3 错误路径：EWOULDBLOCK / EAGAIN → error.FileLocked

        const errno: *c_int = std.c._errno();
        if (errno.* == c.EWOULDBLOCK or errno.* == c.EAGAIN) {
            _ = c.close(fd);
            return error.FileLocked;
        }

LOCK_NB（non-blocking）保证 flock 在锁被占用时立即返回失败而不是阻塞等待。 此时 errno 为 EWOULDBLOCK（或同值的 EAGAIN）。实现先关 fd（避免泄漏）， 再返回新错误 error.FileLocked——调用方可用 catch |err| switch (err) { error.FileLocked => ... } 识别"文件正被他人打开"。

✅ 提示 EWOULDBLOCK/EAGAIN 双检：评审 note 指出两者同值，双检冗余但无害。 保留双检是为了表达意图（涵盖不同平台各自偏好的写法），并保持可移植性，不构成问题。

2.4 其他 flock 错误 → error.OpenFailed

        // other flock failures (EBADF/EINTR/ENOLCK...): treat as open failure
        _ = c.close(fd);
        return error.OpenFailed;
    }

除 EWOULDBLOCK/EAGAIN 之外的 flock 失败（EBADF、EINTR、ENOLCK、 EINVAL 等）统一当作打开失败处理：关 fd 后返回 error.OpenFailed。这些错误多是环境/参数异常， 不是"文件被占用"，因此不返回 FileLocked，避免调用方误判。

2.5 deinit 零改动：锁随 OFD 释放

T-34 对 deinit 零改动——这是 flock 绑定 OFD 带来的天然好处：

pub fn deinit(self: *FilePageStore) void {
    _ = c.munmap(@ptrCast(self.mmap_ptr), REGION_SIZE);
    _ = c.close(self.fd);
    self.freelist.deinit(self.allocator);
}
✅ 提示 锁的生命周期由 OFD 决定：flock 加在文件描述符（更准确说，该 OFD）上。 deinit 的 c.close(self.fd) 关闭最后一个引用该 OFD 的 fd，内核即释放锁——无需显式 flock(fd, LOCK_UN)。同理，进程崩溃或被 kill -9 时内核回收 fd，锁自动蒸发，无死锁残留。

第二部分小结：加锁逻辑只有约 19 行，插在 open 与 fstat 之间；错误路径都先 close(fd) 再返回，避免 fd 泄漏；锁的释放完全依赖内核的 OFD 关闭语义，因此 deinit 与崩溃路径都不需要额外处理。

第三部分语义与边界

理解 flock 的正确用法，关键在于认清它的锁粒度是 open file description（OFD）而非进程或线程。 这一节厘清由此推出的几个重要语义，以及 fork / 崩溃 / NFS 下的边界行为。

3.1 锁的粒度：open file description

flock 的关键事实：

  • 锁挂在 OFD 上，不是挂在内核线程或进程上。
  • 同一 OFD 的所有 fd 共享这把锁（dup、fork 继承的 fd 属于同一 OFD）。
  • 第二个独立的 OFD（另一个进程、或同进程另开一个 fd）来抢锁时，因 LOCK_NB 立即失败。
⚠️ 注意 同进程第二 fd 也会冲突：测试 A1 专门验证了这一点——在同一进程内对同一路径 再 init 一次（第二个 fd = 第二个 OFD），同样返回 error.FileLocked。这不是"多余"， 而是与跨进程行为一致的正确边界：任何"第二个打开者"都被拒。

3.2 fork 子进程的 OFD 继承

// fork'd children inheriting this fd share the OFD and never self-conflict;
// the lock releases when the LAST fd of the OFD closes (deinit's c.close
// suffices, crash included).

fork 的子进程继承父进程的 fd，这些 fd 与父进程的 fd 指向同一 OFD，因此它们共享同一把锁、 不会自冲突。真正需要防的是"子进程自己重新 open 同一路径"——那会产生新的 OFD，被当作第二个 打开者拒绝（测试 A1-fork 验证了这一行为）。

3.3 崩溃 / kill -9 无死锁残留

持有者崩溃 / 被 kill -9 → 内核回收该进程所有 fd → OFD 最后一个 fd 关闭 → flock 自动释放 → 他人可立即重新打开

这是 flock 相比"锁文件"方案的核心优势：无需清理残留锁文件。测试 A3 用一个 fork 出的子进程持锁， 父进程 kill -9 后验证 waitpid 确认被 SIGKILL 终止、再重新打开成功——证明锁随进程消亡释放。

3.4 NFS 等网络文件系统边界

🔴 危险 NFS 上 flock 语义不保证：flock 在本地文件系统（ext4、APFS、btrfs、tmpfs 等） 语义可靠；但在 NFS 及其他网络文件系统上，flock 的跨主机互斥不被保证。文档（usage.md / usage.en.md）明确声明 仅支持本地文件系统。若部署在 NFS 上，此防护可能失效——这是已知边界，不是 bug。

第三部分小结：锁粒度是 OFD；fork 继承共享不自杀冲突、同进程第二 fd 也算第二打开者； 崩溃由内核自动释放；NFS 等网络文件系统是明确声明的不支持边界。

4.2 A1 / A2：进程内双 OFD

test "filelock A1: second concurrent open of the same path returns error.FileLocked" {
    const path = ".test_filelock_a1.db";
    defer unlinkPath(path);

    var a = try FilePageStore.init(alloc, path);
    defer a.deinit();

    var second = FilePageStore.init(alloc, path) catch |err| {
        try std.testing.expectEqual(error.FileLocked, err);
        return;
    };
    // RED on main: control reaches here — second open had no lock at all.
    second.deinit();
    return error.TestUnexpectedResult;
}

A1 先在 a 持锁的前提下对同一路径再 init 一次。若被拒且错误恰为 FileLocked， 测试通过。若 init 成功（RED 状态），控制流落入清理 + return error.TestUnexpectedResult 使测试失败。A2 则先显式 a.deinit() 再重开，验证锁已释放。

4.3 A1-fork：真实跨进程

    const pid = c.fork();
    if (pid < 0) return error.ForkFailed;
    if (pid == 0) {
        // Child: fresh open → fresh OFD. Post-GREEN this must hit the flock held
        // by the parent's (inherited but unused) fd.
        var s = FilePageStore.init(std.heap.page_allocator, pz) catch |err| {
            c._exit(if (err == error.FileLocked) exit_got_lock else exit_other);
        };
        s.deinit();
        c._exit(exit_opened);
    }
    // parent: waitpid 后检查子进程退出码
    try std.testing.expectEqual(exit_got_lock, code);

父进程持锁（a），fork 出子进程；子进程用 page_allocator 对同一路径重新 open （新的 OFD），应命中父进程持的锁。子进程以退出码传达判定：42=FileLocked（期望）、7=意外打开成功、 3=其他错误。父进程 waitpid 校验退出码。这样即使子进程崩溃，父进程也能根据退出码/信号正确断言。 子进程只用 page_allocator（不用 std.testing.allocator），避免共享 testing allocator 内部状态。

4.4 A3：kill -9 后锁释放

    // Pipe: 子进程 init 成功后写一个字节，父进程据此确认锁已持有再 kill
    ...
    // SIGKILL the holder: the kernel closes its fds, the flock must evaporate.
    _ = c.kill(pid, c.SIGKILL);
    ...
    try std.testing.expectEqual(@as(c_int, c.SIGKILL), status & 0x7f);
    // The parent held nothing; the sole holder is dead. Reopen must succeed.
    var b = try FilePageStore.init(alloc, pz);
    b.deinit();

用 pipe 做同步：子进程 init 成功（持锁）后向 pipe 写一字节，父进程读到该字节才确定锁已持有， 再 kill -9。随后 waitpid 确认子进程确被 SIGKILL 终止，父进程（此间未持锁）重新 init 必须成功——证明崩溃后被锁自动释放。

4.6 风险清单与设计总结

风险 / 边界说明缓解
NFS / 网络文件系统flock 跨主机互斥不保证文档声明仅支持本地文件系统
同进程第二 fd 误伤同进程再 open 也被拒（锁粒度是 OFD）符合"单打开者"契约，A1 固定
fork 后子进程自开子进程重新 open 同一路径被拒A1-fork 固定；继承 fd 共享不冲突
崩溃残留持有者崩溃/kill -9内核关 fd 自动释放，A3 固定
deinit 前未 commit锁与持久化无关锁只防并发打开，不替 sync 语义

设计亮点：

  1. 最低成本堵住"误用即损坏"入口：~19 行，插在 open 与副作用之间，先锁后初始化。
  2. 锁随 OFD 生命周期自动管理：deinit 零改动、崩溃自动释放、无死锁残留、无需清理锁文件。
  3. 错误语义清晰：EWOULDBLOCK/EAGAIN → FileLocked（可识别"被占用"）， 其他 → OpenFailed（环境异常）。
  4. TDD 三方法：A1/A1-fork 钉住正向契约，A2/A3 钉住"不误伤正常流程"的反向契约。

T-34 用一把 advisory 排他锁，堵住了 cube_db 唯一"误用即静默损坏"的入口。理解 flock 绑定 OFD 的语义，是读懂这个提交的关键——锁的加、释、fork 继承与崩溃自动释放，全都从这一条语义推出，因此 实现才能如此简洁、deinit 才能零改动。
