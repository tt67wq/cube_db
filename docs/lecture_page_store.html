第一部分PageStore 抽象层与 VTable 多态接口

src/page_store.zig 的前半部分定义了整个存储引擎的多态入口：PageStore 结构体。 它是 B-tree（btree.zig）、数据库门面（db.zig）与底层实现（内存版 MemPageStore、 mmap 文件版 FilePageStore）之间的契约。本部分逐段精讲它的常量、错误集、VTable 形状， 以及每个方法背后的设计取舍。

1.1 文件定位与依赖

//! page_store.zig — 页 Store 接口（vtable）及内存实现（MemPageStore）。
//! 生产级 FilePageStore（mmap）后续实现；MemPageStore 用于测试。
const std = @import("std");
const f2 = @import("format.zig");
const zio = @import("zio");

三个导入对应三个关注面：std 是标准库（分配器、切片、测试）；f2（format.zig） 提供页格式常量与 MetaPage 编解码——它是纯函数模块，page_store.zig 只复用其类型， 不触碰它的实现细节；zio 提供跨平台同步原语（Mutex），内存实现用它串行化页池访问。

分层意图：本文件同时承载「接口」与「一个具体实现（内存版）」。 接口（PageStore + VTable）是稳定契约，实现可替换——这是后续 FilePageStore 能无缝接入的前提。接口与第一个实现同文件，避免空接口先行抽象。

1.2 常量与错误集

/// 数据页起始页号（0=NULL，1=meta0，2=meta1）
pub const FIRST_DATA_PAGE: u32 = 3;

/// 错误
pub const Error = error{
    MapFull,
    PageNotFound,
};

页号空间是全局约定：0 是 NULL 页（哨兵），1/2 是双 meta 页（交替写以做崩溃恢复）， 3 起是数据页。FIRST_DATA_PAGE 把这个约定固化成常量，MemPageStore.init 用它初始化 next_free，确保 bump 分配器跳过保留页。

页号含义谁管理
0NULL_PAGE（哨兵，表「无后续页」）format.zig 常量
1META_PAGE_0（meta 副本 A）readMeta/writeMeta
2META_PAGE_1（meta 副本 B）readMeta/writeMeta
≥3数据页（branch/leaf/overflow）allocPage/freePage

错误集只有两条，都由分配/读取路径产生：MapFull 表示页号空间耗尽（达到 max_pages， mmap 版对应文件区满）；PageNotFound 表示读一个未分配过的页号。注意它们是 anyerror 体系之外的具名错误，但 VTable 方法签名用 anyerror!T，因此任一具体错误都能透传。

1.3 PageStore 结构与 VTable

/// 页 Store 运行时多态接口
pub const PageStore = struct {
    ptr: *anyopaque,
    vtable: *const VTable,

    pub const VTable = struct {
        allocPage: *const fn (ptr: *anyopaque) anyerror!u32,
        freePage:  *const fn (ptr: *anyopaque, page_no: u32) void,
        readPage:  *const fn (ptr: *anyopaque, page_no: u32) anyerror![]const u8,
        writePage: *const fn (ptr: *anyopaque, page_no: u32) anyerror![]u8,
        readMeta:  *const fn (ptr: *anyopaque) anyerror!?f2.MetaPage,
        writeMeta: *const fn (ptr: *anyopaque, meta: *const f2.MetaPage) anyerror!void,
        sync:      *const fn (ptr: *anyopaque) anyerror!void,
        mapsize:   *const fn (ptr: *anyopaque) u64,
    };

PageStore 是经典的两字段 vtable 模式：ptr 是不透明指针（指向具体实现，如 *MemPageStore），vtable 是指向函数指针表的指针。值类型 PageStore 本身是可拷贝的 （一个指针 + 一个指针），在调用栈/结构体字段间传递零开销。PageStore 不拥有 ptr 的生命周期—— 调用方保证实现存活期长于所有借用。

为什么不用 Zig 接口（iface）/trait？Zig 0.14 没有内置 trait 系统， *anyopaque + 函数指针表是社区惯用的「手写 vtable」模式，与 C ABI 友好、 无隐藏分配、可跨实现复用同一份调用胶水。代价是每个实现要手写 8 个 vtXxx 转发函数—— 但每个函数体都是 @ptrCast @alignCast + 转调一行，模板化、低风险。

1.4 八个虚方法逐个拆解

方法签名语义与设计点
allocPage () !u32 分配一页，返页号。优先从 freelist 回收链取（LIFO，局部性好），退路是 bump next_free。 不返页数据——调用方拿到页号后再用 writePage 取可写切片。这是 COW B-tree 写路径的关键： 先 copy-on-write 分配新页号，再把旧页内容拷进去改。
freePage (page_no) void 回收页号入 freelist。不释放页数据（内存版页地址稳定要复用，mmap 版页就是文件区段）。 不报错——回收一个未分配的页是调用方 bug，但接口选择静默吞掉以简化 COW 回滚路径。
readPage (page_no) ![]const u8 返只读切片，零拷贝。内存版直接借页指针 [0..]；mmap 版借 mmap 区指针。 切片生命期绑定到实现（页不被重写/释放前有效）。B-tree 读路径 getBorrowed 依赖此零拷贝。
writePage (page_no) ![]u8 返可写切片。可能触发 ensurePage（内存版按需堆分配新页）。注意是「按页号取可写缓冲」， 不是「写入数据」——调用方拿到切片自己 memcpy。
readMeta () !?MetaPage 读双 meta 页，返合法者（或 null 表空库）。委托 f2.readMetaPage(&meta0,&meta1) 做交替恢复：校验 CRC + 比对 sequence 取较新合法者。崩溃恢复的核心。
writeMeta (*const MetaPage) !void 交替写 meta0/meta1（meta_index 翻转 0↔1）。写完再翻 index， 保证任一时刻总有一份合法旧 meta，崩溃后 readMeta 仍能恢复到上一致点。
sync () !void 刷盘（fsync）。内存版是空操作；mmap 版 msync(MS_SYNC)。 事务提交时由 db.zig 调用，保证 meta 写入落盘后才算提交。
mapsize () u64 页数上限。内存版返 max_pages；mmap 版返预留区页数。供 allocPage 判 MapFull，也供上层预算容量。

1.5 转发胶水方法

    pub fn allocPage(self: PageStore) !u32 {
        return self.vtable.allocPage(self.ptr);
    }
    pub fn freePage(self: PageStore, page_no: u32) void {
        self.vtable.freePage(self.ptr, page_no);
    }
    // ... readPage / writePage / readMeta / writeMeta / sync / mapsize 同形
    pub fn mapsize(self: PageStore) u64 {
        return self.vtable.mapsize(self.ptr);
    }

这 8 个公共方法是「语法糖」：把 store.vtable.fn(store.ptr, args...) 折叠成 store.fn(args...)。调用方（btree.zig、db.zig）只见 PageStore 值类型， 不直接碰 vtable/ptr——实现可替换性就建立在这一层间接上。每个方法体单行透传， 编译期内联后零额外开销。

零拷贝借用的生命期陷阱：readPage 返的 []const u8 借自实现内部缓冲。 调用方必须确保在下次可能重写/扩容该页的操作前用完。内存版刻意把页做成独立堆分配（地址稳定） 以缓解此问题（详见第二部分）；mmap 版则因整个区是固定映射、页地址永不变而天然安全。 B-tree 写路径在分配新页前先把旧页内容拷到栈缓冲，正是为了避免「allocPage 扩容导致借用切片悬垂」。

1.6 调用方如何拿到一个 PageStore

接口侧只定义了形状，具体实现的实例化由各实现自己提供。以内存版为例（完整实现见第二部分）：

pub const MemPageStore = struct {
    // ... 字段略
    pub fn store(self: *MemPageStore) PageStore {
        return .{ .ptr = self, .vtable = &mem_vtable };
    }
};

const mem_vtable: PageStore.VTable = .{
    .allocPage  = MemPageStore.vtAllocPage,
    .freePage   = MemPageStore.vtFreePage,
    .readPage   = MemPageStore.vtReadPage,
    .writePage  = MemPageStore.vtWritePage,
    .readMeta   = MemPageStore.vtReadMeta,
    .writeMeta  = MemPageStore.vtWriteMeta,
    .sync       = MemPageStore.vtSync,
    .mapsize    = MemPageStore.vtMapSize,
};

store() 把 *MemPageStore 装箱成 PageStore：ptr 指向自实例， vtable 指向静态 mem_vtable。mem_vtable 是编译期常量结构体字面量，8 个槽各绑一个 vtXxx 转发函数。调用 s.allocPage() 最终落到 MemPageStore.vtAllocPage(ptr) → @ptrCast @alignCast(ptr) → 真实方法。

1.7 上层如何使用这个接口

btree.zig 的所有 I/O 都只持有 PageStore（按值传递），对底下是内存还是 mmap 无感知：

// btree.zig
const PageStore = ps.PageStore;

pub fn readNodePayload(store: PageStore, page_no: u32) ![]const u8 {
    return store.readPage(page_no);  // 零拷贝借用
}

pub fn writeNodePage(store: PageStore, page_no: u32, ...) !void {
    const page = try store.writePage(page_no);  // 取可写切片
    // memcpy 节点数据进 page ...
}

db.zig 在打开库时用 readMeta 恢复状态，提交时用 writeMeta + sync 落盘：

// db.zig: open
if (try store.readMeta()) |meta| {
    // 恢复 root_page / sequence / freelist ...
}
// db.zig: commit
try self.store.writeMeta(&meta);
try self.store.sync();  // 内存版 no-op，mmap 版 msync

1.8 设计取舍小结

  • 接口与首实现同文件：避免空接口先行抽象。接口有了，马上跟一个内存实现验证形状可用，再上 mmap 版。
  • 页号作分配句柄，不返页数据：allocPage 只返 u32。写者随后 writePage 取缓冲， 读者 readPage 借切片。这样分配与读写解耦，COW B-tree 可「分配→拷旧页→改→原子提交」。
  • 零拷贝借用：readPage 不拷数据。性能靠此，但把生命期管理责任下放到实现（页地址要稳定）和调用方（用完前别重写）。
  • 双 meta 交替写：readMeta/writeMeta 把崩溃恢复下沉到接口层，上层不用关心 meta0 还是 meta1 合法。
  • anyerror 透传：虚方法用 anyerror!T，实现可抛任意错误（MapFull、OutOfMemory、PageNotFound），不需为每种实现定义并集错误集。
  • sync 进接口：把「持久化」作为一等公民。内存版空实现仍要提供，保证调用方代码在两种实现下一致。
风险点：vtable 是 *const VTable（指针），实现侧 mem_vtable 必须是静态/全局存储 （这里用文件级 const，进只读段，安全）。若误把它放成栈局部变量再取地址装箱，store() 返回后 vtable 即成悬垂指针。当前实现正确，但新增实现时须保持「vtable 是编译期常量」这一不变量。

第一部分到此。下一部分（第二部分）讲解 MemPageStore 的具体实现：slab 页池、freelist、互斥锁、 以及为修复并发写者借用悬垂而引入的独立堆分配策略。

第二部分MemPageStore 内存实现

上一部分讲解了 PageStore 抽象层与 VTable 多态接口。本部分聚焦其内存实现 MemPageStore——一个不持久化、专用于测试的页 Store。它完整实现了 VTable 的全部 七个方法，是我们理解"一个页 Store 需要做什么"的最小可运行范例，也浓缩了生产级 FilePageStore（mmap）将复用的核心设计：slab 页池、freelist 回收、互斥锁、meta 双页 交替写，以及 ensurePage 的部分失败回滚。

定位：MemPageStore 是"内存里的页仓库"。每个页是一块独立的 4096 字节堆分配， 按页号索引。它不落盘、不跨进程，生命周期随进程结束。但它精确模拟了真实页 Store 的分配/回收/读写 语义，因此被 page_store_test.zig 及上层 B-tree 测试大量使用。

结构体与关键字段

先看 MemPageStore 的字段定义，每个字段都对应一个设计决策：

pub const MemPageStore = struct {
    allocator: std.mem.Allocator,
    // slab 页池：按页号索引的页指针数组
    pages: std.ArrayList(*[f2.PAGE_SIZE]u8),
    freelist: std.ArrayList(u32),
    // pages/freelist 互斥锁
    freelist_mu: zio.Mutex,
    next_free: u32,
    max_pages: u32,
    meta0: [f2.PAGE_SIZE]u8,
    meta1: [f2.PAGE_SIZE]u8,
    meta_index: u32,
};
字段类型作用
pagesArrayList(*[PAGE_SIZE]u8)slab 页池：页号 → 页指针。指针数组可扩容移动，但每页是独立堆分配，页数据地址稳定
freelistArrayList(u32)已回收页号栈（LIFO），allocPage 优先从中取
freelist_muzio.Mutex串行化 pages/freelist 的所有读写访问
next_freeu32bump 分配游标，初始值 FIRST_DATA_PAGE = 3
max_pagesu32页数上限（对应 mapsize），超限返回 MapFull
meta0 / meta1[PAGE_SIZE]u8两个 meta 页的独立缓冲区，交替写入实现 crash 安全
meta_indexu32下次写哪个 meta（0 或 1），写后翻转

设计要点：为什么每页独立堆分配？

核心设计：pages 是 ArrayList(*[PAGE_SIZE]u8)——存的是指针而非内联页数据。 ArrayList 扩容时会整体搬移元素（指针移动），但每页的堆分配地址不变。这意味着读者通过 readPage 拿到的 []const u8 借用切片，即使在 unlock 后另一个写者 allocPage 触发了 pages 扩容，切片指向的页数据地址仍然有效，不会悬垂。

修复的历史 bug：若 pages 直接存内联页（ArrayList([PAGE_SIZE]u8)）， 扩容会整体搬移所有页数据，此时已借出的切片立即悬垂 → 并发读写下 SEGV。改为存指针是刻意的修复， 代码注释明确标注了这一点。这是"地址稳定性优先于访问局部性"的典型取舍。

init / deinit / store

init 初始化各字段，页按需在 ensurePage 中分配（不在 init 预分配）， next_free 从 FIRST_DATA_PAGE = 3 起步，保留页号 0（NULL）、1（meta0）、2（meta1）。

pub fn init(allocator: std.mem.Allocator, mapsize_pages: u32) MemPageStore {
    const self: MemPageStore = .{
        .allocator = allocator,
        .pages = .empty,
        .freelist = .empty,
        .freelist_mu = .{},
        .next_free = FIRST_DATA_PAGE, // = 3
        .max_pages = mapsize_pages,
        .meta0 = [_]u8{0} ** f2.PAGE_SIZE,
        .meta1 = [_]u8{0} ** f2.PAGE_SIZE,
        .meta_index = 0,
    };
    return self;
}

deinit 遍历 pages 逐个 destroy 每页的堆分配，再释放两个 ArrayList。 注意这里 ensurePage 的回滚正确性至关重要——若回滚不彻底，pages 中可能残留 undefined 指针，deinit 的 destroy 会解引用垃圾地址（见下文 F1）。

pub fn deinit(self: *MemPageStore) void {
    for (self.pages.items) |p| self.allocator.destroy(p);
    self.pages.deinit(self.allocator);
    self.freelist.deinit(self.allocator);
}

pub fn store(self: *MemPageStore) PageStore {
    return .{ .ptr = self, .vtable = &mem_vtable };
}

store() 构造 PageStore 多态句柄：ptr 指向自身，vtable 指向 模块级 mem_vtable 常量。上层代码拿到 PageStore 后即可通过统一接口操作，无需知道底层是内存还是文件实现。

ensurePage：按需分配页 + 部分失败回滚

ensurePage(index) 是 slab 页池的扩容核心，确保 pages 数组覆盖到 index。 若 index 已在范围内直接返回；否则先用 appendNTimes 扩容指针数组（填 undefined）， 再逐个为空槽堆分配真实页并清零。调用方必须持有 freelist_mu。

fn ensurePage(self: *MemPageStore, index: u32) !void {
    if (index < self.pages.items.len) return;
    if (index >= self.max_pages) return error.MapFull;
    const old_len = self.pages.items.len;
    try self.pages.appendNTimes(self.allocator, undefined,
        @as(usize, index) + 1 - old_len);
    var i: usize = old_len;
    while (i < self.pages.items.len) : (i += 1) {
        self.pages.items[i] = self.allocator.create([f2.PAGE_SIZE]u8) catch {
            // 部分失败回滚: 销毁本次已分配的页, 收缩指针数组 (F1)
            var j: usize = old_len;
            while (j < i) : (j += 1) self.allocator.destroy(self.pages.items[j]);
            self.pages.shrinkRetainingCapacity(old_len);
            return error.OutOfMemory;
        };
        self.pages.items[i].* = [_]u8{0} ** f2.PAGE_SIZE;
    }
}

部分失败回滚（F1）：循环中某次 create 失败时，必须销毁 [old_len, i) 范围内本次已成功分配的页，再用 shrinkRetainingCapacity(old_len) 把指针数组收缩回 old_len。否则 pages 中会残留 undefined 指针，后续 deinit 的 destroy 会解引用垃圾地址导致未定义行为。这是"扩容两步走"（先扩数组再填页）必须配套的回滚逻辑。

为什么先 appendNTimes 再逐个分配？appendNTimes 一次性把指针数组扩到目标长度 （填 undefined 占位），避免循环内逐个 append 的多次扩容抖动。随后循环只需填值，逻辑清晰。 代价是 appendNTimes 本身可能 OutOfMemory——但此时尚未分配任何页，无回滚负担，直接传播错误即可。

allocPage / freePage：分配与回收

vtAllocPage 是分配入口，优先从 freelist 取（LIFO 回收的页号），取不到再 bump 分配。 全程持锁。

fn vtAllocPage(ptr: *anyopaque) !u32 {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    self.freelist_mu.lockUncancelable();
    defer self.freelist_mu.unlock();
    if (self.freelist.items.len > 0) return self.freelist.pop().?;
    const pn = self.next_free;
    if (pn >= self.max_pages) return error.MapFull;
    try self.ensurePage(pn);
    self.next_free = pn + 1;
    return pn;
}
freelist 非空? → 是 pop() LIFO 取页号 → 否 pn = next_free → ensurePage(pn) → next_free++

vtFreePage 把页号追加到 freelist（LIFO）。不释放页数据——页指针仍留在 pages 中，下次 allocPage 直接复用。append 失败时静默忽略（catch {}）， 因为 freelist 丢失最坏只是页不可复用，不应因回收失败而中断调用方。

fn vtFreePage(ptr: *anyopaque, page_no: u32) void {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    self.freelist_mu.lockUncancelable();
    defer self.freelist_mu.unlock();
    self.freelist.append(self.allocator, page_no) catch {};
}

readPage / writePage：页读写与锁粒度

读写页对 meta 页号（1、2）特判，直接返回 meta0/meta1 缓冲区，不走 pages。 普通页则持锁后索引 pages。writePage 会先 ensurePage 确保页存在再返回可变切片。

fn vtReadPage(ptr: *anyopaque, page_no: u32) ![]const u8 {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    if (page_no == f2.META_PAGE_0) return &self.meta0;
    if (page_no == f2.META_PAGE_1) return &self.meta1;
    self.freelist_mu.lockUncancelable();
    defer self.freelist_mu.unlock();
    if (page_no >= self.pages.items.len) return error.PageNotFound;
    return self.pages.items[page_no][0..]; // 切片在 unlock 后仍有效
}

fn vtWritePage(ptr: *anyopaque, page_no: u32) ![]u8 {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    if (page_no == f2.META_PAGE_0) return &self.meta0;
    if (page_no == f2.META_PAGE_1) return &self.meta1;
    self.freelist_mu.lockUncancelable();
    defer self.freelist_mu.unlock();
    try self.ensurePage(page_no);
    return self.pages.items[page_no][0..];
}

锁粒度精巧：freelist_mu 只保护 pages 指针数组的查找与扩容，不保护页数据内容。 readPage 在锁内取到切片后立即 unlock 返回。因为每页是独立堆分配（地址稳定）， 切片在 unlock 后仍有效。这允许读者在锁外长时间持有切片读数据，写者可并行扩容 pages （不会移动已分配页的数据），仅短暂争用指针数组查找。这是地址稳定性设计带来的并发收益。

注意：lockUncancelable 而非 lock——选择不可取消的锁版本，避免在持锁期间 因取消点导致锁泄漏。defer unlock() 保证异常路径也能释放。这是 Zig 错误传播 + 延迟释放的标准范式。

readMeta / writeMeta：双页交替写（crash 安全）

meta 页是数据库的"根指针"——存 root_page、sequence、free_head 等关键元信息。 一旦损坏，整个库不可用。MemPageStore 用两个 meta 页（meta0/meta1）交替写入来保证 crash 安全：每次写 meta 先写其中一个，下次写另一个，读时取 sequence 大者。

fn vtReadMeta(ptr: *anyopaque) !?f2.MetaPage {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    return f2.readMetaPage(&self.meta0, &self.meta1);
}

fn vtWriteMeta(ptr: *anyopaque, meta: *const f2.MetaPage) !void {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    const page = if (self.meta_index == 0) &self.meta0 else &self.meta1;
    f2.writeMetaPage(page, meta, self.meta_index);
    self.meta_index = 1 - self.meta_index; // 翻转 0↔1
}
meta_index=0 → 写 meta0 → meta_index 翻转 → 1 → meta_index=1 → 写 meta1 → meta_index 翻转 → 0 → ↻

readMetaPage（定义在 format.zig）的核心逻辑是：分别尝试从 meta0 和 meta1 解码，校验 checksum 与 magic/version，取 sequence 更大者返回。若只有一个有效，返回有效的那个；都无效返回 null。

// format.zig 中的读 meta 逻辑
pub fn readMetaPage(page0: *const [PAGE_SIZE]u8,
                    page1: *const [PAGE_SIZE]u8) ?MetaPage {
    const m0 = readMetaPageSingle(page0);
    const m1 = readMetaPageSingle(page1);
    if (m0 == null and m1 == null) return null;
    if (m0 == null) return m1;
    if (m1 == null) return m0;
    return if (m0.?.sequence >= m1.?.sequence) m0 else m1;
}

crash 安全原理：假设写 meta0 时崩溃——meta1 仍保留上次完整写入，readMetaPage 会取到 meta1（meta0 checksum 校验失败返回 null，只剩 m1）。下次写会写 meta1（因为 index 已翻转），覆盖 那个损坏的旧值……不，交替写保证每次写的是另一个页。只要任一页完好且 sequence 最新， 恢复就能成功。两页轮流牺牲，互为备份。

MemPageStore 的局限：因为是内存实现，crash 后整个 MemPageStore 随进程消失， 双页恢复机制在此并无实际意义——它的价值在于语义对齐：上层代码用 MemPageStore 测试时， meta 读写行为与未来的 FilePageStore 完全一致，测试可无缝迁移。真正的 crash 安全在 FilePageStore + mmap + fsync 时才生效。

sync / mapsize：收尾方法

vtSync 是空实现——内存无需 fsync。但它必须存在以满足 VTable 契约，上层调用 store.sync() 时不会因实现缺失而失败。

fn vtSync(ptr: *anyopaque) !void {
    _ = ptr; // 内存实现无需 fsync
}

fn vtMapSize(ptr: *anyopaque) u64 {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    return self.max_pages;
}

vtMapSize 返回 max_pages，即页数上限。上层用此判断是否还有分配空间（对应 mmap 的 mapsize）。

mem_vtable：VTable 实例

模块级常量 mem_vtable 把七个函数指针打包成 PageStore.VTable 结构。 MemPageStore.store() 返回的 PageStore 即引用此表。这是 Zig 手动多态的标准范式：

const mem_vtable: PageStore.VTable = .{
    .allocPage  = MemPageStore.vtAllocPage,
    .freePage   = MemPageStore.vtFreePage,
    .readPage   = MemPageStore.vtReadPage,
    .writePage  = MemPageStore.vtWritePage,
    .readMeta   = MemPageStore.vtReadMeta,
    .writeMeta  = MemPageStore.vtWriteMeta,
    .sync       = MemPageStore.vtSync,
    .mapsize    = MemPageStore.vtMapSize,
};

设计总结与风险清单

设计亮点：

  1. slab 页池 + 指针数组：每页独立堆分配保证地址稳定，读者切片不因扩容悬垂，并发读写安全。
  2. LIFO freelist：回收页号优先复用，减少 bump 游标增长；不释放页数据，复用零开销。
  3. 锁粒度最小化：锁只护指针数组查找/扩容，页数据访问在锁外，并发性好。
  4. meta 双页交替写：语义对齐 FilePageStore，crash 安全逻辑可测可复用。
  5. ensurePage 部分失败回滚：两步扩容配套彻底回滚，杜绝 undefined 指针残留。
风险点说明缓解
freelist append 静默失败freePage 的 catch {} 丢失回收页号最坏只是页不可复用（仍占内存），不影响正确性；deinit 统一释放
readPage 越界page_no >= pages.len 返回 PageNotFound显式边界检查，调用方须处理 error
MapFullnext_free >= max_pages 或 ensurePage 超限上层应预检 mapsize() 或捕获 MapFull
meta_index 无锁vtWriteMeta 读写 meta_index 未持 freelist_mu设计上 meta 写由单一 writer 串行调用（上层 db.zig 保证），非并发热点
不持久化进程结束数据全失仅用于测试；生产用 FilePageStore

MemPageStore 以最小代价完整实现了页 Store 契约。它的每一处设计——指针数组、LIFO freelist、 锁粒度、meta 双页、回滚——都不是随意的，而是为语义对齐与未来 FilePageStore 复用服务。理解它，就理解了 cube_db 页存储层的骨架。
