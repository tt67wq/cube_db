第三部分mmap 预留区与按需增长 + FilePageStore 初始化/生命周期

src/file_page_store.zig 是生产级页 Store。与测试用的 MemPageStore（堆分配页池）不同， 它把整个数据库视作一个 LMDB 式 1TB 预留 mmap 区：open 时一次性 mmap 占位 1TB 虚拟地址， 文件按需 ftruncate 增长，读写经同一 mmap 指针、零拷贝。本部分精讲它的预留思想、结构体字段、 init 初始化与崩溃恢复流程，以及生命周期方法。

3.1 文件头注释与设计思路

//! file_page_store.zig — 文件页 Store（LMDB 式 1TB 预留 mmap 区）
//!
//! open 时 mmap 1TB MAP_SHARED 预留虚拟区（方案 I，spike_mmap.zig 已验证 macOS 可行）。
//! 文件按需 ftruncate 增长，reader 经同一 mmap 指针读新数据，无 SIGBUS、无需重 mmap。
//! 写路径保留 PageStore 页接口（allocPage/freePage/writePage）；读路径零拷贝直接 mmap 指针。
const std = @import("std");
const f2 = @import("format.zig");
const ps = @import("page_store.zig");
const c = @cImport({
    @cInclude("sys/mman.h");
    @cInclude("sys/stat.h");
    @cInclude("fcntl.h");
    @cInclude("unistd.h");
});

const PAGE_SIZE = f2.PAGE_SIZE;

四个 C 头各司其职：sys/mman.h 提供 mmap/munmap/MAP_SHARED； sys/stat.h 提供 fstat 与 struct stat；fcntl.h 提供 open 与 O_RDWR/O_CREAT； unistd.h 提供 close/ftruncate/fsync/unlink。三个 Zig 模块中 ps（page_store.zig） 提供 PageStore 接口与 FIRST_DATA_PAGE，f2 提供 PAGE_SIZE 与 meta 编解码。

LMDB 式预留的三个关键点：

  • 预留虚拟地址，不预留物理内存/磁盘。 64-bit 进程虚拟地址空间充裕（2⁴⁸ 量级）， mmap 1TB 仅占页表项与虚拟区记录，内核按需按页 fault-in 物理页，不实际占用 1TB。
  • 文件按需 ftruncate 增长，mmap 指针永不变。 写新页前 ensureFileGrowth 把文件 扩到覆盖该页；已扩区域通过同一 mmap_ptr 立即可见，无需重 mmap、无 SIGBUS。
  • 读路径零拷贝。 读页 = 取 mmap_ptr + page_no*PAGE_SIZE 指针，直接借切片，无 read 系统调用、无内存拷贝。
⚠️ 注意 平台前提：此设计依赖「文件增长后旧 mmap 指针对新区域可见」。 MAP_SHARED + 文件 backing 在 Linux/macOS 上成立；某些系统（如旧 mmap 实现需 MAP_NONBASE 或重 mmap）不保证。文件注释提到「spike_mmap.zig 已验证 macOS 可行」即此意。

3.2 REGION_SIZE：1TB 预留区常量

/// 1 TB 预留虚拟区（LMDB 式占位；64-bit 系统虚拟地址空间充裕）
pub const REGION_SIZE: u64 = 1 << 40;

1 << 40 = 2⁴⁰ 字节 = 1099511627776 B = 1 TiB。按 PAGE_SIZE=4096 折算 = 2²⁸ = 268435456 页（约 2.68 亿页）， 即 mapsize() 返回的上限。这个值是工程取舍：

维度值含义
字节2⁴⁰ = 1 TiBregion_size 字段
页数上限2²⁸ ≈ 2.68 亿vtMapSize 返回 region_size / PAGE_SIZE
虚拟占用仅页表（无物理占）内核按需 fault
磁盘占用按已写页数 ×4KB稀疏增长，非 1TB 预分配
✅ 提示 为何选 1TB 而非「按需重 mmap 扩区」？ 重 mmap（MAP_FIXED 或 MREMAP）在跨平台/跨进程下复杂且可能移动地址，使所有借用切片悬垂。预留固定 1TB 让 mmap_ptr 在进程生命期不变——这是 readPage 零拷贝借切片能安全的根本前提。

3.3 FilePageStore 结构体字段

pub const FilePageStore = struct {
    allocator: std.mem.Allocator,
    fd: c_int,
    region_size: u64,
    mmap_ptr: [*]u8,
    freelist: std.ArrayList(u32),
    next_free: u32,
    meta_index: u32,
    meta0: [PAGE_SIZE]u8,
    meta1: [PAGE_SIZE]u8,
字段类型含义
allocatorAllocator用于 freelist 增长与 path 复制；页数据不进堆（在 mmap 区）
fdc_int文件描述符。ftruncate/fsync/close 都经它
region_sizeu64预留区字节大小，恒等于 REGION_SIZE；独立字段便于 regionSize()
mmap_ptr[*]u81TB 区起始指针。不变量：进程生命期内地址恒定
freelistArrayList(u32)回收页号 LIFO 链。与 MemPageStore 同形
next_freeu32bump 分配水位。init 时从活跃 meta 的 last_page+1 恢复
meta_indexu32下次写哪页 meta（0/1）。交替写以崩溃安全
meta0/meta1[PAGE_SIZE]u8meta 双缓冲（进程内副本）。写时先改缓冲，再 flushMetaBuffer 刷到 mmap 区
💡 说明 为什么 meta 要进程内缓冲副本？ mmap 区是文件视图，写 meta 前要在缓冲里 writeMetaPage（编页头 + payload + CRC），再整页 @memcpy 刷到 mmap 区。这样 meta 的 CRC、 页头一次性写入文件视图，避免「半写页」被 readMetaPage 当作合法页读到中间态。也方便 vtReadMeta 先 @memcpy 同步缓冲再解码（reader 可能在跨进程被改写）。

3.4 init：open + ftruncate 初始页 + mmap + meta 恢复

init 是本文件最复杂的方法，分四阶段：

① open 文件 → ② ftruncate 到 ≥3 页 → ③ mmap 1TB MAP_SHARED → ④ 加载 meta + 恢复 index/next_free

① open 文件（O_RDWR | O_CREAT, 0644）

pub fn init(allocator: std.mem.Allocator, path: []const u8) !FilePageStore {
    const path_z = try allocator.dupeZ(u8, path);
    defer allocator.free(path_z);
    const fd = c.open(path_z, @as(c_int, c.O_RDWR | c.O_CREAT), @as(c.mode_t, 0o644));
    if (fd < 0) return error.OpenFailed;

路径要先 dupeZ 成 NUL 终止的 C 字符串（c.open 要 [*:0]const u8）。 O_RDWR | O_CREAT 表示读写打开、不存在则建；0o644 权限。fd<0 即失败。

② ftruncate 到至少覆盖 meta0 + meta1（3 页）

    var st: c.struct_stat = undefined;
    if (c.fstat(fd, &st) != 0) {
        _ = c.close(fd);
        return error.FstatFailed;
    }
    const min_size: u64 = @as(u64, ps.FIRST_DATA_PAGE) * PAGE_SIZE;  // 3*4096
    if (@as(u64, @intCast(st.st_size)) < min_size) {
        if (c.ftruncate(fd, @as(c.off_t, @intCast(min_size))) != 0) {
            _ = c.close(fd);
            return error.TruncateFailed;
        }
    }

页号 0=NULL、1=meta0、2=meta1、3 起数据页（FIRST_DATA_PAGE=3）。无论新库旧库， 文件至少要 3 页（12288 字节）才能承载双 meta。fstat 看当前大小，不够就 ftruncate 扩到 min_size。 每条失败路径都先 close(fd) 再返错，防 fd 泄漏。

③ mmap 1TB MAP_SHARED 预留区

    const ptr = c.mmap(
        null, REGION_SIZE,
        @as(c_int, c.PROT_READ) | @as(c_int, c.PROT_WRITE),
        @as(c_int, c.MAP_SHARED), fd, 0);
    if (ptr == c.MAP_FAILED) {
        _ = c.close(fd);
        return error.MapFailed;
    }

MAP_SHARED 意味着写经页缓存写回文件（非 MAP_PRIVATE 的 COW）；PROT_READ|PROT_WRITE 双向可访问。 offset=0 从文件头映射。返 MAP_FAILED 即失败（关 fd 后返 MapFailed）。成功后 mmap_ptr 指向这 1TB 区——此后进程生命期不动。

⚠️ 注意 MAP_SHARED 的写语义： 写 mmap 区不是立即落盘，而是脏化页缓存，由内核写回线程 或 fsync 刷盘。事务提交时 vtSync 调 fsync(fd) 强制页缓存写回——这是 「mmap 写 + fsync 持久化」组合的语义边界。崩溃在 fsync 前 → 数据可能丢，靠 meta 交替写恢复一致性。

④ 加载 meta 缓冲 + 恢复 meta_index 与 next_free

    var fps: FilePageStore = .{
        .allocator = allocator, .fd = fd, .region_size = REGION_SIZE,
        .mmap_ptr = @ptrCast(ptr), .freelist = .empty,
        .next_free = ps.FIRST_DATA_PAGE, .meta_index = 0,
        .meta0 = [_]u8{0} ** PAGE_SIZE, .meta1 = [_]u8{0} ** PAGE_SIZE,
    };

    // 从 mmap 区加载 meta 缓冲区
    @memcpy(fps.meta0[0..PAGE_SIZE], fps.pagePtr(f2.META_PAGE_0)[0..PAGE_SIZE]);
    @memcpy(fps.meta1[0..PAGE_SIZE], fps.pagePtr(f2.META_PAGE_1)[0..PAGE_SIZE]);

先把 mmap 区第 1、2 页（meta0/meta1 的文件视图）拷进进程内缓冲 meta0/meta1。 之后所有 meta 读写都走缓冲，避免反复直接碰 mmap 区的半页中间态。pagePtr 见 3.5 节。

    const m0 = f2.readMetaPageSingle(&fps.meta0);  // 校验 CRC + 解码，无效返 null
    const m1 = f2.readMetaPageSingle(&fps.meta1);
    if (m0 != null and m1 != null) {
        if (m0.?.sequence >= m1.?.sequence) {
            fps.meta_index = 1;                       // meta0 活跃，下次写 meta1
            fps.next_free = @max(fps.next_free, m0.?.last_page + 1);
        } else {
            fps.meta_index = 0;                       // meta1 活跃，下次写 meta0
            fps.next_free = @max(fps.next_free, m1.?.last_page + 1);
        }
    } else if (m0 != null) {
        fps.meta_index = 1;                           // 仅 meta0 合法，下次写 meta1
        fps.next_free = @max(fps.next_free, m0.?.last_page + 1);
    } else if (m1 != null) {
        fps.meta_index = 0;                           // 仅 meta1 合法，下次写 meta0
        fps.next_free = @max(fps.next_free, m1.?.last_page + 1);
    }
    // else: 都 null（fresh DB），meta_index 保持 0，next_free 保持 FIRST_DATA_PAGE
    return fps;

这是 reopen 的崩溃恢复核心。四种情形：

meta0meta1活跃判定meta_index（下次写哪页）next_free
合法合法sequence 较大者活跃指向非活跃页（覆盖旧者）max(FIRST_DATA_PAGE, 活跃.last_page+1)
合法无效meta0 活跃1（下次写 meta1）max(..., m0.last_page+1)
无效合法meta1 活跃0（下次写 meta0）max(..., m1.last_page+1)
无效无效fresh DB0FIRST_DATA_PAGE
✅ 提示 交替写的恢复逻辑： 活跃 meta 是最近一次成功写入且通过 CRC 校验的那页。 meta_index 总指向下一该写的另一页——即覆盖较旧/无效的那页，保留较新合法页不动。 这样任一时刻 vtWriteMeta 之前，磁盘上总有一份合法旧 meta；若写中途崩溃，下次 init 读到的仍是上次合法页（CRC 保护 + sequence 比较），一致性得以维持。
⚠️ 注意 next_free 恢复的 max 防护： 用 @max(FIRST_DATA_PAGE, last_page+1) 而非直接 last_page+1，防活跃 meta 的 last_page 因某种原因小于 FIRST_DATA_PAGE-1 （如手动写入的脏 meta）导致 next_free 倒退覆盖保留页。最低水位锁死在 FIRST_DATA_PAGE。

3.5 页指针寻址：pagePtr

fn pagePtr(self: *FilePageStore, page_no: u32) [*]u8 {
    return self.mmap_ptr + @as(usize, @intCast(page_no)) * PAGE_SIZE;
}

这是整个文件页 Store 的寻址基石：页号是文件偏移的 PAGE_SIZE 倍数，pagePtr(n) = mmap_ptr + n*4096。 没有任何查找表、没有间接层——页号到地址是纯算术。这让 readPage/writePage 是 O(1) 且零拷贝。

与 MemPageStore 的寻址对比：

  • MemPageStore：pagePtr = 在 pages.items[page_no] 里查独立堆分配的页指针（两次间接 + 边界检查）。
  • FilePageStore：pagePtr = mmap_ptr + page_no*PAGE_SIZE（一次加法），页地址在预留区内连续。

预留 mmap 的根本收益即在此：把「按页号查页」从一次指针数组访问降为一次偏移算术， 且所有页共享一个稳定基地址——借用切片永不悬垂。

3.6 生命周期方法：deinit / regionSize / store

pub fn deinit(self: *FilePageStore) void {
    _ = c.munmap(@ptrCast(self.mmap_ptr), REGION_SIZE);
    _ = c.close(self.fd);
    self.freelist.deinit(self.allocator);
}

pub fn regionSize(self: *const FilePageStore) u64 {
    return self.region_size;
}

pub fn store(self: *FilePageStore) ps.PageStore {
    return .{ .ptr = self, .vtable = &file_vtable };
}

deinit 三步：munmap 释放 1TB 虚拟区映射、close 关 fd、freelist.deinit 释放回收链。 注意 deinit 不刷 meta 也不 fsync——持久化是 vtWriteMeta+vtSync 的职责，deinit 只回收资源； 若调用方在 deinit 前未 commit，已写但未 sync 的数据可能丢（符合事务语义）。

store() 把 *FilePageStore 装箱成 ps.PageStore：ptr=self，vtable=&file_vtable。 file_vtable 是模块级 const（第二部分详述），进只读段，生命周期安全——这与 MemPageStore 的 mem_vtable 同形。之后上层（btree/db）只持 PageStore 值，对底层是内存还是文件无感知。

3.7 flushMetaBuffer：缓冲刷盘（mmap 区）

fn flushMetaBuffer(self: *FilePageStore, page_no: u32) void {
    const buf = if (page_no == f2.META_PAGE_0) &self.meta0 else &self.meta1;
    const dst = self.pagePtr(page_no);
    @memcpy(dst[0..PAGE_SIZE], buf[0..PAGE_SIZE]);
}

vtWriteMeta 先在缓冲里 f2.writeMetaPage（编页头+payload+CRC），再调本方法把整页 4KB @memcpy 到 mmap 区对应页。整页一次性写，配合 MAP_SHARED 脏化页缓存、再 fsync 落盘。 这样磁盘上要么是旧完整页、要么是新完整页，不会出现半页（页尾 CRC 还没算的中间态）——这是 readMetaPageSingle 能用 CRC 区分合法/无效页的物理保证。

3.8 ensureFileGrowth：按需 ftruncate

fn ensureFileGrowth(self: *FilePageStore, page_no: u32) !void {
    const t0 = if (FpsCounters.enable) FpsCounters.now() else 0;
    const needed: u64 = (@as(u64, page_no) + 1) * PAGE_SIZE;
    var st: c.struct_stat = undefined;
    if (c.fstat(self.fd, &st) != 0) return error.FstatFailed;
    if (FpsCounters.enable) FpsCounters.fstat_calls += 1;
    if (@as(u64, @intCast(st.st_size)) < needed) {
        if (c.ftruncate(self.fd, @as(c.off_t, @intCast(needed))) != 0)
            return error.TruncateFailed;
        if (FpsCounters.enable) FpsCounters.ftruncate_calls += 1;
    }
    if (FpsCounters.enable) FpsCounters.ensure_growth_ns += @intCast(FpsCounters.now() - t0);
}

vtAllocPage/vtWritePage 在分配/写新页前调用。逻辑：算出覆盖 page_no（含整页）所需字节 (page_no+1)*PAGE_SIZE，fstat 查当前文件大小，不够就 ftruncate 扩到 needed。

💡 说明 为何每次写都要 fstat？ ftruncate 是幂等的（文件已够大时再调一次也安全）， 但每次写都 ftruncate 会产生不必要的系统调用。fstat 先查、只在确实不够时才 ftruncate，减少写路径的系统调用。 代价是 fstat 本身也是一次 syscall——对极热路径，可考虑缓存文件大小（但需处理跨进程并发增长，当前选保守 fstat）。
⚠️ 注意 稀疏文件与空间： ftruncate 扩的是文件逻辑大小，不立即占物理空间—— 内核在写时才分配物理块。故一个 1TB 预留映射 + 按需 ftruncate 的库，实际磁盘占用 ≈ 已写页数 × 4KB。 但若文件系统不支持稀疏文件（极少见），ftruncate 会预分配全量空间——这是平台前提之一。

FpsCounters 计数只在 enable=true 时累加（profile 开关），生产热路径 enable=false 时分支被 if (false) 优化掉，零开销。第二部分会详述 FpsCounters 全貌。

3.9 初始化/生命周期全景

init: open → ftruncate≥3 页 → mmap 1TB → 加载 meta 缓冲 → 恢复 index/next_free → store() 装箱
运行期: vtWriteMeta→flushMetaBuffer→vtSync(fsync) → 写数据页: vtWritePage→ensureFileGrowth
deinit: munmap + close + freelist.deinit
🔴 危险 生命周期风险：
  • mmap_ptr 在 munmap（deinit）后失效。任何在 deinit 后仍持 readPage 借用切片的调用方都会访问已解除映射的地址 → 段错误。调用方须保证借用短于 deinit。
  • file_vtable 是模块级 const，生命周期 = 进程，安全；但若误把实例 store() 返回值在实例 deinit 后再用，ptr 即悬垂。当前接口设计假定实例存活长于所有借用。

第三部分到此。下一部分（第四部分）讲解 8 个 vtable 函数的实现、meta 交替写的崩溃安全细节、 file_vtable 定义、以及与 MemPageStore 的对比。

第四部分PageStore 接口实现 · meta 崩溃恢复 · 与 MemPageStore 对比

上一部分讲解了 mmap 预留区与 FilePageStore 的初始化/生命周期。本部分聚焦 FilePageStore 如何实现 PageStore 抽象层定义的全部八个 vtable 方法，以及它相对于内存实现独有的能力：基于 mmap 的 零拷贝读写、meta 双页交替写的崩溃安全保证、以及 fsync 持久化语义。最后将两者并排对比， 厘清相同骨架与分叉路径。

本部分核心命题：FilePageStore 与 MemPageStore 共享相同的分配骨架 （bump 游标 + LIFO freelist）和 meta 双页交替写策略，但底层存储范式根本不同——前者读写经 mmap 指针 直接操作页缓存（零拷贝），后者读写经独立堆分配页副本。这决定了它们的并发模型、持久化能力、crash 恢复 是否真正生效。

file_vtable：模块级静态 VTable

与 MemPageStore 完全对称，FilePageStore 也通过模块级常量定义 vtable。 file_vtable 是一个 const 声明，存储在二进制的数据段（静态存储期），生命周期 不随任何 FilePageStore 实例的创建与销毁而变化。

const file_vtable: ps.PageStore.VTable = .{
    .allocPage  = FilePageStore.vtAllocPage,
    .freePage   = FilePageStore.vtFreePage,
    .readPage   = FilePageStore.vtReadPage,
    .writePage  = FilePageStore.vtWritePage,
    .readMeta   = FilePageStore.vtReadMeta,
    .writeMeta  = FilePageStore.vtWriteMeta,
    .sync       = FilePageStore.vtSync,
    .mapsize    = FilePageStore.vtMapSize,
};

💡 说明 静态存储不变量：因为 file_vtable 是模块级 const，其地址在编译期 固定。store() 方法返回的 PageStore 句柄中 vtable 字段指向这个固定地址。 只要进程存活，vtable 就有效——上层代码可以安全持有 PageStore 句柄而无需担心 vtable 悬垂。 这与 MemPageStore 的 mem_vtable 设计完全一致，是 Zig 手动多态的标准范式。

pub fn store(self: *FilePageStore) ps.PageStore {
    return .{ .ptr = self, .vtable = &file_vtable };
}

store() 把 self 指针和 &file_vtable 打包成 PageStore 多态句柄。 调用方拿到句柄后，所有方法调用经 vtable 间接分发到 FilePageStore 的具体实现。注意 ptr 是 *anyopaque，每个 vtable 函数入口需 @ptrCast(@alignCast(ptr)) 还原为 *FilePageStore。

pagePtr：mmap 寻址基础

几乎所有 vtable 方法的读写都依赖 pagePtr 这个简单的地址计算函数。它是理解整个读写路径的基石：

fn pagePtr(self: *FilePageStore, page_no: u32) [*]u8 {
    return self.mmap_ptr + @as(usize, @intCast(page_no)) * PAGE_SIZE;
}

页号到文件偏移的映射极简：偏移 = page_no × PAGE_SIZE。mmap_ptr 是 1TB 预留区的基地址， pagePtr(n) 返回 mmap_ptr + n*4096。页号 0 是 NULL 页（文件偏移 0），页号 1 是 meta0， 页号 2 是 meta1，页号 3 起是数据页。这种线性映射意味着不需要任何索引结构就能定位任意页—— 地址计算 O(1)，比 MemPageStore 的 ArrayList 索引更直接（后者需确保数组已扩容到该索引）。

⚠️ 注意 越界检查不在 pagePtr 内：pagePtr 不做边界检查，调用方必须自行校验 page_no * PAGE_SIZE < region_size。各 vtable 方法在调用 pagePtr 前都有显式的 越界判断（返回 MapFull 或 PageNotFound）。这是性能取舍——热路径省一个分支。

vtAllocPage / vtFreePage：分配与回收

vtAllocPage 与 MemPageStore 版本逻辑结构相同：先 freelist 取（LIFO），取不到再 bump 分配。但有两个关键差异：无锁（FilePageStore 设计为单写者模型）和 ensureFileGrowth（按需 ftruncate 扩展文件）。

fn vtAllocPage(ptr: *anyopaque) !u32 {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    const t0 = if (FpsCounters.enable) FpsCounters.now() else 0;
    if (FpsCounters.enable) FpsCounters.alloc_page_calls += 1;
    if (self.freelist.items.len > 0) return self.freelist.pop().?;
    const pn = self.next_free;
    if (@as(u64, pn) * PAGE_SIZE >= self.region_size) return error.MapFull;
    try self.ensureFileGrowth(pn);
    self.next_free = pn + 1;
    if (FpsCounters.enable) FpsCounters.alloc_page_ns += @intCast(FpsCounters.now() - t0);
    return pn;
}
freelist 非空? → 是 pop() LIFO → 否 pn = next_free → 越界? → MapFull → ensureFileGrowth(pn) → next_free++

与 MemPageStore 的对比要点：

  • 无锁：MemPageStore 用 freelist_mu 串行化分配/回收/读； FilePageStore 无锁。设计前提是上层（db.zig）保证单一写者串行调用 allocPage/freePage/writePage。
  • 无 ensurePage 的回滚问题：MemPageStore 的 ensurePage 需两步扩容（先扩指针数组再逐页堆分配），有部分失败回滚负担；FilePageStore 的 ensureFileGrowth 只调一次 ftruncate，要么成功要么直接返回错误，无中间态。
  • 上限判断不同：MemPageStore 比较 pn >= max_pages（页数上限）； FilePageStore 比较 pn * PAGE_SIZE >= region_size（字节偏移到 1TB 预留区上限）。

vtFreePage 与内存版完全一致：追加页号到 freelist（LIFO），catch {} 静默处理 OOM。 页数据不被释放——mmap 区的页永远"存在"（虚拟地址已预留），freelist 只是记录可复用的页号。

fn vtFreePage(ptr: *anyopaque, page_no: u32) void {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    if (FpsCounters.enable) FpsCounters.free_page_calls += 1;
    self.freelist.append(self.allocator, page_no) catch {};
}

vtReadPage / vtWritePage：零拷贝 mmap 读写

这是 FilePageStore 与 MemPageStore 最本质的区别所在。读写页对 meta 页号（1、2） 特判直接返回缓冲区，普通页经 pagePtr 返回 mmap 指针切片。

fn vtReadPage(ptr: *anyopaque, page_no: u32) ![]const u8 {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    if (FpsCounters.enable) FpsCounters.read_page_calls += 1;
    if (page_no == f2.META_PAGE_0) return &self.meta0;
    if (page_no == f2.META_PAGE_1) return &self.meta1;
    if (@as(u64, page_no) * PAGE_SIZE >= self.region_size) return error.PageNotFound;
    return self.pagePtr(page_no)[0..PAGE_SIZE];
}

fn vtWritePage(ptr: *anyopaque, page_no: u32) ![]u8 {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    const t0 = if (FpsCounters.enable) FpsCounters.now() else 0;
    if (FpsCounters.enable) FpsCounters.write_page_calls += 1;
    if (page_no == f2.META_PAGE_0) return &self.meta0;
    if (page_no == f2.META_PAGE_1) return &self.meta1;
    if (@as(u64, page_no) * PAGE_SIZE >= self.region_size) return error.MapFull;
    try self.ensureFileGrowth(page_no);
    if (FpsCounters.enable) FpsCounters.write_page_ns += @intCast(FpsCounters.now() - t0);
    return self.pagePtr(page_no)[0..PAGE_SIZE];
}

✅ 提示 零拷贝读：vtReadPage 返回的 []const u8 直接指向 mmap 预留区中的 mmap_ptr + page_no*PAGE_SIZE。读操作不经任何内存拷贝——内核将文件页按需调入页缓存（page cache）， 用户态直接通过虚拟地址访问。对比 MemPageStore 返回 pages.items[page_no][0..] （也是零拷贝——返回堆分配页的指针切片），两者都是零拷贝语义，但物理来源不同：mmap 区 vs 独立堆分配。

💡 说明 写路径的 MAP_SHARED 语义：vtWritePage 返回 mmap 区的可变切片 []u8。 调用方写入此切片时，修改直接作用于内核页缓存（因为 mmap 用了 MAP_SHARED）。内核会在后续将脏页 异步刷回磁盘。若需强制持久化，调用 vtSync（fsync）。这与 MemPageStore 写入堆分配页的语义截然不同——后者的写只存在于进程内存，进程退出即消失。

vtWritePage 在返回指针前调 ensureFileGrowth(page_no)——确保文件已 ftruncate 到覆盖该页。若文件尚未增长到 page_no 对应偏移，mmap 读取该区域会触发 SIGBUS。 ensureFileGrowth 是防御此崩溃的关键。

vtWriteMeta：崩溃安全的核心——override + 交替写

vtWriteMeta 是整个 PageStore 接口中逻辑最精妙的方法。它做了三件事：(1) override last_page 为实际已分配页的最大值；(2) 交替写 meta0/meta1；(3) 刷缓冲区到 mmap 区并翻转 meta_index。

fn vtWriteMeta(ptr: *anyopaque, meta: *const f2.MetaPage) !void {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    // 1. Override last_page 为实际最高已分配页号
    var meta_copy = meta.*;
    if (self.next_free > ps.FIRST_DATA_PAGE) {
        meta_copy.last_page = self.next_free - 1;
    } else {
        meta_copy.last_page = 0;
    }
    // 2. 选交替页（与当前活跃页相反）
    const page = if (self.meta_index == 0) &self.meta0 else &self.meta1;
    const page_no = if (self.meta_index == 0) f2.META_PAGE_0 else f2.META_PAGE_1;
    f2.writeMetaPage(page, &meta_copy, self.meta_index);
    // 3. 刷到 mmap 区 + 翻转 index
    self.flushMetaBuffer(page_no);
    self.meta_index = 1 - self.meta_index;
}

⚠️ 注意 为什么 override last_page？调用方传入的 meta 中的 last_page 可能不是最新值——上层 B-tree 层可能在写 meta 前不知道 FilePageStore 内部分配了多少页。 FilePageStore 用自身权威的 next_free - 1（当前已分配的最高页号）覆盖它，保证 reopen 时 init 能正确恢复 next_free（恢复逻辑是 next_free = max(next_free, last_page + 1)）。 若不 override，reopen 后 next_free 可能小于实际已分配页号，导致已用页被错误覆盖（数据损坏）。

🔴 危险 不 override 的后果：假设已分配到页号 100（next_free = 101），但调用方传入 meta.last_page = 50。写 meta 后崩溃。reopen 时 init 读到 last_page = 50， 恢复 next_free = 51。下次 allocPage 返回页号 51——但页号 51–100 可能仍在使用中 （属于 B-tree 节点），被覆盖 → 数据库损坏。override 是防此问题的硬保障。

flushMetaBuffer 把内存缓冲区 meta0/meta1 拷贝回 mmap 区对应的文件位置， 使写入对后续 readMeta 及 reopen 可见：

fn flushMetaBuffer(self: *FilePageStore, page_no: u32) void {
    const buf = if (page_no == f2.META_PAGE_0) &self.meta0 else &self.meta1;
    const dst = self.pagePtr(page_no);
    @memcpy(dst[0..PAGE_SIZE], buf[0..PAGE_SIZE]);
}
meta_index=0 → 写 meta0 → flushMetaBuffer(META_PAGE_0) → meta_index 翻转 → 1 → meta_index=1 → 写 meta1 → flushMetaBuffer(META_PAGE_1) → meta_index 翻转 → 0 → ↻

✅ 提示 崩溃安全原理（与 MemPageStore 对比）：交替写保证：写 meta0 时若崩溃（写入未完成或 checksum 失败），meta1 仍保留上次完整写入的有效状态。reopen 时 init 分别校验两页 checksum 与 magic/version，取 sequence 大者——损坏的那页 checksum 校验失败返回 null， 自动回退到完好的那页。这是 LMDB 式的原子性策略：不做事务日志，而是靠"写新页 + 翻转指针"的写时复制 保证 meta 原子切换。MemPageStore 的 vtWriteMeta 逻辑完全相同（交替写 + 翻转）， 但因为没有持久化，crash 后两页同时消失，恢复逻辑实际不生效——它只是为了语义对齐和测试可迁移性。

init 中的 meta 恢复逻辑（在上一部分详细讲解过，此处补充其与 writeMeta 的闭环关系）：

// init 中：从 mmap 区加载两页缓冲区，再判定活跃页
const m0 = f2.readMetaPageSingle(&fps.meta0);
const m1 = f2.readMetaPageSingle(&fps.meta1);
if (m0 != null and m1 != null) {
    if (m0.?.sequence >= m1.?.sequence) {
        fps.meta_index = 1;  // meta0 活跃，下次写 meta1
        fps.next_free = @max(fps.next_free, m0.?.last_page + 1);
    } else {
        fps.meta_index = 0;  // meta1 活跃，下次写 meta0
        fps.next_free = @max(fps.next_free, m1.?.last_page + 1);
    }
} else if (m0 != null) {
    fps.meta_index = 1;  // 仅 meta0 有效，下次写 meta1
    fps.next_free = @max(fps.next_free, m0.?.last_page + 1);
} else if (m1 != null) {
    fps.meta_index = 0;  // 仅 meta1 有效，下次写 meta0
    fps.next_free = @max(fps.next_free, m1.?.last_page + 1);
}
// else: fresh DB，meta_index=0, next_free=FIRST_DATA_PAGE

💡 说明 writeMeta 与 init 的闭环：vtWriteMeta 写 meta0 后翻转 meta_index 为 1， 下次写 meta1。reopen 时 init 读到 meta0 的 sequence 更大（因为它是最后写入的）， 于是设 meta_index = 1（下次写 meta1）——正好与写入时的翻转方向一致。这个闭环保证：无论在哪一刻 崩溃，reopen 后 meta_index 总是指向"该被覆盖的旧页"，不会覆盖刚写入的最新页。这就是交替写的 原子性保证——无需 fsync meta 即可保证逻辑正确（fsync 只影响物理持久化时机）。

vtReadMeta：从 mmap 同步再读

vtReadMeta 有一个 MemPageStore 版本没有的关键步骤：先从 mmap 区把两个 meta 页 @memcpy 回内存缓冲区，再调 readMetaPage 解码。

fn vtReadMeta(ptr: *anyopaque) !?f2.MetaPage {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    // 先从 mmap 区同步到缓冲区，再读
    @memcpy(self.meta0[0..PAGE_SIZE], self.pagePtr(f2.META_PAGE_0)[0..PAGE_SIZE]);
    @memcpy(self.meta1[0..PAGE_SIZE], self.pagePtr(f2.META_PAGE_1)[0..PAGE_SIZE]);
    return f2.readMetaPage(&self.meta0, &self.meta1);
}

⚠️ 注意 为什么先 memcpy？注释说"reader 可能跨进程写"。在 MAP_SHARED 下，另一个进程 可能通过自己的 mmap 映射同一文件并写了 meta 页。此时 self.meta0/meta1 内存缓冲区 可能还是旧值（上次 init 或 writeMeta 时的快照）。vtReadMeta 每次都从 mmap 区重新同步，保证读到最新值。对比 MemPageStore 的 vtReadMeta 直接读自身缓冲区 （无跨进程场景，缓冲区即唯一真相）——这是文件实现独有的"缓冲区 vs mmap 区一致性"问题。

对比 MemPageStore 版本——一行就完事，因为缓冲区就是数据本体：

// MemPageStore: 直接读缓冲区（无 mmap 同步需求）
fn vtReadMeta(ptr: *anyopaque) !?f2.MetaPage {
    const self: *MemPageStore = @ptrCast(@alignCast(ptr));
    return f2.readMetaPage(&self.meta0, &self.meta1);
}

vtSync / vtMapSize：持久化与容量

vtSync 调 fsync(fd) 强制将内核页缓存中的脏页刷回磁盘。这是 FilePageStore 独有的持久化能力——MemPageStore 的 vtSync 是空实现。

fn vtSync(ptr: *anyopaque) !void {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    if (c.fsync(self.fd) != 0) return error.SyncFailed;
}

fn vtMapSize(ptr: *anyopaque) u64 {
    const self: *FilePageStore = @ptrCast(@alignCast(ptr));
    return self.region_size / PAGE_SIZE;
}

💡 说明 fsync 语义链：写路径经 MAP_SHARED mmap → 写入直接作用于内核页缓存 → 内核异步刷回磁盘（时间不确定） → fsync(fd) 强制同步刷盘并等待完成 → 返回后数据物理持久化。 若不调 sync，进程正常退出时内核也会刷盘，但若崩溃/断电则可能丢数据。sync 是 上层控制持久化时序的接口。注意 fsync 只刷已 ftruncate 到的文件范围内的脏页。

vtMapSize 返回 region_size / PAGE_SIZE——即 1TB 预留区可容纳的页数 （2^40 / 4096 = 2^28 = 268,435,456 页）。对比 MemPageStore 返回 max_pages（构造时指定的页数上限）。两者语义一致——都是"还能分配多少页"的上限参考。

FpsCounters：写路径 profile 计数器

FpsCounters 是一组模块级 pub var 计数器，用 enable 布尔开关控制。 当 enable = false（默认）时，各 vtable 函数中 if (FpsCounters.enable) 分支 不会被编译进热路径（Zig 编译器优化掉常假分支）。

pub const FpsCounters = struct {
    pub var enable: bool = false;
    pub var write_page_calls: u64 = 0;
    pub var alloc_page_calls: u64 = 0;
    pub var free_page_calls: u64 = 0;
    pub var read_page_calls: u64 = 0;
    pub var fstat_calls: u64 = 0;
    pub var ftruncate_calls: u64 = 0;
    pub var write_page_ns: u64 = 0;
    pub var alloc_page_ns: u64 = 0;
    pub var ensure_growth_ns: u64 = 0;

    pub fn reset() void { /* 全部清零 */ }
    pub fn now() i64 { /* clock_gettime MONOTONIC */ }
};
计数器用途
write_page_calls / write_page_ns写页调用次数与累计耗时，量化写路径开销
alloc_page_calls / alloc_page_ns分配页次数与耗时（含 ensureFileGrowth）
ensure_growth_nsftruncate + fstat 累计耗时，定位文件增长瓶颈

read_page_calls / free_page_calls读页与回收页次数

💡 说明 定位与设计：注释明确标注"#41 FPS 写路径计数器（profile 开关，不进生产热路径）"。 enable 默认 false，生产编译时所有 if (FpsCounters.enable) 分支 被优化掉——热路径零开销。开发/调试时设 FpsCounters.enable = true 即可开启计时。 now() 用 clock_gettime(MONOTONIC) 取纳秒级时间戳，reset() 清零全部计数器 用于基准测试前重置。这是典型的"条件编译式 profile hook"——比 #ifdef 更优雅，靠语言层常量折叠 实现零开销。

源码末尾有两个内联测试，分别验证 FilePageStore 最核心的两个行为契约：

test "file_page_store: 1TB region reserved on open" {

    const path = ".fps_region_test.db";
    defer unlinkPath(path);

💡 说明 测试一：1TB 预留验证。验证 init 后 regionSize() 至少 1TB （2^40 字节）。这确认了 mmap 预留区确实映射成功——若 mmap 返回 MAP_FAILED， init 会返回 error.MapFailed，测试会直接 fail（try 传播错误）。 defer unlinkPath 清理测试文件，避免残留。

test "file_page_store: alloc grows file, read-back visible" {
    const allocator = std.testing.allocator;
    const path = ".fps_grow_test.db";
    defer unlinkPath(path);
    var fps = try FilePageStore.init(allocator, path);
    defer fps.deinit();
    const s = fps.store();
    const pn = try s.allocPage();
    const w = try s.writePage(pn);
    @memcpy(w[0..4], "ABCD");
    const r = try s.readPage(pn);
    try std.testing.expectEqualStrings("ABCD", r[0..4]);
}

✅ 提示 测试二：alloc + write + read 回环。这是最核心的端到端验证——allocPage 分配 （触发 ensureFileGrowth 扩展文件），writePage 返回 mmap 可变切片并写入 "ABCD"，readPage 读回同一页验证内容一致。这同时验证了：(1) 分配后文件确实增长 （否则读会 SIGBUS）；(2) 经 mmap 写入的数据对经 mmap 的读取可见（MAP_SHARED 语义）；(3) writePage 和 readPage 返回的指针指向同一物理位置（mmap_ptr + pn*PAGE_SIZE）。unlinkPath 是辅助函数， 把 Zig 切片路径转为 C 字符串后调 unlink 清理文件。

风险清单与设计总结

风险点说明缓解
未调 sync 即崩溃fsync 前脏页仅在页缓存，断电丢失上层在关键 checkpoint 调 store.sync()
meta 写未 fsyncwriteMeta 只 flush 到 mmap（页缓存），未 fsync交替写保证逻辑原子性；物理持久化由上层 sync 统一刷
无锁并发写多写者并发调 allocPage/writePage 会竞态设计为单写者模型，上层 db.zig 串行化
freelist append 静默失败与 MemPageStore 相同的 catch {}最坏页不可复用（不影响正确性）
ensureFileGrowth 重复 fstat每次 allocPage/writePage 都 fstat 查文件大小FpsCounters.fstat_calls 可量化；后续可缓存 st_size
1TB 预留区虚拟空间占 1TB 虚拟地址空间（不占物理内存）64-bit 系统虚拟空间充裕（LMDB 验证）

设计亮点：

  1. mmap 零拷贝：读写经同一 mmap 指针，无内存拷贝，内核页缓存直接映射用户虚拟地址。
  2. 1TB 预留 + 按需增长：虚拟地址一次性预留 1TB，文件按需 ftruncate，无需 remap。
  3. meta 交替写 + last_page override：双页交替写保证逻辑原子性，override 保证 reopen 恢复正确。
  4. 与 MemPageStore 语义对齐：共享 VTable 契约，上层代码零改动切换实现。
  5. FpsCounters 零开销 profile：常量折叠实现开关，生产热路径无额外指令。

FilePageStore 以 mmap MAP_SHARED 为基底，在 MemPageStore 的分配骨架上叠加了零拷贝读写、 按需文件增长、meta 同步与 override、fsync 持久化四层能力。它的每一处设计都服务于持久化与 crash 安全—— 这正是它从"测试用内存 Store"升级为"生产级文件 Store"的核心价值。理解这四层叠加，就理解了 cube_db 页存储层 从内存到文件的完整演进路径。
